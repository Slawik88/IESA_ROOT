# IESA: права доступа и перенос управления внутрь сайта

Дата: 13 октября 2026. Это предлагаемая архитектура. Имена новых сущностей и permissions ниже не означают, что они уже реализованы.

## 1. Что обнаружено в текущем сайте

| Область | Текущий источник | Следствие для переноса |
|---|---|---|
| Пользователи и технические права | `users/admin.py:UserAdmin`, `users/models.py:User` | В административной форме есть `is_staff`, `is_superuser`, группы и прямые права. В дружелюбной панели эти поля не доступны как обычное редактирование профиля |
| Заявки на смену статуса | `users/admin.py:AccountChangeRequestAdmin` | Одобрение, создание Partner и уведомления находятся в административном классе. Логику требуется вынести в общий сервис |
| Карты | `users/services/card_service.py:UserCardService` | Сервис уже есть; расширить проверкой действий, аудитом, транзакцией и результатом операции, использовать с обеих оболочек |
| Модерация | `blog/admin.py:publish_posts`, `reject_posts`, `set_as_draft` | Текущие массовые операции меняют статус через queryset и пишут обычный лог. Нужен общий сервис с причиной, исполнителем и контролем переходов |
| Технические страницы | `core/views.py:admin_analytics`, `component_playground`, `styleguide_md` | Используют широкую проверку `is_staff`; будущая рабочая аналитика должна иметь отдельную возможность |
| Вход от имени пользователя | `users/views/admin_utils.py:impersonate_user` | Сейчас `is_staff` разрешает вход от имени обычного пользователя; защита staff-target уже есть. При переносе право надо отделить от рабочего доступа |
| Бизнес-сотрудник | `users/models.py:Partner.partner_type` | `association_staff` создаёт рабочий профиль без `is_staff`; это правильно сохраняем, но не считаем назначением доступа к панели |
| История визитов | `users/models.py:VisitAudit`, `users/admin.py:VisitAuditAdmin` | Есть предметная история. Новая общая история ссылается на неё, не заменяя детализацию |
| Уведомления администрации | `users/models.py:AdminNotificationProfile`, `users/signals.py` | Профиль ограничен `is_staff`; подписки и получатели должны перейти на права/активные назначения |
| Вложения | `IESA_ROOT/protected_media_views.py:serve_protected_media` | Комментарии обещают owner/staff, но ветви avatars/cards разрешают всем авторизованным, прочие файлы проверяют `is_staff`. Это не готовая объектная модель доступа |
| Настройки сайта | `users/models.py:SiteSettings` | Сейчас singleton без пользовательских полей. Не придумываем UI переключателей, которые ничего не меняют |
| Технические данные | Like, CommentLike, PostView, BlogSubscription, MediaHash | Не переносим каждую таблицу в меню. Нужны предметные действия и диагностика |

Дополнительно существуют `Meeting`, `ClientNote`, `InviteToken`, `InsuranceAgentRequest`, `core.AdminAppeal`, `EventRegistration`, `gallery.Photo`, `products.Product` и маркетинговые модели `core`. Их миграция должна сохранить действующие предметные ограничения и переводы.

Это инвентаризация по исходникам, а не полноценный новый аудит production-доступов. Реальные Django Group, индивидуальные permissions, staff-аккаунты, ACL хранилища и внешние Telegram-интеграции требуется проверить на этапе внедрения. Не копируем систему прав Predvestnik: это другой продукт.

## 2. Основная модель

**Право = действие + ресурс + область + активное назначение.**

Пример: «Мария может проверять и публиковать материалы сообщества»; «Алексей может видеть и корректировать визиты только организаций A и B». Право на организацию A никогда не расширяет другое право до организации B.

Статусы `is_partner`, `is_president`, членство, бизнес-тип `association_staff` и проверка email решают свои задачи. Они не становятся административными ролями. `is_staff` продолжает означать технический вход в Django Admin; новое рабочее назначение не меняет его. Существующий superuser — техническая учётная запись разработчика с исключительными полномочиями Django. Она должна оставаться редкой и защищённой; рабочее делегирование не создаёт новых superuser.

В новом workspace рекомендуется явное назначение владельца даже разработчику. Технический superuser остаётся аварийным способом восстановления назначений, с отдельным аудитом; его нельзя ограничить одной видимостью кнопок. Django Admin должен быть ограничен для обычных операторов после перехода на панель.

По умолчанию всё запрещено. Для списка право определяет queryset, для объекта — повторную проверку его области, для формы — разрешённые поля, для операции — конкретное действие. Спрятанная кнопка не считается защитой.

## 3. Роли первого выпуска

| Шаблон | Для кого | Возможности по умолчанию | Чего нет |
|---|---|---|---|
| Владелец панели | Разработчик или явно назначенный доверенный владелец | Все рабочие разделы, назначения, шаблоны, общая история, настройки | Автоматического создания superuser и выдачи технического доступа |
| Операционный администратор | Ответственный за ежедневную работу | Заявки, участники, карты, партнёры, мероприятия, рабочая аналитика | Управления владельцами/ролями, impersonation, произвольного экспорта всех персональных данных |
| Работа с участниками | Сотрудник ассоциации | Список/контакты участников, бизнес-проверка, заявки на партнёра/сотрудника, обычная выдача/отзыв карты | Права менять доступ, назначать президента, заменять идентификатор карты, управлять контентом |
| Модератор сообщества | Проверяющий контент | Очередь публикаций, публикация/возврат/снятие, модерация комментариев | Контакты участников, права аккаунтов, финансовые данные |
| Редактор сайта | Редактор публичных материалов | Главная, переводы, каталог, преимущества, галерея, публичные партнёры | Договоры, private notes, изменение членства, выдача прав |
| Координатор мероприятий | Организатор | Создание/изменение назначенных мероприятий, регистрации, связь в пределах события | Общая база участников и её экспорт, события вне своей области |
| Менеджер партнёров | Ответственный за организации | Назначенные организации, визиты, встречи, предметная аналитика | Чужие организации, private notes без отдельной политики, управление правами команды |
| Наблюдатель | Контроль процессов | Только разрешённые списки, статусы, агрегаты | Изменения, экспорт, контакты и приватные файлы |

«Администратор доступа» — дополнительный шаблон второго этапа. Может назначать только определённые рабочие шаблоны внутри своей области; не может изменять шаблоны, назначать владельцев или администратора доступа. В первом выпуске права выдаёт владелец, чтобы ограничить сложность делегирования.

Несколько ролей можно назначить одному человеку. Права объединяются только как отдельные пары «набор действий + область»: запрещено сначала объединить все действия, затем все организации и получить их декартово произведение. Если человеку нужна комбинация возможностей с разными областями, показываем отдельные назначения.

## 5. Области и проверка полномочий

Первый выпуск поддерживает `global`, `partner`, `event`. Назначение имеет ровно один тип области и явные объекты. Пустой список объектной области означает нулевой доступ. Глобальная область хранится явным значением; пустота не интерпретируется как «всё».

Отношение ресурса к области задаёт registry: Visit/Meeting → Partner; EventRegistration → Event. Если ресурс не имеет надёжной связи с областью, не пытаемся ограничить его по косвенной строке/названию. Например, общие участники и AccountChangeRequest в первом выпуске доступны только по соответствующей глобальной роли; ограниченный координатор получает проекцию зарегистрированных участников своего события, не глобальный `members.view`.

При создании события event-scoped координатор не имеет права писать в произвольный новый объект. Рекомендуется workflow: глобальный координатор/операционный создаёт событие и назначает ответственного; ограниченный сотрудник редактирует назначенные события. Самостоятельное создание ограниченным координатором добавляется позже как явный сценарий с автоматической привязкой области в той же транзакции.

Проверка операции:

1. Пользователь активен, вошёл, подтвердил email, есть активное назначение по времени сервера.
2. Проверено требуемое действие, допустимая цель и ресурс в области **того же назначения**.
3. Получены только разрешённые поля; вложения связаны с объектом, а не разрешены по префиксу пути.
4. Для POST проверены CSRF, allowlist полей, версия объекта, переход состояния и условия бизнеса.
5. Для опасной операции проверено недавнее подтверждение личности. Для назначения прав — дополнительный предел делегирования.
6. В транзакции повторно проверены критичные полномочия и версия, сохранены изменение и аудит. После commit выполняются внешние уведомления.

Проверки повторяются для HTMX partial, JSON, autocomplete, badge-count, CSV/ICS, preview, upload, downloads и фоновых задач. URL из уведомления не даёт права сам по себе. Недоступный отдельный объект обычно отвечает 404, чтобы не раскрывать его наличие; недоступный раздел — понятным 403. Отсутствующая сессия возвращает предусмотренный сайтами сценарий входа.

## 6. Выдача и отзыв доступа

Рекомендуемые новые структуры в приложении `administration`:

| Сущность | Основные сведения | Ограничения |
|---|---|---|
| `WorkspaceRole` | Стабильный код, название, описание, признак системного шаблона | Уникальный код, архивирование вместо удаления используемой роли |
| `WorkspaceRoleVersion` | Версия, набор кодов возможностей, автор, время | Назначение ссылается на конкретную утверждённую версию |
| `WorkspaceAssignment` | User, версия роли, scope-type, начало/конец, состояние, выдавший, причина | Активность вычисляется по времени, а не только по scheduler; версия для конкурентного изменения |
| `AssignmentPartner`, `AssignmentEvent` | FK назначения и FK ресурса | Уникальные пары; отдельные таблицы с FK вместо JSON списка ID |
| `WorkspaceInvitation` | Email, запланированные назначения, hash токена, срок, отправитель, принятие/отмена | Одно использование, адрес подтверждён, полномочия пригласившего повторно проверены при принятии |
| `AdminActionEvent` | Исполнитель, действующий субъект, действие, объект/область, время, причина, безопасная разница, результат, request-id | Запись не редактируется/не удаляется через рабочую панель |
| `DeliveryJob` / outbox | Ссылка на событие, канал, статус, попытки, ключ уникальности | Повторяет доставку, не бизнес-действие |

Django Permission можно использовать как реестр кодов. Groups допустимы как совместимость для технических разрешений, но сами не выражают сроки и object-scope. Не строим одновременно две независимые системы «Groups» и «назначения» с разными итоговыми правами. Авторитетный источник workspace — назначения; технический Django Admin проходит свой ограниченный gate.

Для изменения шаблона предлагаем версии: владелец видит изменение и затронутые назначения. Расширение создаёт новую версию и явное обновление выбранных назначений; старые не получают новое право молча. Экстренное сужение/отзыв опасного права блокирует соответствующую версию немедленно, без ожидания ручного обновления каждого сотрудника.

**Bootstrap владельца:** проверенная management-команда по точному существующему User ID; dry-run показывает цель, реальный запуск журналируется. Это не регистрационная форма и не автоматическая выдача первому вошедшему. Аварийное восстановление последнего владельца — только разработчиком через защищённую техническую процедуру.

### Ограничения делегирования

- Только владелец назначает владельца и меняет шаблоны. Для передачи владения новый владелец принимает назначение до отзыва прежнего.
- Делегирующий администратор выбирает только явно разрешённые шаблоны и подмножество своей административно управляемой области. Его собственное право выполнить операцию не означает право передать её другому.
- Нельзя назначить/повысить собственные права, редактируя свой User или assignment. Существующая область не расширяется через подмену hidden input.
- Нельзя управлять владельцем либо равным/более привилегированным администратором вне явно разрешённого процесса.
- Нельзя убрать последнего активного владельца. Проверка выполняется под транзакционной блокировкой, включая одновременные изменения и будущую дату окончания.
- Приглашение не закрепляет права навсегда: при принятии проверяем, что оно не отменено, ещё не использовано, адрес совпадает и отправитель всё ещё вправе выдавать именно этот доступ.

### Немедленный отзыв

Для первого выпуска читаем назначения из БД на каждом административном запросе и критическом действии. Уже используемый Django `user._perm_cache` не должен сохранять право между запросами или заменять scoped-policy. В интерфейсе и обработчике разрешения получаются из одного request-local контекста; перед commit критической операции контекст обновляется/проверяется под блокировкой.

Отзыв действует со следующего серверного запроса. Открытая вкладка может пока показывать старую кнопку, но POST не выполняется. Уже подготовленные экспорты и downloads повторно проверяют права при выдаче. Фоновая рассылка проверяет активное полномочие инициатора перед отправкой и останавливается при отзыве; уже доставленные сообщения вернуть нельзя. Для длительных задач определяем безопасную границу отмены явно.

При переключении сохранённого аккаунта права заново вычисляются для нового User. При impersonation административная оболочка выключается; полномочия исходного администратора не переносятся на изображаемого пользователя. Выход, отключение аккаунта и смена чувствительных auth-данных должны закрывать соответствующие сессии по общей политике сайта.

## 7. Чувствительные сведения и журнал

Контактные поля включаются только по разрешению, включая результаты поиска, HTML attrs, JSON и выгрузку. TOTP-секреты, пароли/hash, токены, полный QR/PIN-секрет, cookies и ключи сервисов не выводятся и не записываются в аудит. Карту и QR проектируем отдельно с учётом существующего публичного сценария проверки членства: нельзя случайно сломать его, но путь к закрытому файлу не должен обходить policy.

Для договоров/документов: ресурс связан с объектом, storage ACL приватный, выдача через авторизованный endpoint или короткую подписанную ссылку. Проверка только маршрута `/protected/` бесполезна, если тот же файл публичен через CDN. При внедрении нужно доказать недоступность прямого storage URL, включая старые копии. Контракт не получает публичный ACL от загрузки логотипа.

Административные HTML/HTMX/JSON/download: `Cache-Control: private, no-store` для чувствительных ответов; service worker не кэширует панель и пользовательские данные. Приватные черновики не сохраняются в browser localStorage. CSP, CSRF и сессионные ограничения общего сайта применяются к `/manage/`; исключение текущего `/admin/` не переносим автоматически.

Событие аудита хранит actor, target, scope, action, timestamp UTC, безопасный before/after, reason, request-id, исходную оболочку (`workspace`, `django_admin`, `telegram`, `job`) и outcome. При impersonation actor и effective-user различаются. Просмотр закрытого документа и экспорт тоже журналируются. Отказ в опасной операции имеет минимальный security-event без копии присланных секретов.

Разрешённое редактирование → изменение данных и событие аудита в одной транзакции. Если аудит не записался, чувствительная операция не считается успешной. Уведомление после commit; outbox обеспечивает повторение и уникальный ключ. В панель не попадает обычный сырой application log с токенами и traceback.

История предназначена для accountability, но не гарантирует юридическую неизменность: администратор самой БД технически может менять записи. Для усиленной гарантии позже — отдельное append-only хранилище/экспорт с ограниченной записью. Срок хранения событий, IP и выгрузок задаётся отдельно после согласования политики данных; проект не устанавливает произвольный вечный срок.

## 8. Impersonation и техническая админка

Первый рабочий выпуск не включает вход от имени пользователя в меню персонала. Существующий маршрут должен быть ограничен техническим superuser либо специально подтверждённым исключительным правом до выдачи новых рабочих назначений.

Если сценарий поддержки всё же внедряется: причина обязательна, свежая проверка личности, сессия не дольше заданного короткого срока, яркий постоянный баннер с оригинальным actor, кнопка «Вернуться в управление», запрет на impersonation сотрудников/владельцев и на просмотр auth-секретов. Действия с правами, отправка широких сообщений и финансовые изменения запрещены в этой сессии. Возврат проверяет, что исходный actor всё ещё активен и имеет право; ID в session не считается достаточным доказательством.

Обычные сотрудники после переноса не получают доступ к Django Admin даже через прямой `/admin/`. Все оставшиеся staff-аккаунты инвентаризируются; права и групповые/индивидуальные grants не копируются автоматически. Технический UserAdmin, его custom endpoints и прямые permissions также проверяются: обход через старую оболочку не должен позволить менять `is_superuser`, группы или чужой доступ.

Telegram staff-команды, uploads редактора, dev-analytics, exports, уведомления и любые фоновые jobs включаются в инвентаризацию обходов. Нельзя закрыть только новый UI и оставить старый привилегированный путь с `is_staff` у той же аудитории.

## 9. Архитектура реализации

Предлагаемое приложение `administration`: urls, views, forms, policies, selectors, access-services, модели назначений/аудита и свои шаблоны. Предметные сервисы остаются возле соответствующего домена: `users/services/account_requests.py`, существующий `card_service.py`, `blog/services/moderation.py` и сервис событий.

Путь операции: view → форма с разрешёнными полями → policy → предметный сервис → транзакция данных/аудита → outbox. Общие сервисы используются новой панелью и старой технической оболочкой. Проверки не дублируются в каждой кнопке. Notification preference определяет канал, а policy — допустимого получателя.

Чтение: scoped selectors возвращают queryset/проекцию для списка, поиска, счётчиков и экспорта. Одна функция `allowed_objects(user, capability)` и отдельный `can(user, capability, object)` должны согласованно применять назначения. Коды и зависимости реестра проверяются тестом; неизвестный код запрещён.

Write-services принимают actor, target, expected-version, reason, idempotency-key; не принимают произвольный словарь полей модели. Для заявок, назначения ролей и замены карты используют `transaction.atomic` и блокировку целевых строк. Для форм нужен version-counter или иной надёжный механизм optimistic locking, добавляемый миграцией. `select_for_update` должен проверяться на реальном PostgreSQL: SQLite не доказывает корректность конкурентных операций.

Времена хранятся timezone-aware; для истечения назначения используется время сервера. Ограничение роли не ждёт планировщика. История отображается в текущем timezone сайта с понятным указанием зоны для событий.

## 10. Производительность панели

Нет загрузки всей базы пользователей, всех likes/comments или всего аудита на первый экран. Пагинация серверная, scope применяется до count/aggregate, связанные объекты `select_related`; тяжёлые счётчики получают независимые подзапросы/агрегаты без умножения joins.

Списки и поиск имеют deterministic ordering (время + PK). Поиск с debounce около 300 ms, отменой предыдущего запроса и небольшим лимитом. Главный overview читает только доступные очереди. Сроки кеширования статистики не кешируют права; никакой общий cache-key для scoped содержимого разных сотрудников.

Экспорт больших наборов — job с пределом размера и сроком готового файла, scope и columns снимком заказа плюс повторной проверкой разрешения при исполнении/скачивании. Малый экспорт может быть stream, но не обходить object-policy. CSV защищён от формул из пользовательского ввода.

Новые индексы выбираются по реальным explain/query-plan: assignments `(user, state, valid_until)`, audit `(scope, created_at, id)`, очереди `(status, created_at, id)` — кандидаты, а не слепой список обязательных индексов. Используем существующую систему статических файлов и CSRF/HTMX, не добавляем библиотеку таблиц ради базовой очереди.

Предварительные цели для проверки на staging: первая полезная административная страница до 2 секунд на согласованном мобильном профиле; фильтр/поиск до 500 ms p95 серверного времени при репрезентативном объёме. Это целевые показатели, не измеренный результат этого проекта. Бюджет SQL фиксируется после baseline и проверяется без привязки к случайной middleware-нагрузке.

## 11. План внедрения с условиями перехода

### Этап 0. Инвентаризация и прототип

Проверить реальные группы/индивидуальные права/сотрудников, CDN ACL и все входы (`/admin/`, staff tools, Telegram). Для пяти ключевых сценариев из UI-проекта собрать responsive-прототип на существующих компонентах. Проверить с сотрудниками названия и последовательность. Таблица «текущая операция → новый сервис → capability → область → старый путь» должна покрыть все действия, а не только основные списки.

### Этап 1. Безопасная основа

Добавить приложение, назначения/версии/аудит, registry, policies, scoped selectors, owner bootstrap, оболочку `/manage/`, read-only «Обзор» и «Команда». Создать назначение только разработчику; не импортировать всех staff автоматически. Реализовать выдачу/отзыв, приём приглашения и expiry. Проверить все попытки self-elevation, stale tabs и обходов.

### Этап 2. Первый полноценный рабочий срез

Модерация публикаций и обычные заявки: общие сервисы, причины, конкуренция, уведомления и история. Это первый выпуск для неподготовленных сотрудников. После приёмки отключить их старые административные permissions, проверить невозможность обхода. Сотрудник должен решить задачу от входа до уведомления только в новом интерфейсе.

### Этап 3. Участники и карты

Перенести профиль, членство, карты и приглашения участников. Отдельно протестировать новый QR, потерянную карту, отмену и приватные поля. Не переносить секреты UserAdmin. Ввести восстановление после ошибки файлового storage: успешная запись статуса и создание QR должны иметь определённое поведение, чтобы не выдавать пустую карту.

### Этап 4. Мероприятия, организации, визиты и встречи

Внедрить объектные области, защищённые документы, scoped аналитики/exports, всю мобильную работу. ClientNote оставляется в существующей предметной области, пока отдельная политика не утверждена. Проверить прямые ID чужой организации/события и фоновые процессы.

### Этап 5. Контент и сообщения

Существующие маркетинговые модели, переводы, галерея, порядок, предпросмотр и уведомления. Поддерживаемые settings появляются только вместе с реальными полями. Отдельно создать состояния draft/publish, где их нет, либо честно обозначить немедленное сохранение на сайт.

### Этап 6. Закрытие переноса

Сравнить inventory со всеми реально выполняемыми задачами. Убрать обычный Django Admin из рабочего меню и закрыть вход операторам. Оставить проверенный аварийный доступ разработчика. Провести короткое обучение на задачах и обновить инструкции. Делегирование администратора доступа и расширенные шаблоны добавляются после стабильного первого выпуска.

Функциональные переключатели разделов нужны для постепенного включения. Rollback UI не откатывает назначения и аудит и не возвращает широкие `is_staff` операторам автоматически. При отключении нового раздела доступна read-only информация и помощь разработчика; технический fallback — только доверенным лицам. Миграции БД обратимы по плану и не удаляют рабочие данные ради отката интерфейса.

## 12. Приёмка прав и сквозных сценариев

| Проверка | Ожидаемый результат |
|---|---|
| Обычный участник, партнёр, президент без назначения | Нет workspace-доступа независимо от бизнес-статуса |
| Одна активная роль | Только её разделы, разрешённые действия и поля |
| Несколько ролей с разными областями | Действия роли A не получают область роли B |
| Прямой чужой ID в HTML/HTMX/JSON/preview/download/export | Нет данных и эффекта, включая count и autocomplete |
| Подмена полей `is_staff`, `is_superuser`, groups, actor, recipient IDs | Не приняты; попытка чувствительного обхода журналируется |
| Отзыв в соседней вкладке перед POST | Действие отклонено без изменения данных |
| Истечение срока в момент операции | Серверная проверка не допускает операцию после срока |
| Приглашение принято повторно/другим адресом/после отзыва отправителя | Назначение не создаётся |
| Два сотрудника одновременно одобряют одну заявку | Один итог, один набор связанных объектов, нет двойного уведомления |
| Два запроса отзыва последнего владельца | Не остаётся ноль владельцев |
| Два нажатия отправки/выдачи карты | Одно логическое действие по ключу идемпотентности |
| Старый Django/Telegram/staff путь | Не расширяет workspace-полномочия оператора |
| Смена сохранённого аккаунта / impersonation | Старые полномочия не наследуются |
| Отсутствующее sensitive-field право | Поля отсутствуют и в response-body, не только скрыты CSS |
| Прямой CDN URL закрытого документа | Недоступен без отдельной краткосрочной авторизации |
| Сбой уведомления после commit | Данные и аудит сохранены; повторяется только доставка |
| Сбой сохранения аудита | Чувствительная бизнес-операция не завершена частично |
| CSV с пользовательским текстом, начинающимся как формула | Не запускает формулы при открытии выгрузки |
| Телефон / ПК | Один и тот же сценарий, все поля и решения доступны |

Unit/policy tests покрывают матрицу; request tests — routes/partials/downloads; PostgreSQL transaction tests — конкуренцию; browser tests — пять рабочих сценариев с несколькими ролями. Проверяется восстановление данных, аудит и outbox при сбоях, а не только счастливый путь.

## 13. Что нужно решить перед реализацией, без остановки проектирования

Предлагаемые значения по умолчанию: владелец — разработчик, рабочая панель `/manage/`, выдача прав в первом выпуске только владельцем, scope `global/partner/event`, обычные сотрудники без Django Admin, impersonation исключён из первого рабочего UI.

Перед разработкой уточняются реальные имена ответственных, нужны ли одному событию несколько координаторов, должен ли редактор согласовывать публикацию с другим человеком, сроки хранения аудита/выгрузок, метод усиленного подтверждения личности и политика приватных документов. Эти вопросы не меняют основной интерфейс, но определяют настройки ролей и техническую приёмку. Уровень доступа не выбирается автоматически из должности человека.
