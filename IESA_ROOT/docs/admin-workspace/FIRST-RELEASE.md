# Уточнения проекта и первый рабочий выпуск

14 октября 2026. Этот документ уточняет исходный проект; при разночтениях для первого выпуска используем решения ниже.

## Главное улучшение

Первый рабочий выпуск — небольшой законченный набор задач. Сотруднику не показываем сразу одиннадцать разделов и десятки разрешений. Модератор получает «Мои задачи» и «Сообщество». Владелец — дополнительно «Команда и доступ». Обработка заявок подключается следующим рабочим срезом на той же основе. Остальные разделы из большого проекта — карта развития, а не обещание реализовать всё до первого запуска.

Создан [интерактивный прототип](prototype/index.html): обзор, очередь с поиском/фильтром, проверка материала, возврат с причиной, выдача и отзыв назначения. Переключатель «Посмотреть как» относится только к демонстрации и не появится в рабочей панели. Используются токены и логотип IESA. Данные вымышленные; ни аккаунты, ни реальные права не меняются. Модель доступа проверяется только отображением в прототипе; настоящая защита должна работать на сервере.

## 1. Минимальный состав

| Сценарий | Завершённый результат | Обязательные зависимости |
|---|---|---|
| Вход сотрудника | Видит только свою очередь и рабочие действия | Назначения, политика доступа, общая авторизация |
| Проверка публикации | Решение, понятный итог, обновлённая очередь и уведомление автору | Предметный сервис, причина, аудит, доставка после commit |
| Возврат автору | Автор видит причину, исправляет и повторно отправляет | Состояние доработки и сценарий повторной отправки |
| Добавление сотрудника | Подтверждены человек, роль, область и срок | Владелец, проверка email, re-auth, аудит |
| Отзыв доступа | Следующий запрос не выполняет действие | Проверка назначения на сервере; аккаунт участника сохраняется |
| Ошибки и конфликты | Сотрудник понимает, что сохранено и что нужно сделать | Версии, идемпотентность, явные ошибки вместо ложного успеха |

Без этих зависимостей красивые страницы не считаются готовой админкой.

## 2. Выдача доступа без перегруженной матрицы

Первый выпуск: владелец назначает готовый шаблон и его область. Редактирование отдельных возможностей спрятано в расширенную настройку владельца и не требуется для обычного назначения. Делегирующего администратора доступа пока нет.

Три шага: **Человек → Работа → Проверка**. В проверке отдельно написаны «Сможет» и «Не получит», конкретная организация/событие и дата окончания. Истёкший срок нельзя выбрать. Если такое же назначение уже существует, показываем его и предлагаем продление/изменение вместо создания дубля. С несколькими разными областями создаём отдельные назначения, не объединяем все действия и объекты.

Проверять личность нужно для выдачи/расширения прав, замены идентификатора карты, массовой рассылки и экспорта чувствительных данных. Не требуем дополнительный пароль для каждого обычного чтения или модерации. Отзыв доступа имеет объект, последствия и обязательную причину; повторный вход запрашивается по общей политике свежести сессии, а не механически перед каждым кликом.

Права на страховые обращения, закрытые документы, общие персональные выгрузки и приватные заметки **не входят автоматически** в шаблоны «Работа с участниками» или «Операционный администратор». Они требуют явного отдельного назначения. Это уточняет общие описания ролей в исходной таблице.

## 3. «Вернуть автору» — реальная доработка

В текущем Post есть `draft`, `pending`, `published`, `rejected`. Нельзя просто переименовать `rejected` в «Вернуть автору», если автору не предоставлен путь исправления и повторной отправки.

Предлагаем добавить `changes_requested` и хранить каждое решение в предметной истории модерации: исполнитель, состояние до/после, версия материала, публичная причина, время. `rejected` остаётся отдельным финальным отказом и не является обычной кнопкой доработки.

Разрешённые переходы:

| Откуда | Действие | Куда | Кто |
|---|---|---|---|
| `draft` | Отправить на проверку | `pending` | Автор |
| `pending` | Опубликовать | `published` | Модератор с правом публикации |
| `pending` | Вернуть с обязательной причиной | `changes_requested` | Модератор |
| `changes_requested` | Исправить и повторно отправить | `pending` | Автор |
| `published` | Снять с публикации с причиной | `draft` | Отдельное право |

Редактирование ожидающего материала автором создаёт новую версию. Открытый у модератора старый материал нельзя опубликовать без обновления. Для опубликованного текста отдельная будущая версия предпочтительнее мгновенной замены; до внедрения версий ограничения такого редактирования явно описываются и проверяются.

Возврат не отправляет внутреннюю заметку администрации. В прототипе показан только комментарий автору. Повторная отправка не создаёт новую копию Post и не уничтожает историю прежних решений. Backend-переходы, миграция и авторский экран пока не реализованы.

## 4. Мобильная работа

В проверке публикации нижняя навигация заменяется строкой решения: «Опубликовать / Вернуть автору». Сам комментарий расположен в форме, не в узком подтверждении. Пустая причина вызывает ошибку возле поля и перенос фокуса. На сохранённом решении нижняя навигация возвращается.

Длинные назначения оформляются полноценной страницей. Нижние листы используются только для короткого выбора и фильтров. Все сведения доступны без горизонтального скролла на 360 px. У меню две явные точки входа: верхняя кнопка и нижние «Разделы». У Escape и Back должно быть понятное поведение.

Если клавиатура перекрывает закреплённое действие, UI возвращает его в обычный поток либо адаптирует по visual viewport. Проверка клавиатуры на реальном iOS/Android обязательна; изменение ширины браузера не заменяет её.

## 5. Когда спрашиваем подтверждение

| Действие | Механика |
|---|---|
| Прочитать, фильтровать, открыть объект | Без подтверждения |
| Опубликовать один прочитанный материал | Явная кнопка с понятным следствием и итогом; без второго пустого «Вы уверены?» |
| Вернуть материал | Обязательная причина и явная отправка автору |
| Отозвать назначение | Имя, последствия, причина; подтверждение в диалоге |
| Выдать/расширить доступ | Полное резюме и свежая проверка личности |
| Заменить карту, массово отправить, выгрузить чувствительные данные | Последствия, объём и усиленное подтверждение |

Отмена — только когда сервер умеет безопасно отменять конкретную операцию. Универсальный toast «Отменить» для публикации, прав и рассылок не обещаем. Историю вместо реального rollback не выдаём за восстановление.

## 6. Проверка с сотрудниками

Дать модератору пять задач без пояснения устройства интерфейса: найти публикацию; вернуть её с конкретным замечанием; найти возвращённый материал; понять, увидит ли автор внутренние сведения; определить, где завершилось сохранение.

Владельцу: выдать менеджеру одну организацию до определённой даты, объяснить итог своими словами, найти существующее назначение и отозвать его, убедившись, что участник не удалён. Фиксируем места, где потребовалась подсказка, ошибочные клики и непонятые слова. Предварительный критерий: ни одной случайной выдачи глобальной области, каждый участник проверки понимает последствия своей операции. Это план проверки, а не уже проведённое исследование с людьми.

## 7. Ограничения демонстрации

Прототип хранит изменения только в памяти вкладки; обновление страницы возвращает исходные примеры. Поиск и фильтры действуют на эти примеры. Реальная авторизация, MFA, проверка срока, серверная область, журнал БД, почта/Telegram и авторская повторная отправка отсутствуют.
