# Внутренняя панель администрации IESA

Дата: 13 октября 2026. Статус: подробный проект для обсуждения и последующей реализации. Новая рабочая админка в этом изменении не реализуется.

**Цель:** сотрудник администрации решает свою задачу внутри знакомого сайта IESA, без необходимости изучать Django Admin, модели, служебные флаги и устройство базы данных. Разработчик выдаёт людям ограниченный доступ через понятный раздел «Команда и доступ».

Основное решение: `/manage/` — рабочая панель на общей авторизации и дизайн-системе сайта. Django Admin остаётся резервным техническим инструментом разработчика. Это новый интерфейс к существующим данным и общим бизнес-сервисам, а не вторая база или копия Django Admin.

## Как будет выглядеть работа

| Человек | Первый экран | Основное действие |
|---|---|---|
| Модератор | «Публикации на проверке» | Прочитать, опубликовать или вернуть с объяснением |
| Сотрудник по участникам | «Заявки и участники» | Рассмотреть заявку, изменить членство, выдать карту |
| Координатор мероприятий | «Мероприятия» | Создать событие, проверить регистрации |
| Редактор сайта | «Контент сайта» | Обновить блок, проверить перевод и предварительный просмотр |
| Менеджер партнёров | «Партнёры» | Работать с назначенными организациями и визитами |
| Разработчик / владелец панели | «Обзор» и «Команда и доступ» | Пригласить сотрудника, назначить роль и область работы, отозвать доступ |

Роль — шаблон рабочих возможностей. Область — конкретные партнёры или мероприятия, с которыми человек может работать. Статусы «партнёр», «президент», «участник» сами по себе не дают административных прав.

## Ключевые договорённости проекта

1. На телефоне доступны те же операции и поля, что на ПК; меняется компоновка.
2. Неподготовленный сотрудник видит названия задач: «Вернуть автору», «Выдать карту», «Назначить доступ». Имена моделей и флаги Django ему не показываются.
3. Выдача прав не включает `is_staff` или `is_superuser` автоматически. Доступ к технической админке — отдельный процесс разработчика.
4. Право просматривать данные, право изменять их и право выгружать их разделены. Документы, личные заметки и вход от имени пользователя требуют отдельных ограничений.
5. Одинаковые проверки действуют для страницы, HTMX, поиска, вложений, экспорта и старых административных маршрутов.
6. Перед опасной операцией видны объект, последствия и требуемая причина. После неё — понятный результат и запись в истории.
7. Перенос идёт по разделам. Рабочие процессы проверяются до отключения старого способа управления.

## Основание проекта

Проект составлен по коду Django-сайта в `IESA_ROOT/`, текущим административным действиям и уже проверенным интерфейсам IESA. Админка Predvestnik и React-трек `frontend/` в него не входят. Названия ролей, маршруты `/manage/` и новые структуры доступа ниже — предлагаемые решения; их пока нет в рабочем сайте.

Визуальные примеры взяты из [проверки мобильной версии](../audits/2026-10-13-mobile-parity/REPORT.md). Эти снимки показывают существующие паттерны, а не макеты новой панели. В UI-документе для каждого решения указан исходный компонент сайта.
