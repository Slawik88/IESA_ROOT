# Глубокий аудит и исправления IESA — 22 октября 2026

## Результат и границы

Проведён разбор Django-сайта, исправлены обнаруженные ошибки целостности данных,
безопасности, календаря, Telegram и сборки. Добавлены воспроизводимые проверки,
регрессионные тесты и отдельный workflow сайта. Изменения подготовлены локально;
коммит, публикация и применение миграций к рабочим базам не выполнялись.

Работа велась поверх большого количества уже существовавших изменений.
Предыдущие исправления не приписываются этому аудиту. Код `frontend/` и
`predvestnik_v2/` не менялся. Общий `requirements.txt` теперь включает зависимости
сайта; версии восьми зависимостей секции бота сохранены. Общие библиотеки при
установке из корневого файла обновятся также у бота: разрешение зависимостей
проверено, сам бот в этом проходе не тестировался.

Инвентаризация: **295 Python-файлов, 93 HTML-шаблона, 18 JS- и 27 CSS-файлов**.
Счётчики включают миграции, тесты и поставляемые библиотеки; это не количество
построчно проверенных файлов. Исключены рабочие медиа, окружения, логи и отчёты.
Полная карта — [inventory.json](inventory.json).

| Участок | Устройство и последствия |

Крупнейшие точки концентрации кода: `pages.css` — 3406 строк, `homepage.css` —

## Оставшиеся задачи по приоритету

1. **P1 — надёжная доставка событий.** Вынести daemon threads и внешние вызовы
   из signal handlers в очередь/outbox с повторными попытками и идемпотентностью.
   `on_commit` исправляет границу транзакции, но процесс может завершиться до
   отправки. Admin notifications из существующих signals ещё требуют такого же
   системного разбора.
2. **P1 — проверить PostgreSQL CI до публикации.** SQLite не доказывает корректность
   SELECT FOR UPDATE. Новый workflow должен реально пройти; миграцию 0037 нужно
   применить в проверочном окружении и затем штатным deployment-процессом.
3. **P1 — определить единый источник партнёрского доступа.** Сейчас роль задаётся
   флагом, группой и существованием Partner; `is_partner()` восстанавливает флаг
   по профилю. Удаление группы само по себе не означает отзыв доступа. Порядок
   отзыва необходимо закрепить как бизнес-правило и покрыть отдельным сценарием.
4. **P1 — классифицировать публичные данные.** Поиск показывает email, а публичная
   карточка партнёра содержит договор. Это существующее поведение и не объявляется
   автоматически утечкой. Нужно определить, какие данные действительно должны
   быть публичными, затем менять представления и ACL уже загруженных объектов.
5. **P2 — фоновые напоминания.** Текущая дедупликация по тексту уведомления убирает
   повтор одного scheduler run, но не заменяет отдельный ключ события и durable
   delivery status при конкурентных запусках и изменении языка/текста.
6. **P2 — объединить теневой шаблон поиска.**
   `templates/blog/htmx/post_search_results.html` перекрывает одноимённый файл
   в `blog/templates/`. Правки второго файла не меняют фактический глобальный поиск.
   Оба содержат уже существовавшую работу, поэтому механическое удаление здесь
   не выполнялось. Нужна одна каноническая версия после проверки отображения.
7. **P2 — разделить users/models.py и большие шаблоны.** Сначала выделить модели
   по предметным областям с сохранением app_label/table names и совместимых
   импортов; затем вынести JS профиля/календаря из HTML в отдельные модули.
   Массовое перемещение без проверки миграций создаст лишний риск.
8. **P2 — упорядочить CSS по ответственности.** Зафиксировать порядок слоёв,
   убрать перекрывающиеся legacy overrides и дубли после визуальных проверок
   основных ролей/ширин. Нужна карта используемых правил и эталонные страницы.
9. **P2 — уменьшить CSP unsafe-inline/unsafe-eval.** Для этого требуются вынос
   встроенных обработчиков, проверка HTMX и переход на подходящую nonce/hash-схему;
   удалять разрешения до этой работы нельзя.
10. **P2 — много процессов и rate-limit.** Лимиты сейчас используют per-process
    LocMemCache. В нескольких workers суммарный предел больше одного настроенного
    лимита. Решение должно учитывать доступный Redis и требуемую защиту.
11. **P2 — passwordless-аккаунты.** Деактивация требует локальный пароль, которого
    может не быть после социального входа. Нужен согласованный способ повторного
    подтверждения личности перед этой операцией.
12. **P2 — deployment-конфигурации разных треков.** В старом app.yaml worker ещё
    ссылается на `PredvestnikBot`; workflow frontend тоже содержит старый путь.
    Эти участки другого приложения не менялись. Не использовать весь старый
    deployment manifest как подтверждённо актуальную конфигурацию всех сервисов.
13. **P3 — воспроизводимость зависимостей.** Прямые версии закреплены; транзитивные
    пока разрешаются динамически. Следующий шаг — lock/constraints с hashes и
