# Аудит блока регистрации и аккаунта (IESA) — 2026-10-07

Область: регистрация, вход, сброс пароля, подтверждение e-mail, первый вход (тур), страницы `/auth/*`.
Predvestnik не затрагивался.

## 1. Почему не регистрировались с телефона

Корень был один, но проявлялся по-разному. **Проверено воспроизведением в мобильной эмуляции (375×812).**

| # | Причина | Что видел пользователь |
|---|---|---|
| 1 | JS на странице принимал «спецсимвол» из набора `!@#$%^&*()-_=+[]{};:'",.<>?/\|`~`, а сервер (`SpecialCharacterValidator`) — только `!@#$%^&*(),.?":{}\|<>`. Пароль из менеджера паролей Safari/iOS (`Hyfwiz-5jyqge-tuvzed`) содержит только дефис → браузер пускал дальше, сервер отклонял. | Форма перерисовывалась с пустыми паролями, ошибка отображалась под полем «Подтверждение» вместо «Пароль». |
| 2 | Пароль Chrome/Android (буквы+цифры, без символа) вообще не проходил клиентскую проверку «4 из 4 критериев». Кнопка «Review» просто тускнела. | «Кнопка не работает». |
| 3 | Кнопка «Create Account» была `disabled`, пока JS не получал `input`-события. Автозаполнение телефона не всегда их шлёт. | Кнопка навсегда серая. |
| 4 | Телефон делает первую букву имени заглавной, вход был чувствителен к регистру. | «Неверный логин/пароль» после регистрации. |
| 5 | Поля ввода 15 px → iOS Safari приближает страницу при фокусе; `autofocus` открывал клавиатуру, закрывая форму; нет `autocapitalize/autocorrect`. | Страница «прыгает», имя искажается. |
| 6 | Лимит регистрации 10 POST/час на IP. На телефонах и на мероприятиях (общий Wi-Fi / CGNAT оператора) один IP у десятков людей. Каждая неудачная попытка тоже считалась. При превышении — безликая страница «403 Access restricted». | «403» после нескольких попыток. |
| 7 | После успешной регистрации человека отправляли на форму входа и просили войти заново. | Бросают на этом шаге. |
| 8 | Service worker кэшировал `/auth/register/` (network-first): при обрыве сети на телефоне отдавалась старая копия формы. | Редкие «CSRF verification failed». |

## 2. Что исправлено в этом изменении

Код:
- `settings.py` — убраны `UppercaseValidator`/`SpecialCharacterValidator` (остались: длина ≥ 8, «не слишком похож на логин», «не из популярных», «не только цифры»). Классы остались в `users/validators.py`, вернуть правило = одна строка в `AUTH_PASSWORD_VALIDATORS`.
- `users/auth_backends.py` (новый) + `AUTHENTICATION_BACKENDS` — вход без учёта регистра имени и **по e-mail**. Точное совпадение имени приоритетнее; при неоднозначности никто не входит. `ModelBackend` оставлен в списке намеренно: на него ссылаются уже выданные сессии и `login(..., backend=...)` в инвайтах/impersonate — без него все пользователи были бы разлогинены деплоем.
- `users/views/auth.py` — автоматический вход после регистрации → `/auth/profile/`; залогиненных со страниц входа/регистрации перенаправляет в профиль; понятное сообщение вместо 403 при превышении лимита.
- `users/ratelimit_utils.py` — регистрация 10 → 30/ч с IP, вход 20 → 40/ч (учитывают толпу за одним IP).
- Сброс пароля **без админа**: `/auth/password-reset/…` (4 страницы + письмо HTML/txt), ссылка живёт 2 часа, ответ одинаковый для существующих и несуществующих e-mail, ограничение 10 запросов/час с IP. Ссылка «Forgot your password?» на странице входа.
- `register.html` — переписан: единственное обязательное правило пароля — длина ≥ 8, остальное — подсказка; проверка читает реальные значения полей (а не события); кнопка отправки больше не блокируется, а при ошибке объясняет, что исправить; ошибки сервера по паролю показываются одним блоком на шаге пароля; форма открывается на шаге с ошибкой; защита от двойной отправки; поля 16 px, цели касания ≥ 44 px, `autocapitalize/autocorrect/inputmode`; контраст и размер текста увеличены (метки были 10 px моноширинным капсом при 0.25 прозрачности).
- `login.html` — те же правила читаемости/ввода, подпись «имя пользователя или e-mail», защита от двойного нажатия.
- Тур первого входа (`tour.js`, `tour.css`, `_tour.html`) — см. раздел 3.
- `service-worker.js` — страницы `/auth/register/`, `/auth/password-reset/`, `/auth/email/` не кэшируются; версия кэша `iesa-v3 → iesa-v4` (у всех сотрутся старые копии).
- `forms_verification.py` — имя в инвайт-регистрации проверяется без учёта регистра.
- Переводы (uk/de/fr) для всех новых строк, `.mo` пересобраны.
- Тесты: `users/tests_auth_flows.py` (24 теста) + обновлён один тест в `tests_email_verification.py` (теперь после регистрации редирект в профиль).

## 3. Гайд (тур) — что было плохо и что сделано

Было: тёмный слой 78 % **плюс** затемнение подсветки 72 % → подсвеченный элемент оказывался под почти чёрной вуалью (на скриншоте страница не читается); текст 14 px с 72 % прозрачностью; на каждом шаге кнопка «Got it» (непонятно, что значит), нет «Назад», крестик 28 px; на телефоне карточка внизу закрывала именно тот элемент, о котором рассказывает; счётчик «3 OF 8» мелким красным моноширинным шрифтом.

Стало: затемняет только вырез вокруг элемента (60 %), подсвеченный элемент яркий; текст 15–16 px, контраст 92 %; кнопки «Назад / Далее», явная ссылка «Пропустить», крестик 40 px; на телефоне элемент прокручивается в верхнюю часть экрана, карточка внизу его не закрывает.

## 4. Что осталось — слабые места и варианты (без реализации, нужно решение)

### A. Вход через Google — **нужно решение**
Сейчас нет. Варианты:
1. **Google Identity Services + проверка ID-токена** (рекомендую). Кнопка «Войти через Google» / One Tap, сервер проверяет токен библиотекой `google-auth` (≈100 строк, один endpoint `/auth/google/`, без новых таблиц). Не нужен client secret, отлично работает на телефонах. Привязка к существующему аккаунту по e-mail, который Google подтвердил (`email_verified`) — и такой e-mail сразу считаем подтверждённым. Потребует правки CSP (`accounts.google.com/gsi/*` в script/frame/connect/style-src).
2. **django-allauth** (провайдер Google). Больше «из коробки» (привязка аккаунтов, Apple/Facebook позже), но тянет `django.contrib.sites`, свои таблицы и шаблоны, нужно подгонять под текущую кастомную модель и страницы. Разумно, если планируется 2+ провайдера.
3. Ручной OAuth-редирект (authlib). Больше кода, чем вариант 1, без преимуществ.

Что нужно от вас: OAuth Client ID (Web) в Google Cloud, Authorized JavaScript origins `https://iesasport.ch` и `https://www.iesasport.ch`, экран согласия переведён в «In production», переменная `GOOGLE_OAUTH_CLIENT_ID` в DigitalOcean. Открытый вопрос: где брать согласие на членство — чекбокс рядом с кнопкой Google или шаг «Подтвердите членство» после первого входа (я бы второе).

### B. Нет страницы политики конфиденциальности / условий / imprint — **нужны тексты**
Чекбокс согласия ссылается на «privacy policy», но ведёт на страницу «How it works». Для швейцарской организации (nDSG) и ЕС-пользователей (GDPR) нужна настоящая страница. Могу сделать каркас `/privacy/`, `/terms/`, `/imprint/` и подключить ссылки в чекбоксе и футере; текст должен утвердить юрист/председатель.

### C. Подтверждение e-mail ничего не ограничивает
Баннер есть, но неподтверждённый e-mail не блокирует ни одну функцию. Теперь, когда есть сброс пароля, опечатка в e-mail при регистрации = потеря доступа. Варианты: (1) оставить, но на шаге «Review» показывать e-mail крупно с подсказкой проверить; (2) требовать подтверждение для чувствительных действий (смена e-mail/пароля, заявка партнёра); (3) жёстко блокировать посты/комментарии до подтверждения (риск потери новичков). Рекомендую 1 + 2.

### D. Защита от ботов
Только лимит по IP. Лимит хранится в `LocMemCache` отдельно в каждом процессе (5 воркеров → фактически ×5, обнуляется при каждом деплое). Варианты: (1) honeypot-поле + минимальное время заполнения — бесплатно, 1 час; (2) Cloudflare Turnstile (бесплатно, невидимый, удобнее reCAPTCHA на телефоне); (3) общий кэш (Redis/БД) — сейчас сознательно избегается из-за лимита соединений с БД. Рекомендую 1, затем 2 при реальном спаме.

### E. `/auth/check-username/` и `/auth/check-email/` без ограничений
Любой может перебирать имена и e-mail (раскрытие, существует ли аккаунт) и нагружать БД. Для живой проверки это неизбежная цена; варианты: щедрый лимит 600/час на IP (не мешает толпе на мероприятии) или проверять e-mail только при отправке формы. Рекомендую лимит.

### F. Service worker показывает старый профиль после выхода
`/auth/profile/` в стратегии stale-while-revalidate: на общем телефоне следующий человек на мгновение видит профиль предыдущего (имя, PIN-блок). Варианты: убрать профиль из SWR (проще всего), или чистить `DYNAMIC_CACHE` при выходе (сообщение `CLEAR_CACHE` уже поддерживается). Рекомендую убрать.

### G. Прочее (мелкое)
- Ссылки «Register» не передают `next`, поэтому после регистрации человек теряет контекст (событие, пост). Лёгкая правка — по запросу.
- Нет приветственного письма и подсказки «подключите Telegram» сразу после регистрации.
- Тур стартует одновременно с тостом и баннером «Confirm e-mail» — перегружено. Можно запускать тур через 1–2 секунды или после подтверждения e-mail.
- Профиль после регистрации «0 % complete» — можно спросить имя/фамилию одним необязательным шагом.
- `logout` через GET молча игнорируется (только POST) — корректно, но ссылка-выход, если где-то есть, ничего не делает.
- Тексты ошибок валидаторов профиля (`validators.py`) на русском, остальное на английском.

## 5. Деплой — важно

- Ветка `backup/no-deploy-…` опережает `master` на 134 коммита, **но код IESA в ней идентичен `master`** (разница — только Predvestnik). Поэтому изменения IESA нужно отправлять в `master` **отдельной веткой от `master`**, а не сливать эту backup-ветку целиком.
- Миграций нет. Новых зависимостей нет. Переменных окружения не требуется.
- `start.sh` при деплое сам запускает `sync_translations.py` и `compilemessages` — добавленные переводы переживут.
- После деплоя у пользователей один раз сменится кэш service worker (v4).

## 6. Продолжение: боты и спам, вход через соцсети, заглушка политики

### Откуда шёл почтовый спам (найдено в коде)
Анонимно или с новым аккаунтом сайт мог слать письма на **любые** адреса: (1) письмо подтверждения при регистрации — боты регистрируют списки чужих адресов; (2) письма сброса пароля (теперь есть) — можно «бомбить» адрес участника; (3) смена e-mail в профиле — письмо на новый адрес, а бот с аккаунтом мог менять адрес бесконечно. Дополнительно в DNS нет SPF и DMARC, поэтому любой может рассылать письма «от iesasport.ch».

### Защита (users/antispam.py) — слои независимы, боту нужно пройти все
1. **Ловушка-honeypot**: скрытое поле, которое заполняют только боты.
2. **Подписанный таймер формы**: POST без токена страницы, с подделанным или быстрее 3 секунд — отклоняется.
3. **Cloudflare Turnstile** (бесплатная, почти невидимая капча) на регистрации и сбросе пароля. Включается сама, когда в окружении появляются `TURNSTILE_SITE_KEY` и `TURNSTILE_SECRET_KEY`. Если Cloudflare недоступен — пропускает людей (не запирает сайт).
4. **Одноразовые e-mail** (mailinator, yopmail и др.) не принимаются.
5. **Лимиты в общей БД** (переживают деплой, общие для всех воркеров): письмо подтверждения — 3/час на адрес, 10/сутки на аккаунт, 300/час на весь сайт; сброс пароля — 3/час на адрес, 20/час на IP; регистрация — 60 попыток/час на IP.
6. Лимит 10 обращений/час с IP на форму «апелляция» (`/appeal/`, была открыта без ограничений).
7. Команда очистки уже накопленных ботов: `python manage.py prune_bot_accounts` (по умолчанию только показывает; `--delete` удаляет аккаунты без подтверждённого e-mail и без какой-либо активности старше 14 дней).

### Вход через соцсети (django-allauth)
Google, Microsoft, Facebook, Apple. Кнопка появляется **только** для провайдера, у которого заданы ключи в окружении; пока ключей нет — на сайте ничего не меняется. Подключён только OAuth-поток (`/accounts/<провайдер>/login/`); собственные страницы входа/регистрации allauth **не** подключены, чтобы через них нельзя было обойти антибот. Правила:
- e-mail, подтверждённый провайдером и совпавший с существующим участником → вход в его аккаунт и привязка провайдера (e-mail помечается подтверждённым);
- e-mail совпал, но провайдер его не подтверждает → ничего не привязывается, вход отклонён с понятным сообщением (иначе возможен захват чужого аккаунта);
- новый участник → активное членство, уникальное имя пользователя, как при обычной регистрации; если провайдер не дал e-mail — одна форма «Ещё один шаг».

Переменные окружения (DigitalOcean → App → Settings → Environment Variables), адреса возврата (Redirect URI) для настройки у провайдера:

| Провайдер | Переменные | Redirect URI |
|---|---|---|
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | `https://iesasport.ch/accounts/google/login/callback/` |
| Microsoft | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` | `https://iesasport.ch/accounts/microsoft/login/callback/` |
| Facebook | `FACEBOOK_CLIENT_ID`, `FACEBOOK_CLIENT_SECRET` | `https://iesasport.ch/accounts/facebook/login/callback/` |
| Apple | `APPLE_CLIENT_ID` (Services ID), `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` (содержимое .p8, переводы строк как `\n`) | `https://iesasport.ch/accounts/apple/login/callback/` |

Заметки: Google и Microsoft бесплатны и настраиваются за 10 минут; Facebook требует приложение в Meta for Developers и **URL политики конфиденциальности** для публикации; Apple требует платный Apple Developer ($99/год). Apple и Facebook для публикации обычно просят настоящую политику — заглушка `/privacy/` для этого может не подойти.

### Политика конфиденциальности — заглушка
`/privacy/` честно сообщает, что политика готовится, регистрация и вход не блокируются, всех участников уведомим по e-mail и на сайте, когда она будет опубликована. Ссылка есть в футере, в чекбоксе согласия и под кнопками соцвхода. Когда будет готов настоящий текст — заменить `core/templates/core/privacy.html`.

### Переключение между аккаунтами
Меню профиля → «Add another account» → вход во второй аккаунт; после этого в меню появляется «переключиться» на первый и обратно, без ввода пароля. Хранится в подписанной HttpOnly-куке (`iesa_accounts`, до 5 аккаунтов, 30 дней). Безопасность: привязка снимается при смене пароля или деактивации аккаунта; выход и любой обычный вход (в т.ч. через соцсети) полностью очищают список, чтобы на общем устройстве следующий человек не получил чужие аккаунты; переключение — только POST с CSRF. Код: `users/account_switch.py`.

### Сканеры WordPress
Пути вида `//site/wp-includes/wlwmanifest.xml` (двойной слэш) обходили прежнюю защиту и отдавали полную 404 (~58 КБ). Теперь слэши схлопываются, а `wp-includes/wp-admin/wp-content/xmlrpc/wlwmanifest.xml` отдают пустой 404.

### DNS и почта (iesasport.ch, зона в DigitalOcean) — состояние на 2026-10-07
Почту сайта отправляет **CleverReach** (DKIM-запись `crsend._domainkey` есть), ящики — Google Workspace (DKIM `google._domainkey` есть). **Нет:** SPF и DMARC. Записи для добавления (хост → тип → значение):
- `@` → TXT → `v=spf1 include:_spf.google.com include:spf.crsend.com ~all`
- `_dmarc` → TXT → `v=DMARC1; p=quarantine; pct=25; rua=mailto:iesa@iesasport.ch; adkim=r; aspf=r` (через 2–3 недели без проблем поднять `pct` до 100)
Лишняя запись в зоне: CNAME `iesasport.ch.iesasport.ch → iesasport.ch` (ошибка при создании, безвредна, можно удалить). Записи `www` в зоне нет.
