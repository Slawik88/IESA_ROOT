## Найдено 6 расхождений, отсортировано по серьёзности — все закрыты

### 1. ✅ ИСПРАВЛЕНО — Аукцион: лимит количества в лоте — сайт режет то, что бот не режет

- **Где:** `FastAPI/static/app.04.js:705` — `const maxQ = Math.min(maxQty, 10);`
- **Бот:** `bot/handlers/auction.py:400` — `presets = [1, 5, 10, max_qty] if max_qty > 10 else ...`
  Бот сам предлагает кнопку с полным `max_qty`, если у игрока его больше 10 — **лимита нет вообще**.
- **Backend:** в `FastAPI/routers/auction.py` (`CreateLotRequest`) и `services/auction.py` тоже
  нет верхней границы `quantity` — только проверка `have < body.quantity`.
- **Эффект:** игрок с 50 шт. предмета через бота выставляет лот на все 50 одним лотом,
  через сайт — максимум 10, приходится делать 5 отдельных лотов (тратит `AUCTION_MAX_ACTIVE_LOTS`,
  которых всего 5 — **фактически сайт может заблокировать игрока от продажи остатка**).
- **Причина:** число «10» придумано на фронте без основания ни в одной из трёх точек истины.
- **Фикс:** убрать `Math.min(maxQty, 10)`, использовать `maxQty` как есть (как в боте).

### 2. ✅ ИСПРАВЛЕНО — Аукцион: минимальная ставка — три разных цифры в трёх местах

- **Backend, `core/constants.py:369`:** `AUCTION_MIN_BID: float = 1.0` — реальный технический пол.
- **Бот, `bot/handlers/auction.py:415`:** нижняя кнопка-пресет — `100` 🪙 (нет свободного ввода).
- **Сайт, `app.04.js:733,766`:** `if(!minBid||minBid<50){toast('Мин. ставка от 50 🪙'...)}` — хардкод `50`.
- **Эффект:** не баг «всё падает», но три канала (константа/бот/сайт) не согласованы между собой
  и ни один не тянет значение из общего места. Если DevConsole когда-нибудь решит поднять
  экономический пол (например, `AUCTION_MIN_BID = 200` из-за инфляции Моры), сайт и бот
  просто не узнают об этом — будут по-прежнему пускать ставки от 50/100.
- **Фикс:** ввести `AUCTION_MIN_BID_SUGGESTED` (или переиспользовать сам `AUCTION_MIN_BID`,
  подняв его до реалистичного значения) в `core/constants.py`, отдавать через
  `GET /auction/config` (или в существующий листинг), сайт и бот читают оттуда.

### 3. ✅ ИСПРАВЛЕНО — Прогресс-бар XP — своя копия `XP_PER_LEVEL`

- **Backend, `core/constants.py:7`:** `XP_PER_LEVEL: int = 3_000`.
- **Сайт, `app.02.js:16`:** `const xpInLvl = xp % 3000, xpPct = ...xpInLvl/3000...`
- **Эффект:** сейчас числа совпадают, баг не проявлен. Но `user_level` считается на бэкенде
  (`services/leveling.py`) и всегда приходит готовым в `d.chats[0].user_level` — сама *цифра*
  уровня расхождению не подвержена. Расходится только % заполнения шкалы: если когда-то
  `XP_PER_LEVEL` изменят (ребаланс), число уровня останется верным (оно с бэка), а полоса
  прогресса и подпись «X / 3 000 XP» будут врать молча, без ошибки в консоли.
- **Фикс:** отдавать `xp_per_level` в `/profile/me` (и `/profile/u/{id}`) рядом с `user_xp`,
  сайт использует его вместо литерала `3000`.

### 4. ✅ ИСПРАВЛЕНО — Бейджи эффектов предметов дублируют `description`, а не читают его

- **Где:** `app.04.js:936` — `study_notes` → хардкод `+50% XP · 4ч`.
  `app.04.js:933` — `star_dust` → хардкод `item_id.includes('_l')?5:1`.
- **Совпадает с:** `core/registry.py:56-60` (`study_notes.description` = «...+50% XP от сообщений
  на 4 часа») и `FastAPI/routers/inventory.py:119` (`dust_amounts = {"star_dust_s": 1, "star_dust_l": 5}`).
- **Важный нюанс:** `description` уже выводится в том же модальном окне строкой выше
  (`openItemModal`, `app.04.js:919`) — то есть бейдж ниже **дублирует то, что уже показано**,
  вторым, отдельно хардкоженным источником. Если механику предмета поменяют в `registry.py`
  (например, буст станет +75%/6ч), `description` обновится сам, а бейдж — нет: игрок увидит
  два противоречащих друг другу числа в одном окне.
- **Фикс:** либо убрать бейдж (описание уже всё говорит), либо завести в `ITEMS_REGISTRY`
  структурированные поля (`xp_boost_pct`, `xp_boost_hours`, `dust_amount`) и рендерить бейдж из них
  через API, а не угадывать по названию `item_id`.

### 5. ✅ ИСПРАВЛЕНО — Таблицы редкости (`common/rare/epic/legendary/mythic`) продублированы 4+ раз

- **Файлы:** `app.01.js` (`RC`), `app.02.js` (`_rarLabel`, `rarColors`), `app.04.js` (`RARITY_LABEL`
  с доп. `uncommon`), `app.06.js` (`_AUC_RARITY_COL`, `_AUC_RARITY_LBL`).
- **Эффект:** сегодня везде консистентно (проверено — тексты и порядок совпадают), но это 4
  независимых места правки при малейшем изменении (добавить редкость, переименовать «Эпический»
  → «Эпичный» и т.п.). Не баг сейчас, но ловушка на будущее — статус «найдено при аудите,
  не исправлено» осознанно, чтобы не трогать рабочий UI без повода.
- **Фикс (когда будет повод трогать этот код):** один общий модуль `RARITY_META` в начале
  `app.01.js` (там уже лежит `RC`), остальные файлы импортируют/используют его вместо
  собственных копий.

### 6. ✅ ИСПРАВЛЕНО — (низкий приоритет, dev-only) Текст «100 XP = 1 уровень» в DevConsole

- **Где:** `app.08.js:210` — статичная подсказка про формулу XP боевого пропуска.
- **Backend:** `core/constants.py:546` — `BATTLE_PASS_XP_PER_LEVEL: int = 100`.
- **Эффект:** видно только разработчику в служебной панели, меняется вместе с редким ребалансом
  БП. Риск минимальный, включено в список для полноты.

## Проверено и НЕ является нарушением (ложные срабатывания при grep)

- `app.02.js:709` (`step = reduce ? 90 : 440`) — таймер анимации прелоадера, случайное совпадение
  цифры `440` с ценой «редкой» косметики, к цене отношения не имеет.
- `app.04.js:145` (`d.multi_discount_pct||10`) — защитный дефолт на случай отсутствия поля в ответе
  API, основное значение всегда приходит с бэкенда.
- `CAT_RU` в `app.04.js:888` — чисто фронтовый словарь переводов категорий предметов
  (food/material/...), на бэке нет русских лейблов категорий вообще — это не дублирование
  источника правды, а обычная фронтовая локализация статичного enum.
- Гача-шансы (`app.04.js:167`), VIP-тарифы (`app.05.js:496`), клановый XP (`app.02.js:531`),
  цвет усталости питомца (`fatC`) — всё либо приходит из API, либо чисто визуальный UI-порог
  без «правильного» значения на бэкенде для сверки.
- Уровень игрока (число) — всегда с бэка (`d.chats[0].user_level`), клиент никогда не считает
  его сам из XP — только процент заполнения бара (см. находку №3).

## Как исправлено (2026-07-01)

1. **№1** — `app.04.js`: убран `Math.min(maxQty, 10)`, лимит количества в лоте теперь равен
   инвентарю игрока, как в боте.
2. **№2** — `core/constants.py` не менялся (не стали придумывать новое экономическое число без
   пользователя). Вместо этого технический пол `AUCTION_MIN_BID` теперь отдаётся с бэкенда:
   `GET /auction/lots` → поле `min_bid_floor`. Сайт (`app.04.js`, 4 места: `selectLotItem`,
   `submitLot`, `selectLotPet`, `submitPetLot`) читает `_aucMinBidFloor` вместо хардкода `50`.
   Бот не трогали — его кнопки-пресеты (100+) остаются дизайн-решением, они выше нового
   реального пола и никак не мешают.
3. **№3** — `core/constants.py.XP_PER_LEVEL` теперь отдаётся в `/profile/me` как `xp_per_level`.
   `app.02.js` читает `d.xp_per_level` вместо литерала `3000` — и в расчёте `xpPct`, и в подписи.
4. **№4** — `core/registry.py`: у `star_dust_s`/`star_dust_l` появилось поле `dup_count` (1/5);
   `FastAPI/routers/inventory.py.apply_dust()` теперь берёт число оттуда вместо своего отдельного
   словаря `dust_amounts` (устранена ВНУТРЕННЯЯ дупликация бэкенда, не только фронт-бэк).
   `/inventory/` отдаёт `dup_count` в ответе. `app.04.js`: бейдж `star_dust` использует `it.dup_count`;
   бейдж `study_notes` вообще убран — `description` (уже показан строкой выше) полностью покрывает
   эту информацию, дублирующий бейдж был чистой избыточностью.
5. **№5** — в `app.01.js` (грузится первым) добавлена таблица `RARITY_META` (цвет + русское
   название на редкость) и функции `rarLabel()`/`rarColor()`. `app.02.js._rarLabel` и
   `app.06.js._AUC_RARITY_LBL/_AUC_RARITY_COL` переведены на неё. **Побочная находка при
   унификации:** цвет `legendary` реально разошёлся — `#e8c45a` (app.02.js) vs `#e8b54d`
   (app.06.js) — то есть легендарная косметика в конструкторе профиля и легендарный лот на
   аукционе показывались чуть разными оттенками золота. Теперь везде `#e8c45a`.
   Таблицы множественного числа для фильтров (`RARITY_LABEL` в `app.04.js` — «Обычные», с эмодзи)
   намеренно не трогали: другая грамматическая форма для другого UI-контекста (заголовки секций/
   фильтры), объединение с единственным числом дало бы либо грамматически неверный текст, либо
   потребовало таскать оба варианта — не стоило риска для рабочего UI.
6. **№6** — `/admin/dev/bp/xp-actions` уже отдавал `xp_per_level` (не читался). `app.08.js`:
   статичный текст заменён на `<b id="dev-bpxp-perlevel">`, `app.09.js.loadBpXpActions()`
   проставляет туда реальное значение при загрузке.

Все правки проверены `node --check` (JS) и `python -c "import ..."` (Python-роутеры) —
синтаксис и импорты целые.
