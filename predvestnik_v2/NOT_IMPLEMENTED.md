## 1. Неотменяемые принципы работы (действуют на всех этапах)

## ЭТАП 1: База данных (SQL-миграции)

### 1.1 Глобальный журнал и история кошелька
- Журнал событий и история баланса — это **append-only ledger**. Строки никогда не обновляются и не удаляются после записи — требование для аудита и для предотвращения рассинхрона "Было/Стало".
- "Было X → Стало Y, Изменение Z" — зафиксированный снапшот на момент события, а не live-JOIN с текущим балансом, иначе цифры в истории будут "плыть" при историческом просмотре.
- Для пагинации и фильтров (ID/ник, валюта, тип события, дата) — составные индексы под реальные паттерны фильтрации. Для поиска по нику рассмотри `pg_trgm`/триграммный индекс вместо `LIKE '%...%'` без индекса.
- Пагинация журнала — **keyset/cursor pagination** (по `id`/`created_at`), не `OFFSET`: журнал будет расти, OFFSET деградирует на больших смещениях.

### 1.2 Багфикс удаления сезона (каскад без потери наград игроков)
Это не "просто включи `ON DELETE CASCADE`". Бизнес-правило на первый взгляд противоречиво: удаление сезона должно (а) чистить сиротские записи **шаблонов** наград и прогресса БП, но (б) не трогать уже полученные игроками награды.

- Таблицы **шаблонов** сезона (уровни, требования, описания наград) — `ON DELETE CASCADE` от `season_id`, это безопасно: шаблон не нужен после удаления сезона.
- Таблица **выданных наград игрока** не должна иметь жёсткую зависимость, ломающую целостность при удалении сезона. Выбери и обоснуй в отчёте один из вариантов (молчаливый выбор не допускается):
  - **Снапшот-денормализация**: при выдаче награды копировать в инвентарь игрока неизменяемые данные о предмете (название, редкость, иконка), а `season_id` сделать `ON DELETE SET NULL` — предмет у игрока останется отображаться корректно после удаления сезона-родителя.
  - **Soft-delete сезона** (`is_deleted = true`, скрытие из админки и каталога) вместо физического `DELETE` — устраняет проблему каскада вообще, данные остаются для отчётности.
- Любое решение тестируется на staging-копии данных перед продом: удали тестовый сезон, убедись, что у тестового игрока награда осталась видна и корректна.

### 1.3 Реестр сущностей для конструктора наград
Чтобы убрать хардкод из редактора БП без открытия дыры (см. Этап 2.1), заведи **таблицу-реестр сущностей**: тип сущности, таблица-источник, поля для отображения (название/иконка/редкость). Динамический `ItemSelector` читает этот реестр, а не делает произвольный SQL-introspection по `information_schema` в продакшене.

## ЭТАП 2: Backend

### 2.1 Конструктор наград — безопасно
`ItemSelector` обращается только к таблице-реестру (Этап 1.3), а не выполняет произвольные запросы к схеме БД по вводу из админки. Это устраняет и хардкод новых типов предметов, и риск SQL-инъекции через "универсальный" интерфейс.

### 2.2 Синхронизация тем без конфликтов
БД — источник истины, но при одновременном редактировании в админке и активной сессии игрока возможен race condition между двумя авторитетными состояниями. Реализуй:
- Версионирование темы (`theme_version`/`updated_at`) на сервере.
- Push-уведомление об изменении (WebSocket/SSE) или минимум ETag-ревалидацию — без необходимости игроку перезагружать страницу.
- Явно опиши в отчёте по этапу: что происходит, если игрок применил локально оптимистичное изменение темы за секунду до серверного обновления — какая версия побеждает.

### 2.3 Ребаланс экономики — не "скрипт в одну сторону"
- Скрипт "Time-to-Max" — параметризуемый инструмент (CLI/admin-tool), параметры кривой (база, степень, коэффициенты) — в конфиге, не зашиты в код.
- Перед применением новой кривой опыта/цен — обязательна **симуляция на текущем распределении прогресса живых игроков** (бэктест), не только теоретический расчёт "с нуля". Итог — отдельный отчёт ("сколько игроков на каком этапе пострадают/выиграют") на утверждение человеку до деплоя.
- Изменение цен/курсов не должно retroactively обесценивать уже потраченные игроками ресурсы без явного решения владельца продукта.

### 2.4 Аудит админ-действий
- Любое мутирующее действие в админке (удаление сезона, правка темы, ребаланс) пишется в отдельный журнал админ-аудита (кто/когда/что изменил) — отдельно от игрового журнала событий.
- Все админ-эндпоинты — за role-based проверкой прав, не за "просто секретным URL".

## ЭТАП 3: Frontend (Косметика 2.0 и "Примерочная")

### 3.1 Общий список (Магазин Кастомизации) — только статика
- Карточки в общем гриде — лёгкие статичные превью (`webp`/`avif`), без монтирования Canvas/WebGL/тяжёлых эффектов.
- Ленивая загрузка превью через `IntersectionObserver`; для крупных каталогов — виртуализация списка (windowing), чтобы не держать тысячи DOM-узлов одновременно.
- `contain: layout style paint` на карточках грида для изоляции перерисовки.

### 3.2 Примерочная (Fullscreen Modal) — тяжёлые эффекты только здесь
- Партиклы/глитч-эффекты — строго внутри модалки, собственный цикл через `requestAnimationFrame`.
- `cancelAnimationFrame` и явная очистка (dispose WebGL-текстур/контекстов, снятие всех `addEventListener`) — **обязательны** в cleanup при закрытии модалки/анмаунте. Это главная точка утечек памяти при повторных открытиях "Примерочной".
- `will-change` — точечно, только на элементах с активной анимацией, и снимается после её завершения. Постоянный `will-change` на множестве элементов сам по себе сжирает GPU-память на мобильных.
- Для систем частиц — **object pooling** (переиспользование объектов вместо create/destroy каждый кадр) для снижения нагрузки на GC.
- `prefers-reduced-motion` как дефолтная база + явный тоггл "Отключить анимации" в настройках, сохраняемый per-user.

### 3.3 Пресеты и точечная экипировка
- Сущность `Preset` (Тема + Рамка + Эффект + Фон + Титул) — ссылки на уже существующие сущности косметики (foreign keys), не дублирование данных предмета внутри пресета — иначе правка предмета не применится к уже сохранённым пресетам.
- Игрок сохраняет возможность точечно надевать/снимать отдельные слоты без потери остальных активных пресетных слотов.
