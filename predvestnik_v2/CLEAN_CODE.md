# CLEAN_CODE — единый стандарт кода «Предвестника» для всех ИИ-агентов

> **Кому это обязательно:** любому ИИ-агенту любого вендора (Claude, GPT/Codex, Gemini, Qwen,
> opencode, локальные модели) и любому человеку, который правит код в этом репозитории.
> Правила не зависят от того, кто именно их выполняет: Claude не имеет послаблений,
> GPT не имеет исключений, «мне так удобнее» — не аргумент.
>
> **Когда читать:** до первой правки кода, а не после. Если ты начал писать код в этом
> проекте и не читал этот документ — остановись и прочитай.
>
> **Связь с другими правилами:** `AUTONOMOUS_AGENT_POLICY.md` отвечает на вопрос «как доказать,
> что изменение работает», этот документ — «каким должен быть код и чего в репозитории быть
> не должно». Оба действуют одновременно. Методология проверки там, методология чистоты здесь.
>
> **Что это НЕ:** справочник по механикам проекта. Здесь нет и не должно быть указаний вида
> «в таком-то файле лежит такая-то механика». Факты проекта живут в самом коде, его реестрах
> и документации проекта; этот документ — только о качестве и дисциплине.

## 1. Кодекс

Пять положений. Всё остальное в документе выводится из них. Если правило ниже спорно —
решай по кодексу.

1. **Прод живой.** За каждым коммитом в основную ветку — реальные игроки и реальные данные.
   Ошибка на проде стоит дороже, чем час аккуратности. Скорость важна, но только
   не за счёт корректности.
2. **Код пишется для следующего читателя.** Им будет другой агент — без твоего контекста,
   возможно, другого вендора, возможно, через месяц после тебя. Он должен понять смысл
   без архива переписки. Переменные, функции и структура объясняют намерение; комментарий
   объясняет только то, чего код объяснить не может.
3. **Лагерь чище, чем ты его нашёл.** Ушёл из задачи — не оставил после себя мусора:
   ни мёртвого кода, ни отладки, ни временных файлов, ни осиротевших веток. Мусор одного
   агента — баг, который будет найден другим агентом в самый неподходящий момент.
4. **Минимальный достаточный диф.** Каждая строка в diff'е обязана ответить на вопрос
   «зачем ты в этой задаче?». Не знаешь ответа — строка не попадает в коммит.
5. **Простота — это функция, а не недостаток.** Решай самую простую версию задачи,
   которая закрывает требование. Хитрость оправдана только измеримой необходимостью.

## 2. Архитектурная дисциплина

2.1. **Зависимости направлены внутрь.** Бизнес-логика не знает, кто её вызывает: ни Telegram,
ни веб, ни консоль. Внешний мир приходит через адаптеры, адаптеры — тонкие: приняли ввод,
отдали вывод, делегировали логику. Толстый адаптер — это логика, живущая не в своём слое.

2.2. **Одна логика — одно место.** Правило, по которому живут деньги, предметы, права или
баланс, реализовано один раз и вызывается всеми. Две копии одного правила в разных
частях системы — это не надёжность, а гарантированный рассинхрон в будущем.
Бот и веб-интерфейс — два окна в одну систему, а не две системы.

2.3. **Контракт стабильнее реализации.** Внутренности можно переписывать, форматы обмена —
нельзя ломать молча. Меняешь формат данных, ответ API или схему — обеспечь совместимость
со старыми клиентами и старыми данными либо миграцию для них.

2.4. **Числа живут в конфигурационном слое.** Цены, лимиты, коэффициенты, проценты —
именованные константы и реестры, а не литералы, рассыпанные по логике. Увидел магическое
число в чужом коде по пути — вынеси (это и есть «лагерь чище»).

2.5. **Новые зависимости — обоснованное решение.** Библиотека добавляется, когда своё
решение дороже поддержки чужого. Не добавляй пакет ради одной функции, которая пишется
в пять строк. Каждая зависимость — чужой код в проде.

2.6. **Не создавай параллельных структур.** Не заводи «свою» версию существующей утилиты,
реестра или хелпера рядом со старой, потому что не искал. Сначала поиск по проекту,
потом написание.

## 3. Python

3.1. Явные типы там, где сигнатура неочевидна; аннотации — контракт функции, а не украшение.
3.2. Без `import *`, без неиспользуемых импортов, без импортов внутри циклов.
3.3. **Исключения не глотать.** `except: pass` (и его родственник `except Exception: return None`)
запрещён. Либо обрабатываешь осознанно и логируешь, либо пускаешь выше. Ошибка, которую
спрятали, — это ошибка, которую будут искать часами.
3.4. Асинхронность честная: не блокируешь event loop синхронными вызовами; фоновая задача
без обработки ошибок — это бомба замедленного действия; «запустил и забыл» допустим только
с обработчиком отказа.
3.5. Одна функция — одна ответственность. Если описание функции требует «и», функцию пора
делить. Возвраты ранние, вложенность мелкая, «стрелка вправо» — запах.
3.6. Имена: существительные для данных, глаголы для действий, `snake_case` для всего
публичного. Однобуквенные имена — только счётчики циклов. Имя должно пережить проект
без словарика.
3.7. Без глобального изменяемого состояния. Если двум частям системы нужно делить данные —
это явная структура с явным владельцем, а не переменная модуля.
3.8. Формы данных — явные структуры (dataclass/pydantic/TypedDict), а не словари-«содержимое
неизвестно», передаваемые через пять слоёв.

## 4. JavaScript / фронтенд

4.1. **Знай модель исполнения.** Прежде чем писать, посмотри, как загружается существующий
код (классический скрипт или модули), и соблюдай его ограничения. В классическом скрипте
объявления не разбрасываются по файлу как попало — последствия всплывут в рантайме,
а не при написании.
4.2. Подстановка значений в строки — только шаблонными строками; конкатенация с приведением
типов — источник багов `1 + "1"`.
4.3. Не объявляй повторно имена, уже занятые в той же области видимости. Перед добавлением
функции — убедись, что её нет. Дублирование объявлений в большом скрипте ловится только
проверкой синтаксиса — выполняй её (см. раздел 8).
4.4. DOM-код защищённый: элемент может отсутствовать, быть скрытым, отрендериться позже.
Обращение к `node.value` без проверки существования — баг, просто ещё не выстреливший.
4.5. Слушатели событий не накапливаются: повторный рендер компонента не должен плодить
дубликаты обработчиков. Кто навесил — тот и снимает (или переиспользует узел).
4.6. Сеть всегда неидеальна: у запроса есть таймаут, у кнопки — состояние «загрузка»,
у отказа — сообщение игроку, а не вечный спиннер или молчаливое ничего. Повторный клик
по активной кнопке не должен дублировать операцию.
4.7. Никакой сборки HTML из непроверенных данных: игрокский ввод и внешние данные
вставляются как текст, а не как разметка.
4.8. Никакого `console.log` и `debugger` в закоммиченном коде. Отладка завершилась —
отладочный вывод удалён (см. раздел 6).

## 5. SQL и данные

5.1. Только параметризованные запросы. Строка SQL не собирается склейкой с данными —
никогда, ни «внутреннего» запроса, ни «безопасного» случая.
5.2. Явные списки колонок в `INSERT` и `SELECT` (кроме честного «всё» в уместном месте).
`SELECT *` в продакшен-запросах — дверь к поломке при смене схемы.
5.3. Диалект и драйвер проекта — не ANSI SQL: смотри образцы запросов в проекте и пиши
как они, а не «как в документации вообще». Особенности синтаксиса конфликтов, плейсхолдеров
и приведений типов проверяются по живому коду, а не по памяти.
5.4. Многошаговая операция с данными — одна транзакция. Половина операции, пережившая сбой,
— это испорченные данные, которые заметят через неделю.
5.5. Повтор запроса не должен создавать вторую сущность: там, где возможен повтор, —
идемпотентность (`ON CONFLICT`/уникальные ключи), а не надежда «дважды не нажмут».
5.6. Миграции обратно совместимы: сначала новый код читает старое и новое, потом данные
едут, потом (отдельным шагом, позже) старое удаляется. Разрушение данных — не «часть фичи».
5.7. Деньги и балансы — целыми единицами минимальной точности; float для валюты запрещён.
Списание и начисление — одна атомарная операция с проверкой остатка.

## 6. Анти-мусорный регламент

Это жёсткие запреты. Проверь свой diff перед завершением по каждому пункту.

**Запрещено оставлять в коде и репозитории:**

6.1. Закомментированный код. Мёртвый код удаляется — история живёт в git, а не в комментариях.
6.2. Отладочный вывод: `print`, `console.log`, `debugger`, временные логи «посмотреть, что тут».
6.3. Резервные копии файлов: `*_old`, `*_backup`, `*_copy`, `*.bak`, `final_v2`, `новый (2)`.
Ты не в 2010-м, есть ветки.
6.4. Пустые файлы-заглушки и пустые функции «на будущее» — это YAGNI в чистом виде (раздел 1.5).
6.5. Скриншоты, логи, дампы, экспорты, артефакты сборки в рабочем каталоге. Артефакты
твоей сессии — вне git; то, что обязано существовать временно, — в игнор-листе проекта.
6.6. Одноразовые скрипты в корне проекта. Понадобился разовый фикс — он выполняется
и удаляется, либо, если это повторяемая операция, — оседает в каталоге утилит проекта
с именем, говорящим, что он делает.
6.7. Секреты: токены, ключи, пароли, строки подключения — никогда в коде и коммитах,
только в переменных окружения. Увидел секрет в коде — это инцидент: убрать и сообщить,
а не «пусть висит».
6.8. `TODO`/`FIXME` без имени, даты и плана. Хороший маркер: «что осталось, почему сейчас
не сделано, кто и когда вернётся». Плохой: `# TODO пофиксить`.
6.9. Мусорные имена файлов: транслит, пробелы, регистр как попало, `тест`, `tmp`, `aaa`.
Имя файла — та же документация.
6.10. Осиротевшие ветки и воркспейсы. Задача закрыта и смёржена — ветка удаляется
и локально, и на сервере. Список веток — это тоже интерфейс проекта.

## 7. Git-гигиена

7.1. **Коммит атомарный.** Одна логическая цель: одна фича, один фикс, одна документация.
«Заодно поправил» соседнего слоя — отдельный коммит (или никогда, если не просили).
7.2. Сообщение отвечает на вопрос «что и почему изменилось», а не «что я делал».
Стиль сообщений — как в истории проекта; история коммитов читаема как дневник проекта.
7.3. Перед каждым коммитом: `git status` и `git diff --staged`. Ты отвечаешь за каждую
строку, попавшую в коммит, включая файлы, попавшие туда случайно. «Не заметил, как
закоммитил лог» — не оправдание, а нарушение.
7.4. В этом репозитории два независимых проекта. Один коммит — один проект, без исключений.
7.5. Не переписывай историю общих веток и не пушь силу туда, куда смотрят другие.
7.6. Ветка — под задачу, имя объясняет задачу. Живёт ровно столько, сколько задача.
7.7. Чужие незакоммиченные изменения в рабочем каталоге не трогаем: это не твой мусор
и не твоя правка. Свою работу веди в чистом месте от свежей основной ветки.

## 8. Definition of Done — что значит «готово»

«Готово» — это не «я закончил печатать». Это все пункты списка:

1. **Проверки реально запущены.** Синтаксическая проверка каждого тронутого языка,
   тесты и контрактные проверки проекта, где они есть. «Должно работать» — не результат;
   команда проверки и её вывод — результат.
2. **Контрпример найден.** По правилам `AUTONOMOUS_AGENT_POLICY.md`: минимум один
   реалистичный сценарий отказа рассмотрен и показано, что происходит.
3. **Само-ревью diff'а выполнено.** Перечитал свой диф целиком; каждый ханк объясним;
   мусора из раздела 6 нет; в диффе нет строк «заодно».
4. **Обе стороны согласованы.** Если менялась общая логика — проверено, что бот и веб
   показывают согласованное поведение, а не «я правил только тут».
5. **Документация не соврала.** Изменил поведение, заметное игроку или другому агенту, —
   обновил документацию проекта в том же коммите. Изменил формат данных — описал миграцию.
6. **Игрок увидит новость.** Заметное игроку изменение выпущено по правилам проекта
   о патч-нотах (см. корневой `AGENTS.md`), а не прошло молча.
7. **Мусора нет.** Раздел 6 пройден по списку, временные файлы удалены, ветка-мусор
   не оставлена.

## 9. Этика многоагентной среды

Над проектом одновременно работают агенты разных компаний и люди. Ведите себя как одна
команда, а не как соседи по общежитию.

9.1. **Не перекраивай проект под свой вкус.** Рефакторинг — не переписывание. Стиль
окружающего кода — закон для твоего кода: те же отступы, именование, паттерны ошибок,
что и в соседних файлах. Твой «более правильный» стиль — не основание трогать чужое.
9.2. **Нашёл чужой костыль — не воспроизводи и не ломай молча.** Не копируй его как
образец, но и не переписывай в чужой задаче. Исправь в рамках своей задачи, если это
безопасно, либо зафиксируй находку для владельца.
9.3. **Документация — часть кода.** Рассинхрон документации с реальностью — баг
документации, чинится в том же коммите, что и изменение. Ссылка на несуществующий файл —
тоже баг (и довольно обидный: следующий агент пойдёт по ней и споткнётся).
9.4. **Твой результат должен быть воспроизводим без тебя.** Ты исчезаешь после сессии:
остаются коммит, сообщение, документация и проверки. Всё, что жилo только у тебя в голове
или в переписке, — потеряно.
9.5. **Не блокируй других.** Долгоживущие некоммиченные изменения в общем рабочем
каталоге, занятые общие ресурсы, брошенные полуготовые ветки в общей инфраструктуре —
вредят всем, кто работает параллельно.

## 10. Продакшен-дисциплина

10.1. Ошибка игрока не фатальна. Любой сбой — сеть, данные, таймаут — оставляет игрока
в валидном состоянии с понятным сообщением, а не в зависшем экране. Degradation
предпочтительнее падения.
10.2. Рискованные изменения — за фича-флагом или постепенным включением, а не «покатит».
10.3. Игровая экономика — святая территория: баланс, цены, шансы меняются только
по явной задаче с расчётом до/после, а не «заодно чуть подкрутил».
10.4. Лог ошибки должен позволить исправить её без воспроизведения: контекст,
идентификаторы, что пытались сделать.
10.5. Основная ветка уходит на прод автоматически. Всё, что в неё попадает, — уже
продакшен-код, и относится к нему надо соответствующе (см. раздел 1.1).

## 11. Антипаттерны ИИ-агентов — самопроверка

За каждым пунктом — реальный класс ошибок автономных агентов. Периодически спрашивай
себя, не делаешь ли ты это сейчас:

1. **Забота о гипотетическом будущем.** Три уровня абстракции под одну функцию,
   «пригодится, если». Не пригодится (YAGNI).
2. **Перестройка работающего кода ради красоты.** Диф на 400 строк, чтобы «стало
   аккуратнее», при неизменном поведении — вредительство с хорошими намерениями.
3. **Слепая вера в первый вариант.** Свой код перечитывают. Особенно условия,
   границы и отрицания.
4. **Тихие правки мимо задачи.** «Заодно» причесал соседний модуль, «заодно» обновил
   зависимость — диф перестал соответствовать заявленной цели.
5. **Заявление успеха без проверки.** «Готово» без запущенной проверки — не готово,
   а надежда.
6. **Дублирование вместо поиска.** Написал свой хелпер, не найдя существующий,
   потому что не искал.
7. **Лик без уборки.** Отладка выведена, файлы скачаны, скрипты одноразовые —
   и всё это осталось в репозитории.
8. **Глотание ошибок ради зелёного пути.** Пустой `except`, дефолт вместо отказа,
   «ну хотя бы не падает».
9. **Игнор контрактов.** Изменил формат, не проверив, кто ещё его читает — старые данные,
   старые клиенты, второй адаптер.
10. **Молчание о сомнениях.** Заметил проблему за пределами задачи, промолчал,
    «не моя забота». Твоя: ты её видел.

## Финальный чек-лист (держи в голове одну строку)

**Прочитал правила → понял слои → минимальный диф → проверки запущены → контрпример
найден → диф перечитан → мусор удалён → документация верна → коммит атомарный →
сообщение объясняет «что и почему».**

Если ты дошёл сюда и не согласен с каким-то правилом — не молча обходи его, а скажи
владельцу проекта: правила живые и меняются явно, а не исподтишка.

*Документ обязателен для всех агентов. Обновляется через коммит с объяснением, что
и почему изменилось.*
