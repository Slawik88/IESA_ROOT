## 🔴 П1. Стрик: награда не атомарна, потеря — молча и навсегда

**Файл:** `bot/middlewares/streak_mw.py:74–220`

День забирается атомарно и **коммитится сразу** (`upsert_global_streak`, стр. 91), награда
начисляется **следующим отдельным запросом** (`add_balance`, стр. 103), и всё это обёрнуто
во внешний `try` (74), который заканчивается `except Exception: pass` (219–220).

Транзакции здесь нет. Проверено: `PGAdapter.commit()` (`infrastructure/pg_adapter.py:269–273`)
— *«In auto-commit mode (no active tx) this is a no-op»*, а `db.connection.transaction()` в
этом файле не используется вообще. То есть `await db.commit()` на стр. 147 — пустышка,
а каждый запрос коммитится сам по себе.

**Сценарий отказа:** любой сбой БД между стр. 91 и 103 (таймаут/обрыв — а `DB TimeoutError`
в этом проекте уже случался) → день помечен взятым, Мора и 💎 не начислены, исключение
проглочено. Игрок теряет дневную награду **навсегда** (завтра день уже «взят»), и об этом
**не остаётся ни строчки в логах** — `pass` без `logger`.

**Как правильно** — рядом в том же проекте есть эталон: `transfer_currency()` и
`family_bank_transaction()` оба заворачивают чтение+запись в `async with db.connection.transaction()`.

**Фикс:** обернуть «забрать день + начислить награду» в `db.connection.transaction()` (сбой →
откат заявки на день → игрок получит награду со следующего сообщения) и заменить `pass` на
`logger.exception(...)`. Внешний `except: pass` сейчас прячет *любые* поломки стрика, включая
логические — система может быть сломана месяцами, и никто не узнает.

## 🔴 П2. Скидка Черепахи заморожена на 5% для всех уровней

**Файлы:** `services/economy.py:44–50` (корень), `:58–78`, `:95–97`

```python
def apply_discount(self, price, has_discount: bool) -> int:
    if not has_discount:
        return int(price)
    return int(price * (1.0 - TURTLE_BONUSES[5]["shop_discount"]))   # ← Lv5 ХАРДКОД
```

Реальный уровень читается (`_get_turtle_shop_discount` возвращает точную долю), но тут же
**схлопывается в `bool`** через `has_turtle_discount()` — и уровень теряется. Дальше всем
подряд применяется скидка пятого уровня.

| Уровень Черепахи | Обещано (`TURTLE_BONUSES`) | Реально в магазине | Итог |
|---|---|---|---|
| Lv1 | −2% | **−5%** | игрок переплачен |
| Lv5 | −5% | −5% | ✅ совпало |
| Lv8 | −7% | **−5%** | игрок обделён |
| Lv10 | −10% | **−5%** | игрок обделён вдвое |

**Бьёт и по боту, и по сайту** — оба пути (витрина и списание) зовут `apply_discount`.
Согласованно неправильно: расхождения бот↔сайт нет, но оба врут одинаково.

**Отдельно скверно:** карточка питомца показывает **настоящее** значение по уровню
(`bot/handlers/zoo.py:359`, `services/zoo.py:122`, `app.03.js:353` — все читают
`shop_discount` из таблицы). То есть **карточка обещает «−10% магазин», а касса даёт −5%**.
Описание вида в реестре тоже обещает: *«Lv10 — максимальные скидки»*.

Правильный API **уже написан, но мёртв**: `get_turtle_discount()` (`:40`) и
`apply_discount_fraction()` (`:52`) — **ноль вызовов** по всему проекту (проверено grep).
Докстринг сам признаётся: *«defaults to the Lv5 value to preserve behaviour; new callers
should use get_turtle_discount + multiply manually»* — временная затычка, которую забыли снять.

**Фикс:** перевести `get_item_prices()` и `purchase_item()` на `get_turtle_discount()` +
`apply_discount_fraction()`, `apply_discount(bool)` удалить.

## 🟠 П4. Скидка Черепахи игнорирует слот (нарушение «Блока 12»)

**Файл:** `services/economy.py:12–24`

```python
"SELECT COALESCE(pet_level, 1) FROM pets "
"WHERE owner_id = ? AND placement IN ('active','passive') "
"AND species_id = 'turtle' AND fatigue < 100 LIMIT 1"
```

Два дефекта:

1. **Нет `scale_pet_bonus()`.** По «Блоку 12» питомец в пассивном слоте даёт **половину**
   бонуса. Магазин — **единственный** потребитель бонусов питомцев, который ходит в БД сам
   вместо готового `get_species_bonus()` (`infrastructure/repositories/zoo.py:176`), который
   слот учитывает. Экспедиции, квесты, зоопарк — все используют правильный аксессор.
   А у Черепахи `default_role` = **`"passive"`** — то есть почти у всех она именно в том
   слоте, где скидку положено делить пополам.
2. **`LIMIT 1` без `ORDER BY`.** Если у игрока две Черепахи (актив + пассив), выбирается
   произвольная. Эталон рядом — `get_species_level_placement()` делает
   `ORDER BY (placement = 'active') DESC`.

Сейчас это замаскировано пунктом П2 (значение всё равно выбрасывается в bool), поэтому
**чинить нужно вместе с П2** — иначе фикс П2 включит полную скидку и пассивным Черепахам.

## ✅ П7. Щит новичка при возврате в чат стирает постоянный иммунитет — ПОЧИНЕНО 2026-07-18

> Фикс: `bot/handlers/events.py` теперь зовёт `mod_service.shield_user()` (сохраняет
> `is_immune`, пишет журнал, сам создаёт строки users/user_chat_stats).

**Файл:** `bot/handlers/events.py:267–280`

Автовыдача «щита новичка» при входе в чат (`shield_duration_days` > 0) пишет иммунитет
напрямую, в обход единого сервиса:

```python
await mod_db.set_immunity(db, chat_id, user_id, 0, until_str)   # ← is_immune ЖЁСТКО 0
```

Все остальные три точки записи (`shield_user`, `unshield_user`, `set_immune_user` в
`services/moderation.py`) сначала читают текущий `is_immune` и передают его дальше
(`keep_immune`), чтобы временный щит не сбрасывал постоянный. Этот путь — единственный,
который этого не делает.

**Сценарий отказа:** игроку выдан постоянный иммунитет (`бот иммунитет`). Он выходит из
чата и возвращается (или его кикнули/разбанили) в чате, где включён «щит новичка»
(`бот настройка щита`). Иммунитет молча превращается в обычный временный щит на
`shield_duration_days` дней — после его истечения защита пропадает насовсем, и никто
не увидит это в логах (`set_immunity` не пишет `moderation_logs`, в отличие от
`shield_user`/`set_immune_user`, которые зовут `log_moderation_action`).

Это ровно тот класс бага, что уже чинили в `cbb09db8` («защита/рест: критический баг с
перезаписью иммунитета») — но фикс применили только к ручной команде `бот рест`, этот
параллельный путь (авто-щит при входе) остался нетронутым.

**Фикс:** заменить прямой вызов на `mod_service.shield_user(db, chat_id, user_id,
bot.id, shield_days*1440)` (он сам сохранит `is_immune` и напишет журнал), либо руками
прочитать `get_chat_stats` и передать `keep_immune` — как везде.

## 🚫 П8. Тумблер «бот иммунитет» стирает активный временный рест — WONTFIX (решение 2026-07-18)

> Пользователь решил: не трогать. Иммунитет-тумблер всегда чистит всё — это принятое
> поведение продукта, не баг. Не поднимать повторно.

**Файл:** `services/moderation.py:259–264`

```python
async def set_immune_user(db, chat_id, target_id, admin_id, on, reason=None):
    """Постоянный иммунитет вкл/выкл. Включение/снятие сбрасывает и временный щит."""
    await set_immunity(db, chat_id, target_id, 1 if on else 0, None)
```

`immune_until` жёстко обнуляется при ЛЮБОМ переключении (и включении, и выключении),
независимо от того, активен ли сейчас временный рест. Комментарий в коде выдаёт это
за намеренное поведение, но по факту это побочный эффект, о котором никого не
предупреждают.

**Сценарий отказа:** админ A выдал `бот рест, @юзер 7д`. На 2-й день админ B (по другой
причине — тестирует права, ошибся командой) включает и тут же выключает `бот иммунитет`
для того же юзера. Оставшиеся 5 дней реста исчезают без единого сообщения об этом —
ни экрана подтверждения, ни строчки в `бот кто рест`.

**Фикс:** если `immune_until` в будущем и `on == False` (снимаем постоянный, но был
активный рест) — сохранить `immune_until` как есть вместо `None`. Если это осознанное
решение продукта (иммунитет — только «всё или ничего»), тогда хотя бы предупреждать
админа в ответе бота: «⚠️ у юзера был активный рест до ДАТА — он тоже снят».

## ✅ П9. Ранговая асимметрия: рест выдать легче, чем снять — ПОЧИНЕНО 2026-07-18

> Фикс: `cmd_unprotect` перешёл на `check_admin_rights` (симметрично выдаче,
> без сравнения с рангом цели).

**Файлы:** `bot/handlers/moderation.py:357–362` (выдача) vs `:401–406` (снятие)

Выдача реста проверяет `check_admin_rights` — только ранг инициатора ≥ `rank_shield`,
**без сравнения с рангом цели**. Снятие (и `снять рест`, и постоянный `иммунитет`) идёт
через `_check_target_rights` → при цели ≠ себе вызывает `check_mod_rights`, который
**требует `target_rank < admin_rank`**.

**Сценарий отказа:** админ с рангом 4 (`rank_shield` по умолчанию) защищает Владельца
чата (ранг 6) — команда проходит, target-проверки нет. Через неделю снять этот же рест
он уже не может: `check_mod_rights` вернёт «⚠️ Вы не можете наказать того, чей ранг
равен вашему или выше» — хотя речь не о наказании, а о снятии защиты. Рест «залипает»
до ручного вмешательства более высокого ранга (или самого Владельца).

**Фикс:** либо выдачу реста тоже гонять через target-сравнение (нельзя защитить того,
кто выше тебя), либо снятие — через `check_admin_rights` без сравнения (симметрично
выдаче). Сейчас несимметрично в обе стороны нежелательным образом.

## ✅ П10. `parse_time` без верхней границы — краш на огромном числе — ПОЧИНЕНО 2026-07-18

> Фикс: `parse_time` бросает `TimeTooBigError` при сроке > 3650д; рест/варн/мут отвечают
> явным «Слишком большой срок. Максимум 3650д»; глоб-санкции оставляют число в причине.

**Файл:** `bot/handlers/moderation.py:43–57`, используется в `cmd_warn`, `cmd_protect`

```python
match = re.match(r"^(\d+)([смчдsmhd])$", time_str.lower())
...
return timedelta(days=val)
```

`\d+` не ограничен по длине. `timedelta` в Python хранит максимум ~999 999 999 дней —
за пределами этого `timedelta(days=val)` кидает необработанный `OverflowError` прямо
внутри `parse_time`, до всех `try/except`.

**Сценарий отказа:** `бот рест, @юзер 99999999999999д` (опечатка лишний ноль, не злой
умысел — ранг для этой команды и так ограничивает круг лиц) → хендлер падает
исключением вместо ожидаемого «❌ Неверный формат времени!», админ получает тишину.

**Фикс:** обернуть `timedelta(...)` в `try/except (OverflowError, ValueError): return None`
внутри `parse_time` — один раз чинит и `варн`, и `рест`.
