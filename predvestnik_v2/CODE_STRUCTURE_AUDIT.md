## Найдено, требует решения пользователя перед выполнением

Ниже — реальные, крупные структурные проблемы. Не исправлялись автоматически: каждая
задевает **живой продакшн-бот с реальными деньгами/питомцами/браками игроков**, а объём
правок для полного фикса — от нескольких часов до дня работы с риском регресса. Это
осознанно оставлено на явное решение пользователя (см. «Executing actions with care» —
крупные, труднообратимые правки на проде требуют подтверждения, даже при общем «делай всё»).

### 🔴 Главная находка: SQL вне `infrastructure/repositories/` — нарушение собственного «железного правила»

`BASE_PROMPT.md` прямо запрещает: `infrastructure/ ← только SQL в repositories/`
(bot/FastAPI не должны сами писать `db.execute(...)`, только вызывать repositories).

**Факт (на начало сессии):** 38 файлов в `bot/handlers/` и `FastAPI/routers/` содержали
сырой `db.execute(`, суммарно ~250 отдельных SQL-вызовов мимо `infrastructure/repositories/`.
`FastAPI/routers/zoo.py` (был лидер, 36) и `bot/handlers/zoo.py` (15) — оба обработаны,
теперь по 4 (намеренные исключения) в каждом. Осталось 36 файлов.

**Решение принято 2026-07-02 (карт-бланш пользователя, «как лучше на твоё мнение»):
мигрируются только ИГРОВЫЕ пути с реальным риском расхождения бот↔сайт; dev-консоль и
админ-инструменты осознанно остаются с сырым SQL.** Обоснование: правило существует ради
предотвращения багов класса «стрик бот≠сайт» (два независимых места одной бизнес-логики).
У dev-консоли второй реализации нет и не будет — миграция её ~70 запросов дала бы ноль
защиты от расхождений при реальном риске регресса в рабочих админ-инструментах.

Классификация оставшихся файлов:

| Категория | Файлы | Вердикт |
|---|---|---|
| ✅ Мигрировано | `FastAPI/routers/zoo.py` (36→4), `bot/handlers/zoo.py` (15→4), `bot/handlers/expeditions.py` (12→5) | Общие repo-функции бот+сайт |
| 🔒 Dev-only, осознанно оставлено | `dev_console/*` (bp 19, player 12, vip 10, system 7, sql 1), `bot/handlers/dev.py` (16), `admin.py` (19), `global_admin.py` (10) | Одна реализация, нет риска расхождения; sql.py — сама фича «SQL-консоль» |
| 📖 Ad-hoc reads, допустимо | `profile.py` (15 — эндпоинт-специфичные JOIN-ы), `events.py` (10 — трекинг входов/выходов), остальные ≤6 | Используются в одном месте, не дублируют чужую логику |
| ⚠️ Кандидат следующего пилота | `FastAPI/routers/marriage.py` (10) — семейный банк, реальные деньги; у бота есть parallel-логика в `bot/handlers/marriage.py` | Отдельная сессия с проверкой на живых данных |

**Остающиеся 4-5 «исключений» в мигрированных файлах** — это `BEGIN`/`COMMIT` (управление
транзакциями) и инвентарные `FOR UPDATE`-декременты внутри уже открытых атомарных транзакций
(вынос через `remove_item()` создал бы вложенную транзакцию с непроверяемым на живой БД
поведением при гонках) — задокументировано в самих файлах.

### ✅ `services/scheduler.py` — два больших фоновых таска — РАСПИЛЕНО 2026-07-02

Было: `duel_and_auction_task()` 282 строки и `expedition_background_task()` 189 строк —
всё в одном `while True: sleep(60); try:` блоке. Стало: главные циклы 45 и 26 строк,
каждый шаг — своя именованная функция (`_expire_timed_out_duels`, `_resolve_expired_auction_lots`,
`_send_vip_expiry_reminders`, `_send_bp_season_end_reminders`, `_run_weekly_monday_jobs` +

`_grant_weekly_vip_items`, `_finish_expedition`). Семантика try/except сохранена 1-в-1 на
тех же границах (сбой одного шага не рушит остальные, как и раньше).
Заодно удалён `exchange_scheduler_task` целиком: функция делала `return` первой строкой,

в git-истории); её регистрация в `bot/__main__.py` тоже убрана — задача создавалась и
мгновенно умирала каждый запуск.

### 🟢 Проверено — НЕ проблема, несмотря на размер

- **`bot/core/database.py` (1296 строк)** — выглядит как «god file», но внутри — 12 чётко
  названных функций `_init_X()` по одной на группу таблиц (`_init_users_and_chats`,
  `_init_inventory_and_pets`, `_init_crypto`, `_init_analytics`, ...), каждая — это просто
  последовательность `CREATE TABLE IF NOT EXISTS`. DDL по природе многословен; держать всю
  схему БД в одном файле — осознанная, распространённая практика (проще искать, гарантирован
  порядок создания таблиц с FK). Не рекомендую дробить.
- **`bot/handlers/identity.py`** (`_render_premium_profile` 287 строк, `_render_full_profile`
  175 строк) — проверено на предмет дублирования с `services/profile_render.py.build_profile_text`
  (202 строки): это НЕ одна и та же функция под разными именами. `identity.py` рендерит
  декорированную карточку для команд «профиль»/«кто я»/«анкета» (с темами, премиум-стилем);
  `services/profile_render.py` используется веб-стороной (превью тем в DevConsole/сайте);
  `bot/handlers/profile.py._build_profile_text` (третье место, 41-я строка) — отдельная,
  более лёгкая команда «инфо»/«досье» для быстрого просмотра чужого профиля без декора.
  Три разных уровня детализации для трёх разных команд — намеренный дизайн, не копипаста.
  `identity.py` уже частично переиспользует общий код (`from services.profile_render import
  _render_premium as _shared_premium`).
- **JS-файлы `app.0*.js`** (402–1060 строк каждый) — уже осознанно разбиты на 9 частей по
  established-конвенции проекта (см. `project_appjs_split.md` в памяти), укладываются в
  разумные рамки на файл. Отдельные функции внутри, кроме уже исправленной `loadGlobalDev`,
  не превышают ~150 строк — это нормально для функций, которые строят большие HTML-блоки.

## ✅ Расхождение формулы усталости при перемещении питомца — УНИФИЦИРОВАНО 2026-07-02

Решение (карт-бланш пользователя): единая формула реализует ровно то, что обещает
описание вида Волк в `core/registry.py` («Lv10 — иммунитет перемещений») и что бот всегда
показывал в кнопках (цена за ЛЮБОЕ перемещение):

- Новый `services/zoo.movement_fatigue_cost(db, user_id)` — ЕДИНСТВЕННАЯ точка формулы:
  базовая цена `PET_PLACEMENT_FATIGUE_RESTORE` за любое перемещение (включая склад),
  минус непрерывная скидка Волка по уровню (3-20%), Волк Lv10 → 0 (movement_immunity).
- Бот (`cb_pet_move`) и сайт (`move_pet`) оба зовут его + общий repo `apply_pet_move()`.
  `set_pet_placement()` (сайтовая версия) удалена.
- Что изменилось для игроков: бот НАКОНЕЦ реализует обещанный Lv10-иммунитет (раньше брал
  скидку 20% вместо 0); сайт теперь берёт цену за уход на склад (как бот всегда показывал)
  и даёт скидку Волка на всех уровнях (раньше только Lv10-иммунитет). Кнопки бота теперь
  показывают РЕАЛЬНУЮ цену с учётом Волка, а не голую константу.
