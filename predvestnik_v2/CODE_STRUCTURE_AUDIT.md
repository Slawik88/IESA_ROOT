# CODE_STRUCTURE_AUDIT.md — Аудит структуры: god-файлы, god-функции, SQL не на своём месте

> Запрос 2026-07-01: «код должен быть чистым, читаемым, всё на своих местах, не должно
> быть 1 файл делает всё / функции на пол файла». Метод: замер строк по всем `.py`/`.js`
> файлам проекта (без `.venv`), AST-разбор длины Python-функций, эвристика по JS-функциям,
> сверка с железным правилом иерархии из `BASE_PROMPT.md`:
> `infrastructure/ ← только SQL в repositories/`.

## Найдено, требует решения пользователя перед выполнением

Ниже — реальные, крупные структурные проблемы. Не исправлялись автоматически: каждая
задевает **живой продакшн-бот с реальными деньгами/питомцами/браками игроков**, а объём
правок для полного фикса — от нескольких часов до дня работы с риском регресса. Это
осознанно оставлено на явное решение пользователя (см. «Executing actions with care» —
крупные, труднообратимые правки на проде требуют подтверждения, даже при общем «делай всё»).

### 🔴 Главная находка: SQL вне `infrastructure/repositories/` — нарушение собственного «железного правила»

`BASE_PROMPT.md` прямо запрещает: `infrastructure/ ← только SQL в repositories/`
(bot/FastAPI не должны сами писать `db.execute(...)`, только вызывать repositories).

**Факт (на начало сессии):** 38 файлов в `bot/handlers/` и `FastAPI/routers/` содержали
сырой `db.execute(`, суммарно ~250 отдельных SQL-вызовов мимо `infrastructure/repositories/`.
`FastAPI/routers/zoo.py` (был лидер, 36) и `bot/handlers/zoo.py` (15) — оба обработаны,
теперь по 4 (намеренные исключения) в каждом. Осталось 36 файлов.

Худшие из оставшихся нарушителей (SQL-вызовов / строк файла):

| Файл | SQL-вызовов | Строк |
|---|---|---|
| `FastAPI/routers/dev_console/bp.py` | 19 | 605 |
| `FastAPI/routers/admin.py` | 19 | 733 |
| `bot/handlers/dev.py` | 16 | 722 |
| `FastAPI/routers/profile.py` | 15 | — |
| `bot/handlers/expeditions.py` | 12 | 384 |
| `FastAPI/routers/dev_console/player.py` | 12 | — |
| `bot/handlers/events.py` | 10 | 419 |
| `FastAPI/routers/marriage.py` | 10 | — |
| `FastAPI/routers/global_admin.py` | 10 | 461 |
| `FastAPI/routers/dev_console/vip.py` | 10 | — |

**Почему это важно, а не формальность:** `zoo.py` — и бот, и сайт — оба содержат
независимые SQL-запросы к питомцам/экспедициям вместо общего `infrastructure/repositories/zoo.py`.
Это ТОЧНО тот же паттерн, что вызвал уже пофикшенный баг «стрик бот≠сайт» (БЛОК 26.1) —
два независимых места одной и той же бизнес-логики неизбежно расходятся со временем.

**Что НЕ является проблемой (не считать в объём работ):**
- `FastAPI/routers/dev_console/sql.py` — это САМА функция «SQL-консоль для разработчика»,
  сырой SQL там — не баг, а весь смысл файла.
- Разовые ad-hoc SELECT на 1-2 строки для контекста (например, подтягивание `chat_id` для
  квеста в `auction.py:bid()`) — не обязательно каждый такой запрос выносить в repository,
  если он используется ровно в одном месте и не дублирует чужую логику.

**Масштаб работы, если делать полностью:** нужно пройти оставшиеся 36 файлов, для каждого
SQL-блока решить — переносить в существующий repository, заводить новый метод, или оставить
(если это действительно ad-hoc/dev-only). Это НЕ рефакторинг одной функции — это ревизия
SQL-слоя всего приложения. Официально: несколько часов вдумчивой работы + тестирование
каждого затронутого пути (аукцион, брак, VIP, админка).

**Пилот выполнен на связке `zoo.py` (сайт + бот)** — см. разделы выше, оба сведены на общий
`infrastructure/repositories/zoo.py`. Следующий шаг — решить по остальным 36 файлам
(`dev_console/*`/`admin.py` — низкий риск, dev-only; `marriage.py`/`global_admin.py`/
`profile.py` — по важности, там реальные деньги/отношения игроков).

### 🟡 `services/scheduler.py` — два больших фоновых таска

- `duel_and_auction_task()` — 282 строки, `while True: sleep(60); try: ...` с дуэлями,
  дайджестом аукциона и резолвом лотов внутри одного блока.
- `expedition_background_task()` — 189 строк, аналогичная структура для экспедиций.

Это живые cron-подобные фоновые процессы бота — рефакторинг (разбить на `_expire_duels()`,
`_resolve_auction_lots()` и т.п.) улучшит читаемость, но трогает всегда-работающий процесс
на проде. Умеренный риск, умеренная польза. Не делал без подтверждения.

### 🟢 Проверено — НЕ проблема, несмотря на размер

- **`bot/core/database.py` (1296 строк)** — выглядит как «god file», но внутри — 12 чётко
  названных функций `_init_X()` по одной на группу таблиц (`_init_users_and_chats`,
  `_init_inventory_and_pets`, `_init_crypto`, `_init_analytics`, ...), каждая — это просто
  последовательность `CREATE TABLE IF NOT EXISTS`. DDL по природе многословен; держать всю
  схему БД в одном файле — осознанная, распространённая практика (проще искать, гарантирован
  порядок создания таблиц с FK). Не рекомендую дробить.
- **`bot/handlers/identity.py`** (`_render_premium_profile` 287 строк, `_render_full_profile`
  175 строк) — проверено на предмет дублирования с `services/profile_render.py.build_profile_text`
  (202 строки): это НЕ одна и та же функция под разными именами. `identity.py` рендерит
  декорированную карточку для команд «профиль»/«кто я»/«анкета» (с темами, премиум-стилем);
  `services/profile_render.py` используется веб-стороной (превью тем в DevConsole/сайте);
  `bot/handlers/profile.py._build_profile_text` (третье место, 41-я строка) — отдельная,
  более лёгкая команда «инфо»/«досье» для быстрого просмотра чужого профиля без декора.
  Три разных уровня детализации для трёх разных команд — намеренный дизайн, не копипаста.
  `identity.py` уже частично переиспользует общий код (`from services.profile_render import
  _render_premium as _shared_premium`).
- **JS-файлы `app.0*.js`** (402–1060 строк каждый) — уже осознанно разбиты на 9 частей по
  established-конвенции проекта (см. `project_appjs_split.md` в памяти), укладываются в
  разумные рамки на файл. Отдельные функции внутри, кроме уже исправленной `loadGlobalDev`,
  не превышают ~150 строк — это нормально для функций, которые строят большие HTML-блоки.
