# COMMUNITY_CHANNEL_CONCEPT.md — интеграция TG-канала сообщества с ботом

**Статус:** согласовано с пользователем 2026-07-09, готово к плану реализации.
**Канал:** `t.me/predvestnik_official`, chat_id `-1003939897421`. Бот уже добавлен
администратором канала с правом «Публикация сообщений» — подтверждено пользователем,
доп. настройка на стороне Telegram не нужна.

## Зачем

Пользователь ведёт публичный TG-канал сообщества отдельно от игровых чатов бота.
Сейчас туда всё уходит вручную (копипаста апдейтов, ручные анонсы). Три связанные
задачи:
1. Публиковать апдейты бота в канал одной кнопкой вместо копипасты.
2. Автоматически анонсировать крупные игровые ивенты.
3. Рекламировать канал на сайте (мини-аппе) — но не тем, кто уже подписан.

Общая инфраструктура постинга в канал — одна на все три задачи, поэтому это один
проект с четырьмя частями (A — фундамент, B/C/D — фичи поверх).

## A. Фундамент: постинг в канал

Новый хелпер `services/channel_post.py::post_to_channel(text, parse_mode="HTML") -> dict`.
Raw HTTP через Bot API — тот же паттерн, что уже в `services/purge.py::_tg`,
`FastAPI/routers/dev_console/_common.py::_tg_call` (проект уже отправляет сообщения
именно так, без aiogram-объекта, чтобы работать одинаково из процесса бота и FastAPI).

Chat ID канала — новая переменная окружения `COMMUNITY_CHANNEL_ID` с фолбэком на
реальное значение, тем же способом, что уже сделано для `BOT_USERNAME`:
```python
COMMUNITY_CHANNEL_ID = int(os.getenv("COMMUNITY_CHANNEL_ID", "-1003939897421"))
```
Отдельная DB-таблица под один статичный ID не нужна (YAGNI) — id канала меняется
примерно никогда, ровно как токен бота или ID разработчика.

## B. Dev-консоль: «Опубликовать в канал»

Новый под-роутер `FastAPI/routers/dev_console/channel.py` (регистрируется в
`dev_console/__init__.py`, как остальные — `player, vip, system, bp, broadcast, sql,
themes, metrics, promocodes` → добавить `channel`).

Эндпоинты (по образцу `broadcast.py`, который уже даёт текст + тест-отправку себе +
реальную отправку):
- `GET /admin/dev/channel/draft` — возвращает текст последней записи из
  `PLAYER_CHANGELOG.md` (первый блок между первым `## ` и следующим `## `/EOF) как
  черновик для предзаполнения текстового поля.
- `POST /admin/dev/channel/test` — шлёт себе в ЛС с пометкой «🧪 ТЕСТ ПОСТА В КАНАЛ»
  (как `broadcast/test`).
- `POST /admin/dev/channel/publish` — публикует текст в канал через `post_to_channel`.

**Важное уточнение:** отдельного UI для редактирования PLAYER_CHANGELOG.md в
дев-консоли сейчас НЕТ — запись пишется мной как редактором файла в конце сессии.
Значит, поле «Опубликовать в канал» — это НОВЫЙ текстовый блок (не рядом с
существующей формой, а такой же формы, как форма обычной рассылки в `broadcast.py`),
просто предзаполненный черновиком из `/admin/dev/channel/draft`. Кнопка
«📢 Опубликовать в канал», та же логика теста-перед-отправкой, что и у обычной
рассылки. Ничего не публикуется без явного клика пользователя.

## C. Dev-консоль: тумблеры авто-анонсов ивентов

Новая таблица `channel_event_flags` — копия паттерна `system_flags`
(`infrastructure/repositories/system_flags.py`, `bot/core/database.py` строки ~1183):
```sql
CREATE TABLE IF NOT EXISTS channel_event_flags (
    key     TEXT PRIMARY KEY,
    enabled INTEGER NOT NULL DEFAULT 0,   -- ВСЕ дефолты OFF, включаются явно
    label   TEXT DEFAULT NULL
)
```
Дефолтные строки (создаются в `ensure_table`, как у `system_flags`):
| key | label | enabled по умолчанию |
|---|---|---|
| `shadow_trader` | 🌑 Теневой Торговец | **1** (согласовано) |
| `weekend_boost` | ⚡ Ивент выходного буста (старт/конец) | **1** (согласовано) |
| `bp_season` | 🎫 Открытие/закрытие сезона Боевого Пропуска | **1** (согласовано) |
| `clan_war_result` | 🏆 Итог клановой войны | 0 — задел на будущее, хук ещё не найден/не написан, НЕ включать |
| `weekly_top_digest` | 📊 Еженедельный дайджест топ-3 игроков | 0 — задел на будущее, другой механизм (по расписанию, не по ивенту), НЕ включать |

Только первые три реально получают хук в этой итерации. Последние две строки — просто
существуют в таблице как выключенные тумблеры на будущее (сама идея одобрена
пользователем, включение — отдельным разговором), чтобы потом это было включением
флага + маленьким PR, а не новой архитектурой.

Репозиторий `infrastructure/repositories/channel_flags.py` — 1:1 копия сигнатур
`system_flags.py` (`ensure_table`, `get_all`, `is_enabled`, `set_flag`).

**Важно (известная гонка деплоя в этом проекте):** веб-процесс (FastAPI) может
стартовать раньше бота, а полная схема БД создаётся только в `bot/core/database.py::
init_db()`. Поэтому у каждой новой таблицы должен быть свой `ensure_table`,
зарегистрированный ОТДЕЛЬНО в `FastAPI/main.py::lifespan` (см. существующий список
~строка 55-73, где `system_flags.ensure_table` уже так зарегистрирован) — иначе веб
упадёт на «relation does not exist» до первого рестарта бота. Это касается и новой
таблицы `channel_event_flags`, и новых колонок `users.channel_subscribed`/
`channel_checked_at` из части D — нужен свой `ensure_channel_columns()` в этом же списке.

Точки хуков в `services/scheduler.py` — по факту это ДВЕ разные ситуации, не одна:

- **Теневой Торговец** — уже есть готовый дискретный момент «ивент только что создан»:
  `shadow_merchant_task()` (`services/scheduler.py:871-930`), конкретно строки 918-927
  (`create_event` → `bot.send_message(chat_id, prophecy_text(...))`). Просто добавляется
  один доп. вызов `post_to_channel(...)` сразу после, за `if await channel_flags.is_enabled
  (db, "shadow_trader")`. Текст для канала — отдельный, кросс-промо формат («Теневой
  Торговец появился в одном из наших чатов, успей разгадать!»), а не тот же
  замаскированный текст, что в чате (маскировка имеет смысл только внутри игры).

- **Выходной буст и сезон БП — НЕ имеют дискретного триггера вообще.** Это не события,
  а производные состояния, которые пересчитываются на каждый запрос:
  `weekend_boost_active()` (`services/battle_pass.py:550-553`) = «сегодня выходной
  (`_is_weekend()`) И админ вручную выставил `weekend_boost_pct > 0` через `bp_settings`»;
  активный сезон БП — просто строка с `starts_at <= NOW() <= ends_at`
  (`refresh_seasons_cache`, `services/battle_pass.py:30-46`), тоже без единого места
  «сезон открылся». Поэтому для этих двух нужен НЕ один вызов в существующем коде, а
  **новый лёгкий watcher** — одна общая функция вида
  `_watch_state_change(key, current_value)` в scheduler.py: раз в тик (например, раз в
  10 минут, как и Теневой Торговец) сравнивает текущее состояние (`weekend_boost_active()`
  и «id активного сезона БП») с последним увиденным (хранить в памяти процесса, как уже
  сделано для `_db_seasons_cache` — если процесс перезапустится, максимум пропустим один
  анонс, это приемлемо для некритичного уведомления), и на смене состояния постит в
  канал. Честно говоря сложнее одной строки — это отдельная небольшая функция, а не
  просто «добавить вызов», план реализации должен закладывать это как отдельный шаг.

UI тумблеров — в дев-консоли, новая секция «📢 Канал сообщества» рядом с существующим
списком фиче-флагов (`system.py`), тот же визуальный паттерн (список переключателей).

## D. Сайт: баннер профиля со ссылкой на канал

**Кэш подписки** (переиспользует паттерн `services/membership.py::check_chat_members` —
там уже реализована ровно такая же задача «спросить Telegram про реальный статус и
закэшировать», просто про игровые чаты, а не канал):

Новые колонки `users`:
```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS channel_subscribed BOOLEAN DEFAULT FALSE
ALTER TABLE users ADD COLUMN IF NOT EXISTS channel_checked_at TIMESTAMP DEFAULT NULL
```

Новая функция `services/channel_post.py::is_subscribed_cached(db, user_id) -> bool`:
- Если `channel_checked_at` есть и моложе 24ч → вернуть закэшированное значение сразу,
  без обращения к Telegram.
- Если кэш устарел или отсутствует → вернуть закэшированное значение (или `False`,
  если кэша ещё нет), но ЗАПУСТИТЬ фоновую проверку через `getChatMember`
  (`asyncio.create_task`, тот же приём, что `bot/handlers/events.py` использует для
  отложенного приветствия). **Важно:** фоновая задача НЕ должна переиспользовать
  `db`-объект текущего HTTP-запроса — та коннекция из пула закрывается сразу после
  ответа. Задача открывает СВОЁ соединение через `get_pool().acquire()` (тот же приём,
  что в каждой фоновой задаче `services/scheduler.py`) и сама коммитит результат.
  Профильный запрос никогда не ждёт живого обращения к Telegram.

`GET /profile/me` (`FastAPI/routers/profile.py:88`) — добавить поле
`"show_channel_banner": not subscribed` в возвращаемый словарь.

Фронт: `loadProfile()` в `FastAPI/static/app.02.js` (строки ~3-34+) — та же функция,
что уже собирает HTML-блок `pro-main` (`.hero` карточка) из ответа `/profile/me`.
Карточка-баннер добавляется как отдельный блок сразу после `.hero`-карточки внутри
того же `innerHTML`-шаблона, рендерится по условию `d.show_channel_banner` — ссылка
`t.me/predvestnik_official` открывается через обычный `<a href target="_blank">`
(Telegram Mini Apps штатно открывают внешние t.me-ссылки).

## Проверка результата

- `pyflakes` + полный импорт-тест бота/FastAPI (как во всех правках этой сессии).
- `node --check` на тронутые части `app.NN.js` + полная склейка.
- Ручная проверка: тестовая публикация через `/admin/dev/channel/test` доходит в ЛС
  разработчику; реальная публикация через `/admin/dev/channel/publish` — в канал
  (проверяется пользователем вручную, т.к. это внешнее необратимое действие — бот не
  должен публиковать в канал автоматически в рамках тестирования).
- Тумблеры C: включение/выключение отражается в БД и уважается в `scheduler.py`
  (проверить логами на dev/staging при следующем срабатывании соответствующего ивента,
  живых интеграционных тестов с Telegram API в проекте нет).
- Баннер D: Playwright-мок на статик-стенде для верстки карточки (по существующему
  рецепту тестирования фронта), логику кэша подписки — проверить вручную на реальном
  аккаунте (сначала без подписки → баннер виден, подписаться → в течение 24ч/после
  ручного триггера повторной проверки баннер исчезает).
