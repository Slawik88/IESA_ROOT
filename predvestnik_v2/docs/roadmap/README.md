# Конвейер сессий «Предвестника»

Большой план работ владельца разрезан на **25 самостоятельных сессий** (`sessions/S01…S25`). Одна сессия = один кусок работы, который можно довести до конца за один заход. Новая сессия стартует с чистого листа и узнаёт всё из этой папки.
Источник правды о ходе работ — [`STATUS.md`](STATUS.md). Конвейер рассчитан на **одну сессию за раз**: владелец ждёт, пока она закончит, и открывает следующую.

**Приоритет документов.** Для работы по дорожной карте этот README главнее общих правил `CLAUDE.md` (правило 5) и `docs/agent/06-git-and-release.md` в двух местах, потому что владелец решил иначе: (1) **визуальное выкатывается в master только после «ок» владельца**; (2) **деплой на проде проверяет владелец**, из облака это невозможно. Во всём остальном те правила действуют.

## Стартовые промпты (владелец вставляет один из них в новую сессию)

**Обычный** (сессия сама выбирает следующую):
> Ты рабочая сессия проекта «Предвестник» (папка `predvestnik_v2/`). Открой `predvestnik_v2/docs/roadmap/README.md` и действуй по нему: возьми следующую сессию по правилу «Выбор сессии», прочитай её файл и выполни до конца. Журнал обновляй сама.

**Конкретная:** «Выполни сессию S05 из `predvestnik_v2/docs/roadmap/sessions/`. Начни с `predvestnik_v2/docs/roadmap/README.md`.»

**Влить одобренное** (визуальная часть ждёт «ок», а владелец согласовал): «Владелец одобрил S05в: влей её ветку по разделу «Режим: влить одобренное» из `predvestnik_v2/docs/roadmap/README.md`.» Одобрение с замечаниями — тем же сообщением с их списком.

## Что где лежит

| Файл | Зачем |

| `STATUS.md` | Журнал: порядок, таблица сессий, «ждут ок», «ждёт подтверждения прода», «нужны решения владельца», «находки по пути» |

| `findings/*.md` | Результаты исследования кода от 2026-10-27 с путями и строками. Не переисследовать заново, а **сверять с текущим кодом** (строки сдвигаются: ищи по имени функции или `grep`) |
| `seed/nodb-render/` | Заготовка стенда образов без базы данных (для S16) |

## Выбор сессии

1. Прочитать `STATUS.md`: строка «Порядок выполнения» и таблица.
2. Взять **первую в порядке выполнения строку со статусом `не начата`, у которой все зависимости `готово`**. Зависимость в `ждёт ок` не считается выполненной: взять следующую доступную; если доступных нет, сказать владельцу, чего именно ждём. Если выбрана другая сессия, а где-то висит `ждёт ок`, одной строкой напомнить владельцу о ней.
3. Если владелец назвал номер, брать его; при невыполненных зависимостях сделать только независимую часть и честно записать остаток.
4. Проверить, что работа не начата ранее: `git fetch --all -q; git log --all --oneline --grep "Roadmap: SNN"; git branch -r | grep -E "roadmap|claude/"`. Ветка с коммитами этой сессии, а строки в журнале нет, — прошлая сессия оборвалась: продолжить с её ветки.
   Свежие коммиты (меньше суток) в чужой ветке могут принадлежать параллельной сессии: спросить владельца, не трогать молча. Суффикс-строки (`S05б`) от `S05` отличай по суффиксу.

## Протокол старта (по порядку)

1. Выбрать сессию (выше). Статус `в работе` в master **не записывается** (лишний деплой): о незавершённой работе говорит ветка.
2. Прочитать `CLAUDE.md` (корень репозитория) и `predvestnik_v2/AGENTS.md`, дальше по его таблице: `CLEAN_CODE.md`, `AUTONOMOUS_AGENT_POLICY.md`, `AUTONOMOUS_MODE.md` (протокол критика и повторных попыток). Если сессия трогает тексты для игрока — `docs/PLAYER_COPY.md`;
   если видна игроку — `docs/PATCH_NOTES.md`; если визуальная или правит админку — `docs/MINIAPP_DESIGN_RULES.md`; для git — `docs/agent/06-git-and-release.md` в **корне репозитория** (ссылка в нём на несуществующий `predvestnik_v2/PRODUCTION_RELEASE_CHECKLIST.md` устарела: вместо неё разделы «Выкатка» ниже).
3. Прочитать свой файл `sessions/SNN-….md`, `findings/`, на которые он ссылается, «Итог» зависимостей и пункты `OWNER_REQUEST.md`, к которым относится сессия.
4. Сверить журнал с реальностью: `git log --oneline -30 -- predvestnik_v2`; в разделе «Ждёт подтверждения прода» `STATUS.md` есть строки — в первой же реплике коротко спросить владельца, подтвердил ли он прод (не блокироваться, если ответа нет).
5. Поднять окружение: `bash predvestnik_v2/docs/roadmap/env-setup.sh` (из корня репозитория), см. `ENV.md`. Снять **базовую линию**: тесты области на чистом состоянии, результат записать.
6. Создать рабочую ветку (см. «Выкатка»).

**Откуда запускать команды:** все команды в `sessions/` и `findings/` — из `predvestnik_v2/`, кроме `env-setup.sh` (из корня). Пути `FastAPI/…`, `services/…` — от `predvestnik_v2/`. В командах `python` = `$PY`, браузерные — с `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers BOT_TOKEN=1:x PYTHONPATH=.` (точные примеры в `ENV.md`).

## Правила работы

- Код и данные — **только** внутри `predvestnik_v2/`. Сайт IESA (Django) не трогать. Единственное исключение: указатели в корневом `CLAUDE.md`, если факт изменился. Один коммит — один проект.
- Держаться границ своей сессии. Нашлось постороннее (баг, мусор, идея) — строкой в «Находки по пути» в `STATUS.md`, **не чинить**.
- Нужно решение владельца (деньги, цены, данные игроков, правила, видимость чужого контента, новая механика) — строкой в «Нужны решения владельца» и **продолжить с безопасным дефолтом** (функция за выключенным флагом или минимальный вариант). Не гадать и не блокироваться.
- Секреты: ключи, токены, DSN прода не печатать и не коммитить. Чужие незакоммиченные изменения не трогать.
- Большие файлы (`app.NN.js` и др.) правили сразу два ИИ (Claude и Codex): перед правкой смотреть `git log -p` по файлу.
- Тексты для игрока, подсказки, Путеводитель, ответы бота — по `docs/PLAYER_COPY.md`. Новая механика = новая тема Путеводителя **в том же коммите**. Заметное игроку обновление = патч-нот дня и скриншот (`docs/PATCH_NOTES.md`).
- Тиры, цены и id образов не менять. Figma не используется: внешний вид согласуется через стенд «до/после» (S16) или скриншоты.
- Параллельные сессии допустимы только из разных блоков с непересекающимися файлами; `STATUS.md` правят построчно, при конфликте — `git fetch` + `git rebase origin/master`.

## Выкатка (master = прод, деплой автоматический, каждый пуш в master перезапускает бота и сайт)

**Ветки.** Среда может назначить сессии ветку `claude/…`: работать в ней. Иначе — `feat/roadmap-SNN-<тема>`. Любую ветку с работой **пушить в origin** (резервная копия и вход для режима «влить»). В master — только fast-forward:
`git fetch origin master && git rebase origin/master && git push origin HEAD:master` (без `--force`, после повторных проверок). Если пуш в master запрещён правами или средой — **не обходить**: оставить всё в ветке, сообщить владельцу, статус `ждёт ок`.

**Один пуш в master на единицу работы.** Код, документы, журнал (`STATUS.md`, «Итог» в файле сессии, `ENV.md`, `findings/`) и релизная запись попадают в **один коммит-набор и один пуш**, который делается **после** всех проверок. Журнал пишется заранее с учётом того, что известно до пуша
(в том числе «прод из облака не проверен»), чтобы после пуша править было нечего. Хэши коммитов в журнал не вписывать: сессию находят по `Roadmap: SNN` (`git log --all --grep`).

**Смешанная сессия** (серверная часть + экран, например S05, S10): серверная часть, не меняющая вид и **совместимая со старым клиентом** (старый экран продолжает работать), выкатывается своим пушем; сессия получает `готово`. Визуальная часть оформляется **отдельной строкой `SNNв`** со статусом `ждёт ок` и веткой. Тексты сообщений бота, которые видит игрок, относятся к визуальной части.
Остаток, не уместившийся в сессию, — строка `SNNб` (статус `не начата`). Обе строки вписываются в «Порядок выполнения» сразу после своей сессии.

| Что | Куда | Когда |
|---|---|---|
| Не-визуальный код (сервер, бот без изменения видимых текстов, тесты, измерения), документы, журнал | master | после проверок сессии, одним пушем |
| Визуальный код (экраны, меню, образы, тексты на экранах и в сообщениях бота, вид админки) | ветка | в master только после «ок» владельца |
| Код, выкатываемый выключенным (`включение`) | master | выключатель по умолчанию off; включает владелец |

Служебный блок, добавляющий данные в существующую раскладку админки без смены вида (например, «Здоровье» в S01), «ок» не требует.

**Снимки для «ок».** Публиковать приватным Artifact (если инструмент доступен); иначе небольшие WebP (≤150 КБ) в `docs/roadmap/shots/SNN/` **только на ветке** (при вливании в master удалить папку, если владелец не попросил оставить). Ссылку или путь и ветку записать в «Ждут твоего ок» в `STATUS.md`.

**Проверка прода — за владельцем** (адреса прода из облака недоступны: HTTP 000; `tools/verify_production_http.py` из сессии не запускать). Поэтому **до пуша** сессия: прогоняет все локальные проверки; пишет в `STATUS.md` строку в «Ждёт подтверждения прода» («не проверено из облака»); в «Итог» и релизную запись — что проверено локально, а что нет.
**После пуша** сообщает владельцу три пункта проверки: в панели DigitalOcean деплой `Healthy`; `/api/health` и `/api/ready` отвечают; Mini App открывается. Сломалось — откат (`git revert` + пуш) по просьбе владельца. Строка в «Ждёт подтверждения прода» живёт, пока владелец не подтвердит; её закрывает ближайшая сессия, которой он подтвердил («подтверждено <дата>»),
и не дольше двух сессий: затем она переносится в «Находки по пути» как «прод не подтверждён».

**Определения, на которые ссылаются файлы сессий:**
- **PG-гейт:** все `*_pg.py` тесты затронутой области и новые PG-тесты на новые таблицы, индексы, запросы проходят на локальной PostgreSQL (`ENV.md`); схема идемпотентна (повторный `init_db` ничего не меняет); тесты, требующие пустую базу, запускаются на свежей (`env-setup.sh --fresh-db ИМЯ`);
  разрушающих DDL нет, индексы — только `CREATE INDEX CONCURRENTLY IF NOT EXISTS` вне транзакции.
- **Независимый read-only аудит:** отдельный субагент (только чтение: тип Explore или Plan) получает дифф и цель сессии и ищет регрессии, гонки, утечки скрытых данных, нарушения правил проекта (`AUTONOMOUS_MODE.md`, п. 1.4). Сессия исправляет найденное или аргументированно отклоняет; вердикт записывается в «Итог».
  Требуется там, где так сказано в файле сессии (деньги, права, приватность, пул и блокировки, миграции).
- **Стенд «до/после»:** снимки одного экрана или образа на базовой ревизии и на ветке (S16 создаёт инструмент; до него — `ui_smoke.py --shots` и `tools/admin_stand.py`).

**Релизный журнал проекта.** По `AUTONOMOUS_AGENT_POLICY.md` (§4) история релизов ведётся в `docs/audits/AUTONOMOUS_RELEASE_BACKLOG.md`. Каждая выкатка в master получает там короткую запись: идентификатор `ROADMAP-SNN`, что выпущено, как проверено, что не проверено (оговорка в политике есть).
Новых файлов в документации и релизном журнале под задачи не плодить (вне `docs/roadmap/`); код, тесты, скрипты, патч-ноуты и снимки — по правилам проекта.

## Протокол финиша (обязательно)

1. Все проверки из файла сессии зелёные. Красное — не коммитить «на потом».
2. Дописать в файле сессии раздел **«Итог»**: что сделано (коммиты находятся по `git log --all --grep "Roadmap: SNN"`), что проверено и как, подраздел **«Остаток»** (что не сделано и почему), что обнаружено.
3. Обновить строку сессии в `STATUS.md`: статус, дата, ветка (если есть), «сделано» и «осталось» по одной строке; добавить строки `SNNб`/`SNNв`, если они нужны (ссылка на раздел «Итог» файла сессии); вписать их в «Порядок выполнения».
4. Если из-за сессии изменился факт, описанный в документации, — обновить документ в том же коммите.
5. Коммит-сообщения по правилам репозитория: `тип(predvestnik): суть` (`feat`, `fix`, `docs`, `test`, `chore`), в конце отдельной строкой `Roadmap: SNN`, затем атрибуция, которую требует среда.
6. Релизная запись `ROADMAP-SNN`, затем **один** пуш по разделу «Выкатка». Кратко отчитаться владельцу по-русски: что сделано, что дальше, нужны ли от него «ок» или данные, три пункта проверки прода.

## Статусы и особые случаи

`не начата` → `ждёт ок` (визуал на ветке) → `готово`. Статуса `в работе` и `частично` в master нет: недоделанное уходит в строку `SNNб`, визуальное — в `SNNв`.
Колонка «Ок» в `STATUS.md`: `нет`; `да` (владелец смотрит снимки до выкатки в master); `включение` (код выкатывается выключенным, владелец включает сам по образцу); `да (экран)`/`да (интерфейс)` (серверная часть без «ок», экранная — строкой `SNNв` с «ок»).

**Режим «влить одобренное»** (по строке `SNNв` или любой `ждёт ок`):
1. `git fetch --all -q`; ветку взять из строки «Ждут твоего ок» в `STATUS.md` (запасной поиск: `git log --all --grep "Roadmap: SNN"`); прочитать «Итог» и замечания владельца.
2. Если замечаний нет — перейти к п. 4. Если есть — выполнить их, пересобрать снимки. Если замечания **меняют вид**, запушить в ветку, оставить `ждёт ок`, показать снимки и ждать ответа. Если владелец явно написал «после правок влей без повторного показа» — продолжить.
3. `git rebase origin/master`; если за время ожидания master изменился так, что снимки уже не отражают результат, пересобрать снимки и показать владельцу ещё раз.
4. Повторить проверки сессии; обновить журнал (`ждёт ок` → `готово`, убрать строку из «Ждут ок», добавить в «Ждёт подтверждения прода»), «Итог», релизную запись `ROADMAP-SNN` — коммитом **перед** пушем; один пуш `HEAD:master`.
5. После пуша — три пункта проверки прода владельцу.

**Если владелец не ответил на «ок»:** сессия заканчивается статусом `ждёт ок` с названием ветки и тем, что посмотреть; зависимые сессии ждут. Владелец вернётся промптом «влить одобренное».

## Общие проверки (сверять с файлом сессии)

- Сервер/бот: `tools/test_<имя>.py`; PG-тесты с `--dsn` (`ENV.md`).
- Экран: `tools/ui_smoke.py --only <экран> --widths 320,390,430`, при движении `--perf --device mid`. **Экран должен входить в `SCREENS` (`tools/ui_smoke_checks.py`)**, иначе `--only` отработает на 0 сценариях и «пройдёт» вхолостую: проверять, что выполнен ≥1 сценарий. Админка: `tools/admin_stand.py --tabs <вкладки>` (снимки на фикстурах без входа, 320/390/430, две темы).
- Тексты игроку: `tools/test_player_copy_contract.py`, `tools/test_guide_navigation.js`.
- Патч-ноты: `tools/audit_release_whatsnew.py`, `tools/test_patch_notes_contract.py`, `tools/test_whatsnew_v3_contract.py`.
- Перед любым пушем в master: нет секретов, нет посторонних файлов, ветка на актуальном `origin/master`.
