## Цель

Убрать лишнюю работу, которая вызывает «микрофризы»: DDL на каждый запрос, топы без кэша и индекса, тяжёлый `/profile/me`, частые heartbeat, лишние UPSERT на каждое сообщение. Контекст: `findings/A1-stability-performance.md`, «Топ-10 источников лагов», пункты 1, 4, 6, 7, 8, 10.

## Границы

**Делаем (в порядке «эффект/усилие»):**
1. **`season_pass.ensure_tables` на каждый запрос** (`infrastructure/repositories/season_pass.py:7-37`, роутер `:19,26`): флаг готовности схемы, как у остальных репозиториев (`_schema_ready`). Тест, что `CREATE TABLE IF NOT EXISTS` не выполняется повторно.
2. **Топы** (`services/leaderboards_v1.py:142-144,185-186`, `infrastructure/repositories/stats.py:61-75,140-190`): серверный кэш 30–60 с на ключ (чат, период, страница) с инвалидацией по времени; индекс `daily_user_stats(date,user_id)`;
   на клиенте не сбрасывать `_v3TopCache` на каждое WS-событие `activity_changed` (`FastAPI/static/app.01.js:300-304`): склейка событий с паузой 5–10 с.
3. **`/profile/me`** (`FastAPI/routers/profile.py:456-600`): посчитать число запросов и сгруппировать независимые в один/параллельные на **одном** соединении через короткие `gather`-безопасные блоки (asyncpg одно соединение — последовательно;
   поэтому объединять SQL), кэш 5–10 с с инвалидацией после мутаций, `ETag`. Аватар уже отдельный после S02 (если нет — сделать здесь).
4. **Heartbeat** `/analytics/tab-duration` (`app.01.js:704-707`, `FastAPI/deps.py:94,96`): интервал 15 → 60 с, накопление в памяти и сброс пачкой; `sendBeacon` при закрытии.
5. **`record_message`** (`bot/chat/tracking.py:96-135`, ≥7 UPSERT на сообщение + 3 SELECT gate-проверок): буфер счётчиков в памяти с периодическим сбросом и `ON CONFLICT … WHERE … IS DISTINCT FROM`; потеря буфера при рестарте допустима только для вторичных
   счётчиков, **а не для денег/достижений**: сначала составить список того, что считается, и согласовать разделение в журнале. Если риск потери данных неясен — оставить как есть и записать.
6. **Админский поиск и журнал** (`services/admin_people.py:97-100,256-262,350,408-411`): триграммный GIN (`pg_trgm`) на username/name/tag; предрасчёт last-seen и суммы сообщений (есть `presence_v1`); индексы `moderation_logs(chat_id,user_id,action,created_at)`,
   `(user_id)`, `(created_at)` (индекс по `created_at::timestamptz` заменить корректным типом).
7. **`loadPurgeEntry`** (определение `FastAPI/static/app.07.js:54`, вызов `app.01.js:650`): не считать `COUNT` по всем чатам при каждом открытии «Ещё» (кэш/флаг «есть доступ»). Согласовать с S05, чтобы не делать дважды.

**Миграции и индексы:** только `CREATE INDEX CONCURRENTLY IF NOT EXISTS` вне транзакции, по одному, с `lock_timeout`, в фоновой задаче старта с логированием и пропуском при отказе; **никакого удаления данных и переименований**.
Расширение `pg_trgm` — проверить права на управляемой БД DigitalOcean; нет прав → записать вопрос владельцу и обойтись без него.

**Не делаем:** смену архитектуры пула (S03), экран «Чистка» (S05), ленивые образы (S06).

Что сделано, по пунктам:
1. **Сезонный пропуск:** `ensure_tables` сначала проверяет, что таблицы есть (`to_regclass`), DDL только на пустой базе.
2. **Топы:** рейтинги и личные места — в памяти процесса **45 с** на ключ (границы периода, чат, размер страницы; `services/leaderboards_v1.py`, `core/ttl_cache.py`); имена, образы и регалии видимых строк читаются свежими. Индекс `daily_user_stats (date, user_id)` (без `INCLUDE (message_count)`: столбец растёт с каждым сообщением, и индекс с ним лишил бы эти обновления дешёвой записи «на месте»; по замечанию аудита, скорость та же). Клиент перечитывает топ по событию «новое сообщение» не чаще раза в 10 с (первое — сразу, пачка — одним запросом в конце паузы).
3. **`/profile/me`:** снимок на **8 с** (`FastAPI/profile_snapshot.py`) с `ETag` и ответом 304. Снимок забывается после любого не-GET запроса игрока (в `get_db`, после записи) и при любом живом событии о нём (`notify`: баланс, данные, активность). Чтение, начатое до записи, кладёт результат под старое «поколение», которое больше не читается. Три запроса результатов игр объединены в один. Аватар уже отдельно (S02).
4. **«Пульс» вкладок:** клиент копит секунды и шлёт раз в минуту и при сворачивании (`keepalive`), а не каждые 15 с; сервер складывает в памяти и пишет одной командой раз в минуту (`services/tab_time.py`), запрос «пульса» не берёт соединение. Индекс `site_analytics (user_id, session_id, tab, visited_at)`: раньше каждая запись искала строку визита перебором таблицы.
5. **Запись на каждое сообщение** (`bot/chat/tracking.py`). Список того, что пишется: `users` (ник, имя), история ников (только при смене), `chat_settings` (название чата, «бот в чате»), `user_chat_stats` (+1 всего, время последнего сообщения), тег участника (только при смене), `daily_user_stats` (+1 за день), `daily_login` (стрик).
   - **Найдено и исправлено:** строка игрока перезаписывалась тем же ником на каждое сообщение, а это будило триггер `users_live_profile_v1` («профиль изменился»), и открытое приложение автора перечитывало профиль на каждое его сообщение. Теперь `users` и `chat_settings` переписываются только при реальной смене (`ON CONFLICT … WHERE … IS DISTINCT FROM`).
   - **Буфер счётчиков не делали (решение сессии по правилу «риск неясен — оставить»):** счётчики сообщений питают регалии, достижения, стрик и «Чистку»; потеря при перезапуске затронула бы их.
6. **Админка:** индексы `moderation_logs (chat_id, user_id, action, created_at)`, `(user_id)`, `(created_at)`; журнал сравнивает столбец `TIMESTAMP` с приведённой границей, а не приводит столбец (иначе индекс не работает); поиск по ID и имени считает сумму сообщений только найденных игроков (`LATERAL`), список «недавние» оставлен прежним (одним проходом быстрее). Триграммные индексы поиска строятся, только если `pg_trgm` уже установлен.
7. **Вход в «Чистку» в «Ещё»:** `GET /purge-v1/access` (`EXISTS` по тому же правилу, что список), клиент помнит «нет» 10 минут. Список и сама «Чистка» не тронуты — S05 может опираться на `moderation_chats.has_purge_access`.
8. **Сверх плана:** соединения Предвестника открываются с `jit=off`. На синтетике JIT компилировал план ~200 мс на запросах с большой оценкой строк при ~30 мс работы (поиск в админке 220 → 31 мс только от этого). На сайт IESA не влияет.

**Индексы на проде** строит фоновая задача после старта (`infrastructure/db_indexes.py`, после блокировки экземпляра): `CREATE INDEX CONCURRENTLY IF NOT EXISTS` по одному, на своём прямом соединении (не слот пула), `lock_timeout` 60 с, без `statement_timeout`; ошибка — запись в лог и повтор при следующем старте; брошенный деплоем INVALID-индекс удаляется и строится заново. Порядок: `idx_daily_stats_date_user`, `idx_mod_chat_user_action_at`, `idx_mod_user`, `idx_mod_created_at`, `idx_sa_user_session` (+3 триграммных при `pg_trgm`). На синтетике 1 млн строк — 1,0 с, остальные доли секунды; запись в таблицы во время постройки не ждёт (тест). Итог видно в логе строкой `db indexes: …`. Отдельного окна «вне часов пик» не нужно; если таблицы на проде в десятки раз больше — всё равно не блокирует запись.

**Изменение поведения:** топ сообщений обновляется с задержкой до 45 с (раньше мгновенно); свой профиль после действий в боте, о которых нет живого события, может отставать до 8 с; секунды на вкладках пишутся раз в минуту (при перезапуске теряется не больше минуты этой статистики).
