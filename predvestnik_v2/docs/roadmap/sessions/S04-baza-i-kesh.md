## Цель

Убрать лишнюю работу, которая вызывает «микрофризы»: DDL на каждый запрос, топы без кэша и индекса, тяжёлый `/profile/me`, частые heartbeat, лишние UPSERT на каждое сообщение. Контекст: `findings/A1-stability-performance.md`, «Топ-10 источников лагов», пункты 1, 4, 6, 7, 8, 10.

## Границы

**Делаем (в порядке «эффект/усилие»):**
1. **`season_pass.ensure_tables` на каждый запрос** (`infrastructure/repositories/season_pass.py:7-37`, роутер `:19,26`): флаг готовности схемы, как у остальных репозиториев (`_schema_ready`). Тест, что `CREATE TABLE IF NOT EXISTS` не выполняется повторно.
2. **Топы** (`services/leaderboards_v1.py:142-144,185-186`, `infrastructure/repositories/stats.py:61-75,140-190`): серверный кэш 30–60 с на ключ (чат, период, страница) с инвалидацией по времени; индекс `daily_user_stats(date,user_id)`;
   на клиенте не сбрасывать `_v3TopCache` на каждое WS-событие `activity_changed` (`FastAPI/static/app.01.js:300-304`): склейка событий с паузой 5–10 с.
3. **`/profile/me`** (`FastAPI/routers/profile.py:456-600`): посчитать число запросов и сгруппировать независимые в один/параллельные на **одном** соединении через короткие `gather`-безопасные блоки (asyncpg одно соединение — последовательно;
   поэтому объединять SQL), кэш 5–10 с с инвалидацией после мутаций, `ETag`. Аватар уже отдельный после S02 (если нет — сделать здесь).
4. **Heartbeat** `/analytics/tab-duration` (`app.01.js:704-707`, `FastAPI/deps.py:94,96`): интервал 15 → 60 с, накопление в памяти и сброс пачкой; `sendBeacon` при закрытии.
5. **`record_message`** (`bot/chat/tracking.py:96-135`, ≥7 UPSERT на сообщение + 3 SELECT gate-проверок): буфер счётчиков в памяти с периодическим сбросом и `ON CONFLICT … WHERE … IS DISTINCT FROM`; потеря буфера при рестарте допустима только для вторичных
   счётчиков, **а не для денег/достижений**: сначала составить список того, что считается, и согласовать разделение в журнале. Если риск потери данных неясен — оставить как есть и записать.
6. **Админский поиск и журнал** (`services/admin_people.py:97-100,256-262,350,408-411`): триграммный GIN (`pg_trgm`) на username/name/tag; предрасчёт last-seen и суммы сообщений (есть `presence_v1`); индексы `moderation_logs(chat_id,user_id,action,created_at)`,
   `(user_id)`, `(created_at)` (индекс по `created_at::timestamptz` заменить корректным типом).
7. **`loadPurgeEntry`** (`app.01.js:649`, `app.07.js:54`): не считать `COUNT` по всем чатам при каждом открытии «Ещё» (кэш/флаг «есть доступ»). Согласовать с S05, чтобы не делать дважды.

**Миграции и индексы:** только `CREATE INDEX CONCURRENTLY IF NOT EXISTS` вне транзакции, по одному, с `lock_timeout`, в фоновой задаче старта с логированием и пропуском при отказе; **никакого удаления данных и переименований**.
Расширение `pg_trgm` — проверить права на управляемой БД DigitalOcean; нет прав → записать вопрос владельцу и обойтись без него.

**Не делаем:** смену архитектуры пула (S03), экран «Чистка» (S05), ленивые образы (S06).

## Критерии готовности

- Для каждого пункта в журнале есть «до/после» (число запросов или время `EXPLAIN` на синтетике).
- `GET /season-pass/me` не выполняет DDL (тест).
- Бюджет запросов `/profile/me` зафиксирован тестом.
- Индексы создаются без блокировки записи (проверка `CONCURRENTLY`, отсутствие длинных блокировок в локальном прогоне).
- Вторичные счётчики и денежные пути не потеряны (тесты экономики/достижений зелёные).
