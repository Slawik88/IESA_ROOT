# S05 · «Чистка» с нуля: фоновая очередь, прогресс, без лагов

**Блок A** · **Зависит от:** S03 · **Смешанная сессия.** Единица 1 — серверная часть (воркер, API, кэш, индексы), **совместимая со старым экраном `app.07.js`**: выкатывается в master одним пушем после проверок, сессия получает `готово`. > **Промпт:** Выполни сессию S05 из `predvestnik_v2/docs/roadmap/sessions/S05-chistka.md`. Начни с протокола старта из `predvestnik_v2/docs/roadmap/README.md`.

## Цель

«Чистка» (чистка неактивных участников чата по норме сообщений) долго грузится, лагает, а у двух админов, смотрящих её одновременно, показывается с огромным пингом. Перестроить её на фоновую очередь с прогрессом, чтобы она не мешала остальному сайту и боту.
Контекст: `findings/A2-admin-and-purge.md` («Чистка: где и почему лагает», «Архитектурное исправление»).

## Границы

**Делаем:**
1. **Фоновый воркер** по образцу `services/broadcasts.py:546-640` (durable-цели в БД, дозапуск после рестарта, порционная отправка). Досье больше не через `asyncio.create_task` без ссылки (`bot/chat/purge.py:353`, `FastAPI/routers/purge_v1.py:93`); `unsent_targets()`
   (`infrastructure/repositories/purge_sessions.py:131`) начинает использоваться при старте. Деплой не должен терять рассылку досье.
2. **Запуск как задание.** `start` отдаёт 202 + id задания, подсчёт нарушителей (`find_violators` в `bot/chat/purge.py:145`) идёт в воркере; не в HTTP-запросе под `statement_timeout` 30 с.
3. **Прогресс.** `counts` «отправлено N из M», ревизия/ETag; WS-событие `data_changed{scope:'purge'}` через уже существующую шину `notify` вместо поллинга каждые 2 с (`FastAPI/static/app.07.js:34`); поллинг 10–15 с только запасной.
4. **Telegram-вызовы.** Кэш `getChatMember` 30–60 с на пару (чат, актёр); для решения один `getChatMember(target)` + кэш прав бота (`bot/chat/purge.py:490,506,508,530`); удаление сообщений в закрытом чате пачками до 100 (`bot.delete_messages`), буфер 300–500 мс (`purge.py:435-456`).
   Троттлер уже исправлен в S03: проверить, что `purge` его не обходит.
5. **SQL.** Индексы `moderation_logs` (если не сделаны в S04), подзапросы в `find_violators` свести к одному проходу; `loadPurgeEntry` (определение `FastAPI/static/app.07.js:54`, вызов `app.01.js:650`) не считает `COUNT` по всем чатам при каждом открытии «Ещё».
6. **Экран «Чистка» в Mini App** (`FastAPI/static/app.07.js:17-205`): состояния «готовлю список», «отправляю досье N из M», «готово», ошибки с «Повторить», работающая кнопка «Назад»; под правила дизайна `docs/MINIAPP_DESIGN_RULES.md`. **Админка:** переход «Чистка ›» из карточки чата не должен
   выбрасывать из админки (`FastAPI/static/bot-admin/admin.js`: искать `startapp=purge_`): здесь только подготовить серверный интерфейс, экранную часть берёт S10.
7. **Нагрузочная проверка «двое смотрят одновременно»** (скрипт): два клиента поллят/слушают WS при идущем задании на чат с N участниками, задержка ответов не растёт.

**Совместимость.** Пока экран не влит, старый `app.07.js` в master обязан работать с новым API: старые эндпоинты и формат ответов остаются (новое поведение подключается по параметру/версии), удаляются только после слияния `S05в`.
**Права.** Кэш `getChatMember` и прав бота (30–60 с) нужен для просмотра и статуса; **перед необратимой санкцией (кик, бан, мут) права проверяются заново без кэша**.

**Не делаем:** смену правил самой чистки (кого считать нарушителем, нормы), права доступа, внешний вид админки.

## Критерии готовности

- Замер «до/после» в журнале: время старта задания, время ответа при двух одновременных клиентах.
- Рестарт посреди рассылки досье не теряет цели (тест).
- Поллинг не создаёт Telegram-вызовов (тест: ноль `getChatMember` на запрос статуса).
- Нет соединения БД, удерживаемого на время вызова Telegram (тест как `test_avatar_pool_pg.py`).
- Экран проходит `ui_smoke` на 320/390/430 (≥1 сценарий выполнен), правила дизайна соблюдены; патч-нот и тема Путеводителя («Чистка» для админов чатов) добавлены вместе с экраном (единица 2).
- Старый экран работает с новым API до слияния единицы 2 (тест совместимости).
