# S02 · Вход и аватарки: надёжность авторизации и фото

**Блок A** · **Зависит от:** S01 (нужны причины 401 и телеметрия, чтобы проверить результат) · **Нужен «ок»:** нет · Выкатка в master после проверок.

> **Промпт:** Выполни сессию S02 из `predvestnik_v2/docs/roadmap/sessions/S02-vhod-i-avatarki.md`. Начни с протокола старта из `predvestnik_v2/docs/roadmap/README.md`.

## Цель

Игроки жалуются на ошибки авторизации и не грузящиеся аватарки. Сделать вход самовосстанавливающимся, а загрузку фото предсказуемой, **не меняя правило «аватарки в Mini App показываются только VIP»**
(`FastAPI/routers/profile.py:204-207,241`). Контекст: `findings/A1-stability-performance.md`, разделы «Вход» и «Аватарки».

## Границы

**Делаем (вход):**
1. initData старше 24 ч (`FastAPI/auth.py:53`) не должен приводить к оверлею Login Widget внутри Telegram. Варианты по безопасности: сервер отвечает машинно-читаемой причиной `stale_auth_date`; клиент в Telegram
   запрашивает свежий initData у SDK (`Telegram.WebApp.initData` пересчитывается при каждом запуске; если SDK отдаёт тот же устаревший — показать понятный экран «Закрой и открой Предвестник заново» с кнопкой
   `Telegram.WebApp.close()`/перезапуска вместо Login Widget). Срок жизни initData не продлевать без отдельного решения: это безопасность.
2. `INIT_DATA` фиксируется один раз (`FastAPI/static/app.01.js:35`): перечитывать при повторном входе.
3. Загрузка `telegram-web-app.js` (`FastAPI/static/index.html:18`): таймаут, повторная загрузка с запасного адреса/локальной копии, события в телеметрию S01; без SDK не показывать «вход не удался», а объяснять.
4. `api()` (`app.01.js:149-168`): таймаут (по умолчанию 15 с), безопасные ретраи **только для идемпотентных GET**, понятное сообщение при сетевой ошибке, различение 401/403/5xx; на мутациях никаких автоповторов.
5. initData не класть в URL WebSocket (`app.01.js:230`, `FastAPI/main.py:349`): передавать первым сообщением или в заголовке подпротокола.

**Делаем (аватарки):**
6. Общий долгоживущий `httpx.AsyncClient` вместо нового на каждую загрузку (`FastAPI/routers/profile.py:99-136`), раздельные таймауты на шаги, один общий бюджет.
7. Кэш, переживающий деплой: хранить уменьшенное фото (например 128 px WebP) в БД (по образцу существующих таблиц; идемпотентная схема) с ключом `file_unique_id`, отдавать **отдельным запросом** `/profile/avatar/{id}` с `ETag` и `Cache-Control`, а не data-URI внутри JSON `/profile/me`, топов и карточек. Правило VIP-видимости сохраняется на стороне сервера.
   **Админские аватарки:** сейчас они живут только в памяти процесса (`services/admin_avatars.py`: `_CACHE`, 6 ч / 30 мин) и пропадают при деплое; перевести на тот же кэш в БД. Правило «**админка видит аватарки всех игроков, не только VIP**» сохраняется (это отдельный маршрут `/bot-admin/avatar/{uid}`, VIP-гейта в нём нет): закрепить тестом.
8. Повтор при `null` на `/me` и в топах (`profile.py:570`, `FastAPI/routers/leaderboards.py`): **только когда фото ожидается** (игрок VIP, а фото ещё грузится): сервер отдаёт явный признак `avatar_state` (`ready` / `loading` / `absent` / `vip_only`), клиент перезапрашивает при `loading` с нарастающей паузой, ограниченное число раз; при `vip_only` и `absent` повторов нет (это норма, не ошибка); шапка не «один раз за сессию».
9. Понятная заглушка (инициал или созвездие), без мерцания; `onerror` везде.

**Не делаем:** смену правила VIP, продление срока initData, новые механики; сервер/БД оптимизации вне аватарок (S03/S04).

## Критерии готовности

- Новые тесты красные до правок, зелёные после; существующие `test_avatar_*` зелёные.
- Сценарий «устаревший initData» не показывает Login Widget внутри Telegram.
- Аватарка VIP не теряется после деплоя (проверка: перезапуск процесса в тесте, фото отдаётся из БД без запроса к Telegram).
- Правило «не-VIP получает `avatar=null`» не изменено (тест); **тест: не-VIP игрок получает фото в админке**; **тест: новый маршрут `/profile/avatar/{id}` не отдаёт фото не-VIP по прямому URL** (проверка VIP на сервере при каждом запросе) (`/bot-admin/avatar/{uid}`); для `vip_only` и `absent` клиент не делает повторных запросов (тест).

## Итог (заполняет сессия)

**2026-10-28, готово** (коммиты: `git log --all --grep "Roadmap: S02"`, экран — `Roadmap: S02v`). Выкачено в master одним пушем вместе с S02v: владелец дал «ок» на снимки «до/после»

**Вход.** 401 несёт заголовок `X-Auth-Reason` (категория из `services/ops_health.AUTH_REASONS`, не сам пропуск); срок initData не продлевался. Клиент (`static/app.01.js`): `INIT_DATA` читается
заново при возвращении в приложение и перед одним повтором GET после 401; без SDK — из подписанного хэша запуска (`tgWebAppData`). Если telegram.org не отдал SDK, `index.html` грузит копию
`static/vendor/telegram-web-app.js` (из `@twa-dev/sdk` 8.0.2; в «Здоровье» видно как `sdk_missing` «local copy loaded»). `api()`: таймаут 15 с (изменения — 30 с), повтор только GET
(обрыв, 502/503/504), после таймаута не повторяет; понятный текст вместо «TypeError». Один обработчик отказа `handleAuthRefusal` (api, «Чистка», казино): внутри Telegram — экран «Закрой
Предвестник и открой снова» с кнопкой закрытия (S02v), в браузере — прежний виджет. WebSocket: пропуск первым сообщением `{"type":"auth",…}`, ожидание 5 с, не больше 300 ждущих сокетов;
`?init=`/`?token=` пока принимаются для клиентов, открытых до выпуска.

**Аватарки.** Эндпоинт фото — `GET /profile/avatar/{profile_ref}?v=<версия>` (WebP 128 px, ETag/304, кэш браузера 5 мин); VIP проверяется на каждом запросе, не-VIP и удалённые — 404.
JSON (`/profile/me`, `/profile/avatar`, публичная карточка, топы) несёт этот адрес и `avatar_state`: `ready` / `loading` (клиент переспрашивает с паузой 2–5–10 с) / `absent` и `vip_only`
(повторов нет). Кэш — таблица `avatar_photos` (`infrastructure/repositories/avatar_photos.py`), переживает деплой; очищается сам: фото перепроверяется раз в сутки (один запрос к Bot API,
скачивание только при новой версии), «фото нет» — через 30 мин, после сбоя Telegram пауза 60 с, известное фото при сбое не стирается. Telegram — общий `httpx.AsyncClient`
(`infrastructure/telegram_photo.py`), бюджет 8 с на обновление, соединение с базой на время Telegram не держится. Админка (`/bot-admin/avatar/{uid}`) берёт фото всех игроков из того же кэша
без правила VIP (тест `test_avatar_pool_pg`).

**Причина (по коду; цифр с прода ещё нет).** Шаг 5 отложен: телеметрия S01 только начала копиться. Гипотезы, которые закрыты: устаревший initData (24 ч) давал виджет входа внутри
Telegram; незагрузившийся SDK давал пустой initData; фото жили в памяти процесса и пропадали после каждого деплоя, при промахе клиент получал `null` и не переспрашивал.
Через 3–5 дней сверить в «Здоровье» → «Почему не пустило» долю `stale_auth_date` и `no_header`, и `sdk_missing` по сообщениям.

**Проверено.** Новые тесты красные на коде до S02 и зелёные после: `test_auth_recovery_browser` (копия SDK, вход без SDK, причина и экран «открой заново», повтор только GET, пропуск сокета
не в адресе), `test_ws_account_gates_pg` (первое сообщение), `test_avatar_pool_pg` (пул, перезапуск без запроса к Telegram, VIP на прямом адресе, админка видит не-VIP, повторная схема),
`test_avatar_recovery`, `test_avatar_signed_photo`, `test_avatar_recovery_ui.js`, `test_leaderboard_avatar_ui.js`, `test_bot_admin_avatars`. Плюс соседние тесты профиля, топов, Ритма, Сапёра,
жалоб, контракты патч-нотов и текстов, `ui_smoke --only profile,top` 320/390/430 (в файле сессии указано `tops`, такого экрана нет — правильно `top`; предупреждения на «top» те же, что на базе).
Независимый read-only аудит: auth-обходов нет; одно серьёзное (фото, видимое только по подписанной ссылке Mini App, стиралось фоновым обновлением) и мелкие (ожидание сокета, сбой хранилища
