# Autonomous Release Backlog

> Единственный оперативный источник следующей автономной работы. Исторические
> спецификации и аудиты остаются доказательствами и контрактами, но не очередью.

## Stop-ship

Открытые stop-ship: **LCB-001** и **LCB-002**. Они блокируют retirement старого
контента и production-релиз до безопасного решения по данным и компенсации.

- [ ] **LCB-002 · Компенсация за retirement контента.** Перед production-удалением
  старого контента нужен versioned, идемпотентный и проверяемый план компенсации
  владельцев удаляемых сущностей. Соотношение не обязано быть 1:1, но каждая
  категория, формула, целевая новая механика/валюта, ledger-запись, dry-run,
  повторный запуск и обратимый audit trail должны быть утверждены владельцем.
  Без этого удаление legacy-данных и production-релиз заблокированы.

  **Завершена безопасная подволна инвентаризации (2026-08-24):** добавлен
  `tools/audit_retirement_compensation.py` — отдельный aggregate-only отчёт
  только для явного loopback DSN восстановленного локального snapshot. Он не
  читает `.env`/`DATABASE_URL`, отклоняет remote DSN, использует `REPEATABLE
  READ READ ONLY` и не содержит формулы, payout, ledger write или миграцию.
  Инвентарь fail-closed отмечает отсутствующие таблицы/колонки, а не считает их
  нулём; охватывает юниты и partial shards, unfinished battles, pending-duel
  escrow, legacy expeditions, Shadow Gates, рейды, Бездну/войны и клановые
  активы. Аномалии (invalid state JSON, orphan, overdue, gate-placement,
  stake > shared reserve) требуют manual recovery. Отчёт — только агрегаты,
  sorted canonical JSON с checksum от `snapshot_id`; никакие Telegram ID,
  имена, тексты или raw state не выходят. Независимая read-only критика
  отклонила повторное использование старого SQL-аудита: он падает на partial
  schema и не покрывает все обязательства. Проверки:
  `test_retirement_compensation_audit`, `py_compile`, remote-DSN deny,
  `test_old_combat_retirement`, `test_legacy_duel_retirement`,
  `test_first_release_boundary` — зелёные.

  **Остаточный blocker:** для фактического dry-run нужен предоставленный
  владельцем локально восстановленный неизменяемый PostgreSQL snapshot и
  утверждённые категории/формулы компенсации. Инструмент не подключается к
  production и не может самостоятельно выбрать коэффициенты конвертации.

## Ожидает решения владельца

- [ ] **ARB-011 · Безопасное подтверждение покупки VIP во всех адаптерах.**
  2026-08-24: сквозная проверка `чат → callback → services.vip →
  economy_ledger` и `Mini App → /vip/purchase → services.vip` выявила два
  связанных риска. Личное меню «бот вип» не привязано к его автору: в группе
  другой человек может нажать тариф и купить VIP для себя, хотя текст меню
  показывает статус и срок автора. Кроме того, и callback, и HTTP-покупка
  вызывают `purchase_vip` без idempotency key; `FOR UPDATE` не даёт уйти
  балансу в минус, но повтор одного события может законно списать второй раз
  и продлить срок второй раз. Подарочный путь уже owner-bound, что служит
  проверяемым внутренним эталоном.

  **Нужно решение владельца о UX покупки:**
  **A (рекомендуется)** — новое owner-bound callback-меню, явное подтверждение
  суммы в чате и Mini App, idempotency от сообщения/запроса и fail-closed
  обработчик старой кнопки; **B** — те же ownership и idempotency, но без
  дополнительного подтверждения; **C** — оставить кнопки доступными всем,
  явно переписав их как покупку VIP для нажавшего, с подтверждением и
  idempotency. До выбора не менять денежный UX и не выпускать этот сценарий
  как безопасный. Независимая read-only критика подтвердила оба риска и
  отвергла вариант, где idempotency применяется только к ledger: повтор тогда
  мог бы дать бесплатное второе продление, если не остановить обновление VIP.
