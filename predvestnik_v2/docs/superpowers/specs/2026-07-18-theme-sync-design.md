# Синхронизация тем профиля: код vs ручные правки — дизайн

**Дата:** 2026-07-18
**Статус:** дизайн утверждён пользователем, ожидает записи и перехода к implementation-плану

## Проблема

Темы профиля описаны в коде (`core/themes.py::THEMES`, 61 штука) и рендерятся в двух местах:
`services/profile_render.py` (сайт/превью, DevConsole Theme Lab) и `bot/handlers/identity.py`
(команды `я/профиль/кто/анкета`). Часть тем администратор редактирует вручную через
DevConsole Theme Lab (`/admin/dev/theme-templates/*`, `/admin/dev/theme-meta/*`).

Ручная правка сохраняется как **полный overwrite**, а не мёрж с кодом:

- `profile_theme_overrides.raw_text` — весь текст карточки профиля одной строкой
  (top/sep/bot/accent/side/prefix вместе). Если для темы есть эта строка, рендер использует
  **только её** — `core/themes.py` для этой темы полностью игнорируется, включая любые более
  поздние правки.
- `theme_metadata_overrides` — точечный мёрж по полям (`name/rarity/source/price_*/desc`), но и
  тут: если поле переопределено вручную, последующие правки этого же поля в коде эффекта не
  дают — оверрайд побеждает всегда, для этого конкретного поля, навсегда.

Итог: любая правка кода темы (новый текст, новая механика рендера, новая цена) не долетает до
всех тем, которые когда-либо редактировались вручную, пока админ не зайдёт и не пересохранит
каждую такую тему руками. При 61 теме и растущем числе ручных правок это не масштабируется.

## Цели

1. Администратор сохраняет полный доступ к ручному редактированию тем (Theme Lab как есть).
2. Правки кода (текст темы, цена, редкость и т.д.) применяются **ко всем темам, включая уже
   отредактированные вручную**, автоматически, без захода в консоль — вплоть до переопределения
   того, что админ написал руками.
3. Единый механизм для обеих таблиц оверрайдов (`profile_theme_overrides` и
   `theme_metadata_overrides`) — асимметрии в поведении между ними быть не должно.
4. Существующие ручные оверрайды, накопленные до этой фичи, приводятся в соответствие с кодом
   как часть выката, без отдельного разового скрипта.

## Не цели

- Частичная защита отдельных вручную заполненных полей от кода (обсуждалось как альтернатива,
  отклонено пользователем — код должен побеждать полностью, а не только «незаполненные» поля).
- UI в DevConsole для просмотра истории автосбросов — лог пишется, но отдельная вкладка для
  его просмотра не обязательна в этой итерации.
- Изменения в самом Theme Lab UI (форма редактирования не меняется).

## Архитектура

Было два уровня («код» и «ручная правка», побеждает тот, что записан позже). Станет три:

1. **Код** (`core/themes.py::THEMES`) — источник истины, как сейчас.
2. **Снимок на момент правки** (`base_snapshot`, новое поле) — что код-дефолт выдавал для этой
   темы в момент последнего ручного сохранения. Пишется автоматически при `set_override`,
   руками не редактируется, пользователю не показывается напрямую.
3. **Ручная правка** (`raw_text` / поля метаданных) — как сейчас, без ограничений в моменте
   редактирования.

Резолвер при рендере не меняется концептуально: есть оверрайд → берём его, нет → берём код.
Меняется момент, где решается, «есть ли оверрайд» — теперь это не просто «есть строка в
таблице», а «есть строка в таблице, чей `base_snapshot` всё ещё совпадает с текущим кодом».
Проверка и переход в состояние «оверрайда нет» (через `DELETE`) происходит не на каждый рендер,
а один раз при старте приложения.

## Компоненты

- **`profile_theme_overrides`**: + колонка `base_snapshot TEXT`. Значение — то, что вернул бы
  `_default_raw_text_for_basic_theme(theme_id)` для обычных тем или
  `_DEFAULT_RAW_TEMPLATES[template_id]` для 14 тем с `premium_template`, на момент сохранения.
- **`theme_metadata_overrides`**: + колонка `base_snapshot TEXT`. Значение — сериализация
  (JSON) полей `name/rarity/source/price_mora/price_diamonds/price_zarniki/price_dark/desc` из
  `THEMES[theme_id]` на момент сохранения.
- **Новая функция `reconcile_theme_overrides(db)`** (предположительно `services/themes.py`,
  рядом с существующим `_merge`) — один проход по обеим таблицам:
  для каждой строки пересчитать текущий код-дефолт → сравнить с `base_snapshot` →
  не совпало (включая `base_snapshot IS NULL` и «темы больше нет в `THEMES`») →
  записать в лог и `DELETE`.
  Вызывается при старте, после того как таблицы гарантированно существуют, до того как
  процесс начинает принимать трафик — **в обеих точках входа**, а не в одной: бот и FastAPI
  здесь могут подниматься как отдельные процессы (это видно по тому, что `ensure_table` для
  обеих таблиц оверрайдов уже сейчас продублирован и в `bot/core/database.py::init_db()`, и в
  соответствующих repository-модулях — ровно на случай, если поднимется только один из
  процессов). Реконсиляция дублируется туда же, по той же причине. Идемпотентна по построению:
  `DELETE` уже удалённой строки — no-op, так что параллельный старт обоих процессов безопасен
  без дополнительной блокировки.
- **`infrastructure/repositories/theme_templates.py::set_override`** и
  **`theme_meta.py::set_override`** — при сохранении дополнительно вычисляют и пишут
  `base_snapshot` тем же способом, что использует `reconcile_theme_overrides`.
- **`theme_override_reset_log`** (новая таблица, либо переиспользование существующего
  админ-аудит-лога, если он подходит по форме — решается на этапе implementation-плана):
  `table_name, key (theme_id/template_id), reset_at, old_content, old_updated_by`.
  Пишется в той же транзакции, что и `DELETE` в `reconcile_theme_overrides`.

## Жизненный цикл / data flow

1. Админ сохраняет тему X в Theme Lab → `set_override` пишет `raw_text` (или поля метаданных)
   **и** `base_snapshot` одной операцией.
2. Рендер темы X — без изменений: читает `raw_text`/смёрженные метаданные, ничего не
   пересчитывает на каждый показ.
3. Код темы X меняется (`core/themes.py`), коммит, деплой.
4. Старт приложения → `reconcile_theme_overrides(db)` проходит по всем строкам обеих таблиц →
   для X текущий код-дефолт ≠ сохранённый `base_snapshot` → запись в
   `theme_override_reset_log` → `DELETE` строки оверрайда.
5. Следующий показ темы X → оверрайда нет → «стандартный» путь рендера → всё из кода, включая
   правку. Для метаданных — аналогично, поле берётся напрямую из `THEMES`.
6. Админ, если хочет, может снова зайти в Theme Lab и настроить X заново — цикл повторяется.

## Граничные случаи

- **Существующие строки без `base_snapshot`** (сохранены до этой фичи) — трактуются как
  протухшие сразу, сносятся первым же прогоном `reconcile_theme_overrides` после деплоя.
  Это закрывает цель 4 (массовый сброс существующих ручных правок) без отдельного скрипта.
- **14 premium_template тем** — код-дефолт считается через `_DEFAULT_RAW_TEMPLATES`, не через
  `_default_raw_text_for_basic_theme`; сверка использует то же ветвление по `premium_template`,
  что уже есть в `_render_premium_impl`.
- **Тема удалена из `THEMES` целиком** — код-дефолт посчитать не из чего → оверрайд считается
  осиротевшим → тоже `DELETE` + запись в лог.
- **Гонка при старте** — сверка выполняется до начала приёма трафика, конкурентных сохранений
  через Theme Lab в этот момент быть не может.
- **`theme_metadata_overrides`** — тот же механизм: `base_snapshot` хранит JSON-снимок
  переопределяемых полей, сверка идёт по всем полям сразу (не по каждому отдельно) — если
  код-дефолт разошёлся хоть в одном учитываемом поле, оверрайд целиком считается протухшим.

## Аудит

Лёгкий лог `theme_override_reset_log` пишется при каждом автосбросе (таблица, ключ, момент,
что было до сброса, кто это в своё время сохранил). Отдельный экран в DevConsole для его
просмотра — не в этой итерации; при необходимости данные доступны прямым запросом к БД.

## Тестирование

- `reconcile_theme_overrides` — чистая функция от (текущий `THEMES`, строки БД) → (что удалить,
  что оставить), тестируется на фейковых данных изолированно: снимок совпадает → не трогать;
  не совпадает / NULL / темы нет в коде → удалить + залогировать.
- На реальном деплое — контрольный сценарий: вручную отредактировать тестовую тему → изменить
  её в коде → задеплоить → убедиться, что карточка вернулась к коду, а в логе появилась запись.

## Решения, принятые в брейншторминге (для истории)

- Код побеждает ручные правки **полностью**, включая уже написанный вручную текст — не только
  новые поля/механику. Решение пользователя, осознанно: мануальная правка не должна становиться
  постоянной вилкой, которая блокирует код навсегда.
- Тот же механизм распространяется на `theme_metadata_overrides` (цены/редкость/название) —
  без исключения для «бизнес-решений вроде спец-цены на промо».
- Сверка — при старте приложения (не на каждый рендер): дешевле, укладывается в то, что деплой
  на DO и так перезапускает процесс.
- Лёгкий лог автосбросов — нужен, чтобы было видно, что и когда снесло ручную правку.
