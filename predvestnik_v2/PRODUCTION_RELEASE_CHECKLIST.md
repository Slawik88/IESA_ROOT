# Production release checklist

Этот шлюз обязателен перед каждым переносом `predvestnik_v2` на production.
Он не даёт разрешение на деплой: push, merge, рестарт и миграции выполняются только
после отдельного прямого указания владельца.

## 1. Зафиксировать обе стороны сравнения

1. Записать точный Git SHA кандидата (`git rev-parse HEAD`).
2. Определить точный SHA, реально работающий на production. Если платформа не
   публикует SHA, выбрать предполагаемый ref и подтвердить его сравнением live
   статики/контрактов; не называть `origin/master` production без проверки.
3. Обновить remote refs через безопасный `git fetch`, но ничего не push/merge.
4. Сохранить список коммитов и файлов между production SHA и кандидатом.

## 2. Обязательный аудит «📣 Что нового»

Запустить из `predvestnik_v2`:

```bash
python tools/audit_release_whatsnew.py \
  --base <PRODUCTION_SHA> \
  --production-url https://iesaroot-app-8kuyb.ondigitalocean.app/predvestnik/updates.json \
  --output /tmp/predvestnik-release-whatsnew.md
```

Скрипт намеренно блокирует релиз, если между версиями есть пользовательский код,
но live/local лента одинакова. Его отчёт — вход для анализа, а не автогенератор
маркетингового текста.

После отчёта агент обязан прочитать diff по подсистемам и для каждого изменения
решить:

- увидит ли его игрок, администратор или владелец чата;
- выпущено ли оно реально, либо пока скрыто feature flag/dev-only стендом;
- это фича, исправление, баланс или важное изменение поведения;
- какое обещание можно проверить после деплоя.

В `FastAPI/static/updates.json` добавляются только реально выходящие изменения:

- понятный игроку заголовок и короткий итог;
- конкретные детали без внутренних имён функций/таблиц;
- честные ограничения без обещаний будущего контента;
- новые записи наверху, уникальные `id`, дата фактического релиза;
- связанные мелкие фиксы группируются, а не превращаются в технический лог коммитов.

Исторические production-записи не удалять и не переписывать молча. Если исправление
старого текста необходимо, оно должно быть отдельно отмечено в release-аудите.

## 3. Предпроизводственный шлюз

- синтаксис всех изменённых Python/JavaScript-файлов;
- профильные unit/integration/UI тесты;
- `npm run check:preview` и проверка `tools/unknown-api.log`;
- `python tools/test_static_delivery_contract.py`, если затронуты preview, ассеты
  или HTML: внутренние файлы не должны стать публичными, а CSS-зависимости не могут
  существовать только на localhost;
- `tools/test_static_delivery_asgi.py` в окружении с production Python-зависимостями,
  если менялись FastAPI static routes или `ROOT_PATH`: матрица 200/404, MIME и
  `/predvestnik` должны проходить на самом ASGI-приложении;
- `verify_reconstruction_preview_contract.mjs`, если менялись `/game`, Reconstruction
  bridge или production HTTP-контракт: browser должен использовать `/reconstruction`,
  а не raw dev route;
- ручной просмотр затронутых экранов на 320/390/430 px;
- отдельная ревизия diff после тестов;
- dry-run всех миграций с планом отката;
- повторный запуск `audit_release_whatsnew.py` — итог должен быть `READY`;
- `tools/test_profile_whatsnew_resilient.py`, чтобы лента не уронила профиль при
  рассинхроне схемы БД.

## 4. После явно разрешённого деплоя

1. Проверить health/readiness приложения и бота.
2. Открыть live `/predvestnik/updates.json`: новая верхняя запись и весь набор
   подготовленных ID должны присутствовать.
3. Открыть вкладку «📣 Что нового» как обычный пользователь, проверить бейдж,
   раскрытие деталей и сохранение `whatsnew_seen_id` после перезапуска страницы.
4. Проверить ключевые изменённые сценарии и логи без записи/правки данных вручную.
5. Зафиксировать production SHA и результат post-deploy smoke в release-отчёте.

Если любой пункт не доказан, релиз не считается завершённым.
