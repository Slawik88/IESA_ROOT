# ECO-04 PR-C — Gifts by tier and the gift shelf

Risk: T2 (new currency sink in three currencies, limits, a social surface with player-written text). Source: `../ECO-04-PR-B-shop/designer_brief.md` §1 (Gifts tab), §2 (Gifts), §3 (Gift shelf) and the gifts section of `../ECO-04-PR-B-shop/shop_catalog.json` (4 tiers, 12 gifts, prices as given).

## Scope (first release)
- Gifts only to the marriage partner (as the old partner gifts). Not to any player; no «decline gifts» / «report note» yet.
- New catalogue: tiers 1 «Знак» (Mora), 2 «Тёплый» (Mora), 3 «Редкий» (💎), 4 «Легендарный» (✨), three gifts each.
- Shop tab «Подарки», send flow (recipient → gift → optional note ≤60 → confirm), bot notification to the recipient.
- Gift shelf in the own profile (four shelves, slots, silhouettes, counters, pins ≤3, history with tier filter); other profile / public card shows only pinned (≤3) + total, and a small badge for a top-tier gift.
- Flag `gifts_v2`, default off, fail-closed. Flag off: no tab, no shelf, no gifts block on the public card, `/gifts-v2/*` answers 404 «Подарки пока закрыты». Old `/marriage/gifts` and `/marriage/gift` are untouched and keep working either way.
- Not in this PR: «Что нового» (ships with the flag decision), gifts to any player, search by name.

## Design
- `core/gifts_v2.py` (pure): `GIFTS_VERSION`, `FLAG`, `REASON_CODE = "gift_send_v2"`, `TIERS`, `GIFTS` (owner numbers), `DAILY_SEND_LIMIT = 5`, `DAILY_PER_RECIPIENT_LIMIT = 3`, `NOTE_MAX = 60`, `PIN_MAX = 3`, `normalize_note`, `request_hash`, `catalog_payload` / `catalog_digest`.
- `infrastructure/repositories/gifts_v2.py`: `gift_sends_v2` (append-only, trigger `gift_sends_v2_append_only`): id, sender_id, receiver_id (CHECK ≠ sender), action_id (UNIQUE per sender), gift_id (CHECK pattern `^gift_[a-z0-9_]{1,40}$`), tier (1–4), note (NULL or 1–60 chars), request_hash, gifts_version, catalog_digest, price JSONB, marriage_id, economy_operation_id (UNIQUE, FK economic_operations), sent_on (UTC day), created_at. `gift_pins_v2` (send_id PK → gift_sends_v2, receiver_id): the only mutable part.
- `services/gifts_v2.py` `send`: one transaction → `lock_user(sender)` (same advisory key as shop, chests, exchange) → replay by (sender, action_id) with request hash → action id owner check (`shop_v1.action_owner`, now also knows `gift`) → flag → catalogue version/digest → recipient (partner, `FOR SHARE` on the marriage row; a `to` ref to oneself → «Себе дарить нельзя.»; anyone else → «Подарки пока можно дарить только супругу.») → UTC day from one `CLOCK_TIMESTAMP()` (`shop_v1.window`) → 5/day per sender, 3/day per sender→recipient → shortages (409 «Не хватает: …», nothing debited) → `economy_ledger.apply_balance_change(reason_code="gift_send_v2", idempotency_key="gift-v2:<send_id>", source_type="social", target_id=receiver, metadata no_power)` → receipt row.
- Notification after commit (router): in-app gift box through the existing `_notify_partner_gift` (WS or web_notifications, payload type `partner_gift`, so the existing «Подарок от супруга» box shows it) plus a Telegram bot message via the Bot API with HTML-escaped sender, gift and note. Both are best-effort and logged; a failure never turns a committed gift into an error.
- API: `GET /gifts-v2/me` (balances, recipient {name, ref}, limits {daily, recipient, resets_in_seconds}, tiers with gifts {cost, missing, affordable, irreversible, available}, own shelf), `POST /gifts-v2/send {gift_id, action_id, catalog_version, catalog_digest, note?, to?}`, `GET /gifts-v2/history?box=received|sent&tier=&gift_id=&limit=`, `POST /gifts-v2/pin {send_id, pinned}`. Public card (`/public-profile-v3/{ref}`) gets `gifts: {total, pinned ≤3 (gift, icon, name, tier only — no note, no sender), top_badge, can_send}` only while the flag is on. Telegram ids never leave the server: people are `{name, ref}` from `public_profiles_v1.player_projection`.
- Wallet history label `gift_send_v2` → «🎁 Подарок»; bot metrics group «Подарки и компенсации» now includes `gift_` codes.
- Tables are created by `bot/startup_schema.py` (production path) and the FastAPI lifespan.
- Mini App: `FastAPI/static/app.45.js` (new part in `_APP_JS_PARTS`, after app.44.js). The shop gets a small generic hook `_shopExtra` in app.44.js (`{id: {name, on(), load(), html()}}`); the gifts part registers its tab there, so app.44.js keeps no gift code. The tab bar became `grid-auto-flow: column` so three or four tabs fit. Own profile: `giftsShelfShell()` in `renderProfileHome` (new block `#pro-gifts`, there was no `#pro-marriage-card` host). Public card: `ppGiftsHtml(d)` and `giftBadgeHtml(...)` in app.21.js. Styles `.gift-*` in app.css right after the shop block: tier 1 thin line, 2 gold wash (`--border`, `--gold-dim`), 3 violet glow (`--violet`, `--violet-dim`), 4 gold + violet gradient, `--glow-gold`, slow shimmer (off under `prefers-reduced-motion`). Only existing tokens.

## Decisions
- «Max 3 per person per day» is counted per sender→recipient pair (the sender's limit, as the brief's error texts read). Both limits are serialised by the sender's lock only; no recipient lock is needed. With partner-only sending the 3/recipient limit binds first; the 5/day limit matters after a divorce and a new marriage on the same UTC day (tested).
- Request hash = gift id + note. Prices and the catalogue digest stay out (PR-B review fix), so a retry after a deploy still returns its receipt. A replay is answered before the flag and catalogue checks.
- `gift_id` CHECK is a pattern, not an `IN (...)` list: `ensure_tables` has a fast path, and a new gift must not need a constraint migration. The fast path checks the last-created object (`gift_pins_v2`) plus the trigger.
- One action id belongs to one store: `shop_v1.action_owner` returns `gift` for a gift action id (guarded by `to_regclass`, so the shop works on a stand that never created the gift table); the shop refuses it, and gifts refuse any id the shop, chests or exchange already own. The gift's ledger idempotency key is `gift-v2:<send_id>`, never the client action id.
- Notes: strip, empty → NULL, ≤60 characters (code points, the client counts the same way), refused if they contain control (Cc/Cs/Co/Cn), line/paragraph separators or bidi override/isolate characters; emoji with ZWJ are fine. Stored as typed; every UI place prints them through `_profileEsc`, the bot message through `html.escape`.
- The shelf has one slot per catalogue gift (3 per tier); an empty slot is the gift's emoji as a dark silhouette. Old `partner_gifts_log` keepsakes are not on the shelf (different catalogue, no tier); they stay in the marriage card data as before.
- Pins: toggle, idempotent, ≤3, only gifts the player received; the public card never shows notes or senders.
- Top-tier badge: the icon of the newest received Legendary gift, after the name on the own profile and on the public card.
- «Подарить» appears on someone else's card only when the viewer may gift them now (their partner); it opens the shop on the Gifts tab.
