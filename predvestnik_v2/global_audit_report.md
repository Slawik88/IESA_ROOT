## 🔴 CRITICAL

### C1 — Азартные игры: гонка обходит КД, дневной лимит и уводит баланс в минус
**Категория:** 🐞 Баг/уязвимость (дюп/абуз)
**Где:** `services/games.py` (`_settle` стр. 37–73; `play_dice/coin/number/roulette`)
**Корень:** PGAdapter работает в **autocommit** (см. H1). `games.py` НЕ открывает
`BEGIN` и НЕ берёт `FOR UPDATE`. Поток ставки:
1. `_check_cooldown` (чтение, КД ещё не выставлен),
2. проверка баланса (чтение),
3. `_settle`: списать ставку → начислить выигрыш → `add_daily_winnings` →
   `set_cooldown` в самом конце.

**Эксплойт:** игрок шлёт N **параллельных** запросов (особенно тривиально через
Web API). Все N проходят `_check_cooldown` (КД ещё нет) и проверку баланса до того,
как хоть один запишет cooldown/winnings:
- **обход КД** — N игр вместо одной;
- **обход дневного лимита** `GAMBLE_DAILY_CAP` — все читают одинаковый
  `already_won` до записи (стр. 48, 56, 62) → суммарный выигрыш > cap;
- **отрицательный баланс** — проверка баланса (стр. 84/107/132/155) отделена от
  списания; две полные ставки проходят чек и обе списываются.

**Фикс:** обернуть ВСЮ ставку в одну транзакцию + `SELECT … FOR UPDATE` на строке
игрока, и **проверять+выставлять КД и дневной лимит внутри той же транзакции**
(до розыгрыша). Т.е. `_check_cooldown`/`get_daily_winnings`/баланс читать под
блокировкой, мутации — там же, один `commit` в конце (как сделано в
`economy.transfer_currency`). Пока не исправлено — это рабочий принтер валюты.

**Доп. мелочь:** в `_settle` списание ставки всегда логируется `source="gamble_loss"`
даже при выигрыше (стр. 51), а вычисленный `source` (стр. 49) не используется —
в `wallet_log` выигрышная игра даёт пару `gamble_loss`(−bet)+`gamble_win`(+gross).
Косметика отчётности.

## 🟠 HIGH

### H1 — Модель транзакций: autocommit + неверный docstring → дебет-после-чека без блокировки небезопасен
**Категория:** 🏗 Архитектура / 🐞 уязвимость
**Где:** `infrastructure/pg_adapter.py` (`commit` стр. 261–265 — no-op без `_begin`;
`_run` стр. 189–228), `infrastructure/repositories/economy.py` (docstring стр. 1–5,
`add_balance` стр. 29–55).
**Суть:** без явного `BEGIN`/`BEGIN IMMEDIATE` каждый `execute` исполняется в
автокоммите; `db.commit()` тогда — **no-op**. При этом docstring economy.py
утверждает «All balance-changing functions use explicit asyncpg transactions» —
это **неправда** для `add_balance` (INSERT+UPDATE+log тремя отдельными
автокоммит-стейтментами).
- Чистый **кредит** безопасен: `UPDATE … = balance + ?` атомарен на уровне строки.
- **Дебет с предварительным чтением баланса** безопасен ТОЛЬКО если вызывающий код
  обернул всё в `BEGIN` + `FOR UPDATE`. Кто это делает: `economy.transfer_currency`,
  `auction`, `battle_pass`, `duel`, `vip`, `dark_mora`, `marriages`, `relics`,
  `zoo`, `gacha`. Кто **не** делает и трогает баланс: `games` (см. C1),
  `promocodes`, `quests`, `achievements`, `daily_deal`(?), `scheduler`, `leveling`
  — каждый из них требует проверки на «чек→дебет без блокировки» в Этапе 2.
**Фикс:** (1) исправить docstring; (2) ввести единый помощник
`async with eco.atomic(db, user_id):` (BEGIN + FOR UPDATE строки users), и
прогнать через него все debit-after-check сайты; (3) рассмотреть `CHECK
(user_balance_* >= 0)` на уровне БД как страховку от ухода в минус.

### H2 — `add_balance(commit=...)` — мёртвый параметр, маскирующий неатомарность
**Категория:** 🏗 Архитектура (ловушка)
**Где:** `economy.add_balance` (стр. 35), повсеместные вызовы `commit=False`.
**Суть:** параметр `commit` — «kept for API compat, no-op». Десятки вызовов пишут
`commit=False`, создавая ложное ощущение «я внутри транзакции, закоммичу позже».
Реально, если вызывающий не открыл `BEGIN`, изменение уже зафиксировано. Это прямо
питает класс багов H1/C1. **Фикс:** либо удалить параметр и сделать атомарность
обязанностью внешнего `BEGIN`, либо реально поддержать отложенный commit.

## 🟠 HIGH

### H3 — Гача списывает баланс без `FOR UPDATE` → овердрафт в минус
**Категория:** 🐞 Уязвимость (овердрафт)
**Где:** `services/gacha.py` `roll_single` стр. 202–214, `roll_multi` стр. 308–316.
Внутри `BEGIN IMMEDIATE`, но баланс читается `eco_repo.get_balance` (обычный
SELECT, без `FOR UPDATE`; единственный `FOR UPDATE` в гаче — на строке pity).
Два параллельных спина читают один баланс, оба проходят проверку, оба списывают
(`= balance + (-cost)` атомарно) → итог уходит **в минус**. Деньги не создаются,
но игрок крутит «в долг». **Фикс:** `SELECT … FOR UPDATE` на строке users внутри
транзакции (как в battle_pass/vip).

### H4 — Достижения: потеря прогресса + двойной грант + двойной wallet_log
**Категория:** 🐞 Баг (data integrity / дюп)
**Где:** `services/achievements.py` `increment_metric` стр. 31–81.
1. **Потеря прогресса:** `new_progress = record.progress + delta`, затем
   `upsert_achievement(..., new_progress)` (SET, не атомарный инкремент). Два
   параллельных события (бот+сайт по одной метрике) читают одинаковый `record`
   → последний перезаписывает первого → **дельта теряется**. (В quests прогресс
   инкрементится атомарно — здесь регресс.)
2. **Двойной грант уровня:** оба прохода видят `current_level=L`, оба грантят
   награды уровня L+1. Нет атомарного guard на повышение уровня.
3. **Двойной лог моры:** `add_balance(mora=…)` уже пишет в `wallet_log`
   внутри себя; строка 54 добавляет ВТОРОЙ `log_wallet` для той же моры (для
   алмазов строка 60 второго лога нет). → ачивочная мора-награда задваивается в
   истории кошелька. **Фикс:** убрать строку 54; перевести прогресс на атомарный
   инкремент с возвратом значения; повышение уровня — под `FOR UPDATE`.

### H5 — Квесты: двойной грант награды под гонкой
**Категория:** 🐞 Баг (дюп награды)
**Где:** `services/quests.py` `increment_metric` стр. 126–150. `row["completed"]`
читается ДО атомарного инкремента; `mark_completed` безусловный. Два события,
одновременно пересёкших `target` (особенно бот-инкремент + сайт-инкремент одной
метрики вроде `gacha_spins_today`), оба вызывают `mark_completed`+грант →
**награда выдаётся дважды**. **Фикс:** `mark_completed` сделать условным
(`UPDATE … SET completed=1 WHERE … AND completed=0 RETURNING`) и грантить
ТОЛЬКО если флаг реально переключился.

### M7 — Daily Deal: овердрафт в минус (нет `FOR UPDATE`)
**Где:** `services/daily_deal.py` `purchase_slot` стр. 141. Есть `BEGIN

### M8 — Craft: частичная потеря ингредиентов
**Где:** `services/craft.py` `craft`. Многоингредиентный рецепт списывает
ингредиенты по одному (`remove_item` атомарен поштучно), но БЕЗ объемлющей
транзакции (autocommit). Если 2-й ингредиент кончился (параллельный крафт) после
списания 1-го — 1-й уже **безвозвратно списан**, результат не выдан. «No commit —
caller must commit» здесь иллюзорно (H2). **Фикс:** обернуть весь крафт в
`transaction()`.

### M9 — Промокоды: окно потери награды + лёгкое превышение глобального лимита
**Где:** `services/promocodes.py`. (1) Запись redemption (PK-guard ✓ от
двойной активации) коммитится ДО выдачи наград в autocommit; сбой между ними →
юзер «отмечен активировавшим», но награды нет, и повтор заблокирован →
**потеря награды**. (2) `max_activations` (стр. 63) читается, инкремент позже
(стр. 108) — разные юзеры в гонке могут слегка превысить глобальный лимит.
(3) `item_id` из промо не валидируется против `ITEMS_REGISTRY` (стр. 134) →
опечатка админа создаёт «призрак» в инвентаре. **Фикс:** вся выдача в одной
транзакции с redemption-guard; атомарный `activations_count` с проверкой лимита;
валидация item_id.

### M10 — Квесты: двойное назначение при гонке первого вызова
**Где:** `services/quests.py` `get_or_assign_quests`/`increment_metric` авто-assign.
Проверка «len(existing)>=3» не под локом; два параллельных первых вызова
`_select_quests` (рандом) → разные наборы → >3 квестов на день. Косметика. **Фикс:**
один источник назначения + уникальный guard на (user, chat, date).

### M11 — Утечка слоёв: aiogram в services
**Категория:** 🏗 Архитектура (нарушение CLAUDE.md «services не импортирует bot.*»)
**Где:** `services/utils.py` (`from aiogram import types` — реальная утечка,
утилита для services должна быть платформо-независимой), `services/scheduler.py`
(`from aiogram import Bot` + inline `InlineKeyboardBuilder/CallbackData` —
оправдано рассылками, но это адаптерный код в слое логики),
`services/global_moderation.py` (aiogram exceptions). **Фикс:** вынести
aiogram-зависимые куски в `bot/`, оставить в services чистую логику; scheduler —
осознанно задокументировать как пограничный.

проблема изолирована в аукционе.

# ЭТАП 4 — Web Mini App (routers + app.js/app.css)

## ✅ Что сделано ХОРОШО (важный позитив по безопасности)

- **Аутентификация реализована ПРАВИЛЬНО.** `verify_webapp_data` (auth.py 26)
  корректно считает HMAC-SHA256 (secret = HMAC(`WebAppData`, token)), сравнивает
  через `compare_digest` → подделать `user_id` нельзя. Session-token —
  HMAC-подписан (`{uid}:{exp}:{sig}`), Login Widget проверяет `auth_date` (24ч).
  **Impersonation невозможна.**
- **Все 127 эндпоинтов под auth** (`require_tg_user`/dev-гарды) — пофайловая
  сверка не нашла ни одного мутирующего эндпоинта без гейта.
- **Имена питомцев/ников безопасны:** pet `name` берётся из реестра species
  (не user-text), ник рендерится через `textContent` (экранируется браузером).
- **api()-обёртка адекватна:** 401 → сброс сессии + оверлей логина; парсинг
  `detail` ошибок; состояния загрузки/пустоты присутствуют (~178 маркеров).
- **Паритет со стороны сайта структурно здоров:** роутеры ходят через

# 🚑 ДОПОЛНИТЕЛЬНО — Баги, мешающие игроку (НАЙДЕНО + ИСПРАВЛЕНО)

Точечный проход по жалобам игрока на сломанный UX. Все три ниже — **исправлены**
в этом коммите.

### BUG-A 🔴 — Лоты аукциона не видны на сайте (видны только в боте)
**Корень:** `app.js` — вкладка аукциона открывалась вызовом `loadAuction(1)`
(`swAuction`, стр. 3120), а API `/auction/lots` **0-индексный** (`page=0` —
первая страница). При ≤20 активных лотах `page=1` (offset 20) возвращает пустоту →
сайт показывает «нет лотов», хотя они есть. Бот при этом показывал их (свой
запрос) → выглядело как «лот есть только в боте».
**Фикс:** `loadAuction(0)` при открытии вкладки.
**Сопутствующее (заметка):** конвенции пагинации рассогласованы — аукцион
0-индексный, админка (`/admin/.../users`,`/logs`) 1-индексная. Источник класса
таких off-by-one; стоит унифицировать на одну конвенцию.

### BUG-B 🔴 — Нельзя сделать первую ставку («нужно 105 на лоте за 100»)
**Корень:** `services/auction.place_bid` — для лота БЕЗ ставок бралось
`current_high = min_bid − 0.01`, и порог считался как `min_bid × 1.05`
(`100 → 104.99 → «≥105»`). Кнопка бота предлагала «Ставка 100» (`_ceil(min_bid)`),
а сервер её отклонял с «≥105» → ставку нельзя было сделать почти никогда.
**Фикс:** первая ставка = ровно `min_bid`; шаг +5% применяется ТОЛЬКО когда уже
есть активная ставка.

### BUG-C 🟡 — Высокий пол минимальной ставки
**Запрос игрока:** «убери минимальные ставки».
**Фикс:** `AUCTION_MIN_BID` 10 → 1 (продавец может выставлять лот с мин. ставкой
от 1; шаг +5% на повторных ставках сохранён как анти-спам). Полностью убирать
минимум (0) не стал — нулевые/спам-ставки сделали бы аукцион нечитаемым; порог 1
снимает реальное ограничение.

**Проверка:** `node --check app.js` ✓, `py_compile auction.py/constants.py` ✓.
Эти три бага закрывают связку «аукционом нельзя пользоваться».
