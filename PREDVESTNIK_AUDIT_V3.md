### ✅ CRIT-006 — `miniapp_dev_analytics`: `db.fetchall` не существует → 500 (ИСПРАВЛЕНО)

**Файл:** `IESA_ROOT/IESA_ROOT/miniapp_views.py`, строка ~6925  
**Тип:** AttributeError при каждом обращении  
**Частота:** Каждый запрос к `/api/dev/analytics`

**Описание:**  
`PostgresConnection` класс имеет метод `fetch()`, но не имеет `fetchall()`. В `miniapp_dev_analytics` 3 вызова `db.fetchall(...)` и 1 вызов `db.fetchone(...)` с tuple-обёрткой параметров `(date_from,)` вместо позиционных аргументов.

**Исправление (применено):**  
`db.fetchall(sql, (param,))` → `db.fetch(sql, param)` (3 места)  
`db.fetchone(sql, (param,))` → `db.fetchone(sql, param)` (1 место)

### ✅ CRIT-007 — Аукцион: продавец НЕ получает деньги при продаже (ИСПРАВЛЕНО)

**Файл:** `PredvestnikBot/api/auction.py`, функции `buyout_auction()` и `finalize_expired_auctions()`  
**Тип:** Финансовый баг — деньги теряются при transaction rollback  
**Частота:** При каждой продаже через аукцион (если add_to_treasury бросит ошибку)

**Описание:**  
`add_to_treasury()` открывает СОБСТВЕННУЮ транзакцию через `postgres_connect()` и коммитит независимо. Основная транзакция аукциона (`buyout_auction`) тоже использует `postgres_connect()`. Если `add_to_treasury` бросает исключение ПОСЛЕ коммита казны:
1. Казна получает комиссию ✅ (закоммичено в отдельной транзакции)
2. Внешняя транзакция откатывается ❌
3. Продавец НЕ получает деньги ❌ (откат)
4. Предмет НЕ передаётся покупателю ❌ (откат)
5. Аукцион остаётся `active` ❌ (откат)

Дополнительно: в `finalize_expired_auctions` 3 места использовали `logger.error(...)` вместо `_log.error(...)` — NameError в обработчике ошибок.

**Исправление (применено):**  
- Убрал вызов `add_to_treasury()` из обеих функций
- Вставил SQL INSERT напрямую через `db.execute()` внутри той же транзакции
- Исправил `logger` → `_log` в 3 местах

### ✅ HIGH-014 — Аукцион: concurrent bids без блокировки (ИСПРАВЛЕНО)

**Файл:** `PredvestnikBot/api/auction.py`, функция `place_bid()`  
**Статус:** ✅ Исправлено  
`SELECT * FROM auctions WHERE id=? FOR UPDATE` добавлен в `place_bid()`.

**Описание:**  
При одновременных ставках двух пользователей:
1. Оба читают текущую цену (например 100)
2. Оба проходят проверку `bid > current_price`
3. Оба делают UPDATE → один перезаписывает другого
4. Предыдущему биддеру возвращается ставка неправильного размера

**Исправление:** Добавить `SELECT ... FOR UPDATE` при чтении аукциона перед ставкой.
