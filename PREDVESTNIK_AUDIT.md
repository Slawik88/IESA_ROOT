## 🔴 CRITICAL — Критические уязвимости (28)

### BUG-001 · CORS `Access-Control-Allow-Origin: *`
- **Файл**: `miniapp_views.py` · строка 151
- **Описание**: Все API-эндпоинты мини-приложения возвращают `Access-Control-Allow-Origin: *`. Это позволяет ЛЮБОМУ сайту отправлять запросы к API от имени пользователя.
- **Воздействие**: Злоумышленник может создать фишинговую страницу, которая будет красть данные пользователей или делать переводы.
- **Исправление**: Ограничить Origin до `https://t.me` и домена мини-приложения.

### BUG-002 · Захардкоженный `_DEVELOPER_ID`
- **Файл**: `miniapp_views.py` · строка 787
- **Описание**: `_DEVELOPER_ID = 1460945748` — ID разработчика прямо в коде. Разработчик обходит ВСЕ проверки (feat_website gate, модерацию и т.д.).
- **Воздействие**: При утечке кода любой может узнать привилегированный ID. Нет возможности ротации без деплоя.
- **Исправление**: Вынести в переменную окружения `os.environ["DEV_TELEGRAM_ID"]`.

### BUG-003 · Гонка в `transfer_mora()` — получатель не существует
- **Файл**: `db.py` · строка 4672
- **Описание**: Функция `transfer_mora()` не проверяет, что получатель (`to_uid`) существует в таблице `users`. Если `UPDATE users SET balance = balance + ? WHERE user_id=?` затрагивает 0 строк (пользователя нет), деньги отправителя уже списаны, а функция комитит транзакцию `await db.commit()`.
- **Воздействие**: Мора бесследно исчезает: списана у отправителя, не зачислена получателю.
- **Исправление**: Проверять `cursor.rowcount` на UPDATE получателя; откатывать при 0.

### BUG-004 · Гонка в `deduct_family_pool()` — двойное списание
- **Файл**: `db.py` · строка ~2049
- **Описание**: Read-modify-write без блокировки: SELECT баланса → проверка → UPDATE. Между SELECT и UPDATE параллельный запрос партнёра может пройти ту же проверку.
- **Воздействие**: Оба партнёра одновременно снимают из семейного кошелька больше, чем есть. Баланс уходит в минус.
- **Исправление**: Использовать `SELECT ... FOR UPDATE` или атомарный `UPDATE ... WHERE balance >= ?`.

### BUG-005 · `@csrf_exempt` на ВСЕХ эндпоинтах
- **Файл**: `miniapp_views.py` · все функции
- **Описание**: Каждый API-эндпоинт помечен `@csrf_exempt`. В сочетании с CORS `*` это позволяет cross-site запросы без защиты.
- **Воздействие**: CSRF-атаки из любого браузера. Фишинговая страница может выполнять действия от имени авторизованного пользователя.
- **Исправление**: Полагаться на проверку `X-Telegram-Init-Data` HMAC как CSRF-токен; убрать CORS `*`.

### BUG-006 · Auth Bypass через query-параметры
- **Файл**: `miniapp_views.py` · строки 157–165
- **Описание**: `_get_init_data()` читает initData из GET-параметров (`?initData=...`) как fallback. Браузерные GET-параметры легко подделать.
- **Воздействие**: Если бот-токен утечёт, злоумышленник может формировать валидные initData и действовать от любого user_id.
- **Исправление**: Убрать fallback на GET-параметры; принимать initData ТОЛЬКО из заголовков.

### BUG-007 · Dev Mode Bypass — `_BOT_TOKEN` не задан
- **Файл**: `miniapp_views.py` · строки ~287
- **Описание**: Если `_BOT_TOKEN` не задан (dev-среда), аутентификация пропускается и любой может передать `?user_id=123` для доступа к чужому аккаунту.
- **Воздействие**: Полный обход аутентификации. Если в production забыли задать токен — открыт доступ ко всем данным.
- **Исправление**: Запрещать запуск без `BOT_TOKEN` в production; добавить защиту `DEBUG=True`.

### BUG-008 · IDOR — принятие чужих предложений брака
- **Файл**: `miniapp_views.py` · строки 896–903
- **Описание**: `miniapp_marriage_respond()` не валидирует, что вызывающий — получатель предложения. Любой может принять/отклонить чужое предложение, зная его ID.
- **Воздействие**: Злоумышленник может жениться на любом пользователе без его согласия.
- **Исправление**: Проверять `to_user_id == uid` ПЕРЕД обновлением.

### BUG-009 · Гонка гача-покупок — двойная прокрутка
- **Файл**: `miniapp_views.py` · строки ~3220
- **Описание**: `miniapp_gacha_roll()` не блокирует баланс пользователя при 10x/50x прокрутке. Два параллельных запроса могут пройти проверку баланса одновременно.
- **Воздействие**: Пользователь платит за 10 итемов, получает 20. Эксплойт экономики.
- **Исправление**: `SELECT ... FOR UPDATE` на балансе перед прокруткой.

### BUG-010 · IDOR — панель разработчика без аудит-лога
- **Файл**: `miniapp_views.py` · строки 1187–1247
- **Описание**: `miniapp_dev_setbalance()` позволяет выставить баланс 0–10M, `miniapp_dev_add_xp()` — до 100M XP. Никакого журнала изменений.
- **Воздействие**: Невозможно отследить злоупотребления. Компрометация dev-аккаунта = неограниченная Мора.
- **Исправление**: Логировать все dev-операции в отдельную таблицу с timestamp, admin_id, target_id, old_value, new_value.

### BUG-011 · Гонка check_daily_mora — двойной стрик
- **Файл**: `db.py` · строка ~1950
- **Описание**: `check_daily_mora()` читает стрик → проверяет → инкрементирует без атомарности. При параллельных сообщениях в одну секунду стрик может увеличиться дважды.
- **Воздействие**: Пользователи получают 2× дневную награду при высокой активности.
- **Исправление**: Атомарный UPDATE с проверкой `last_daily_date != today`.

### BUG-012 · SQL-инъекция через `field` в `increment_tracker()`
- **Файл**: `db.py` · строка ~5400
- **Описание**: `f"UPDATE user_mora SET {field} = ..."` — имя столбца подставляется через f-string без валидации по whitelist.
- **Воздействие**: Если `field` контролируется пользовательским вводом, возможно выполнение произвольного SQL.
- **Исправление**: Валидировать `field` по списку разрешённых имён столбцов.

### BUG-013 · Рулетка — пити-счётчик без коммита
- **Файл**: `api/roulette.py`
- **Описание**: При гарантированном выигрыше по пити-системе счётчик поражений обнуляется, но `commit()` не вызывается в той же транзакции.
- **Воздействие**: При ошибке до коммита пити-счётчик не сбрасывается → пользователь получает гарантированный выигрыш повторно.
- **Исправление**: Включить обнуление пити в ту же транзакцию, что и выигрыш.

### BUG-014 · Аукцион — дублирование ставки (двойная оплата)
- **Файл**: `api/auction.py`
- **Описание**: Списание денег за ставку и обновление `highest_bidder_id` происходят в разных операциях. Между ними возможна параллельная ставка.
- **Воздействие**: Деньги списаны у обоих участников, но побеждает только один. Проигравший теряет ставку.
- **Исправление**: Единая транзакция с `SELECT ... FOR UPDATE` на лоте.

### BUG-015 · Гача — компенсация дубликатов вне транзакции
- **Файл**: `api/gacha.py`
- **Описание**: При получении дубликата компенсация зачисляется отдельным запросом. Если он упадёт — итем списан, компенсация не получена.
- **Воздействие**: Пользователь теряет редкие итемы без компенсации.
- **Исправление**: Обернуть в единую транзакцию.

### BUG-016 · owner.py — неопределённые переменные при распределении XP
- **Файл**: `handlers/owner.py` · строка ~330
- **Описание**: В блоке распределения XP используются переменные, не определённые в текущей области видимости.
- **Воздействие**: `NameError` при вызове команды — функция полностью не работает.
- **Исправление**: Исправить имена переменных / вынести из вложенного scope.

### BUG-017 · pets.py — TOCTOU гонка в усыновлении питомцев
- **Файл**: `handlers/pets.py` · строка ~145
- **Описание**: Проверка доступности питомца и его присвоение — два отдельных запроса. Между ними другой пользователь может забрать того же питомца.
- **Воздействие**: Два пользователя получают одного питомца; дублирование в базе.
- **Исправление**: Атомарный UPDATE с WHERE (статус + отсутствие владельца).

### BUG-018 · tax_event.py — двойная финализация события
- **Файл**: `handlers/tax_event.py` · строка ~160
- **Описание**: Финализация налогового события не проверяет, что событие ещё не завершено. Параллельные вызовы могут начислить награды дважды.
- **Воздействие**: Двойная выплата наград всем участникам.
- **Исправление**: Атомарный UPDATE `SET finished=1 WHERE finished=0 RETURNING id`.

### BUG-019 · diligence.py — глобальный dict без блокировки
- **Файл**: `handlers/diligence.py`
- **Описание**: Глобальный словарь состояния модифицируется из разных async-контекстов без lock/mutex.
- **Воздействие**: Повреждение данных при конкурентном доступе; непредсказуемое поведение.
- **Исправление**: Использовать `asyncio.Lock()` или `collections.defaultdict` с атомарными операциями.

### BUG-020 · shop.py — кто угодно может менять цвет чужого питомца
- **Файл**: `handlers/shop.py` · строка ~430
- **Описание**: При смене цвета питомца нет проверки `not_your_button()` — один пользователь может нажать кнопку в сообщении другого.
- **Воздействие**: Любой пользователь чата может менять цвет чужих питомцев (и тратить их деньги).
- **Исправление**: Добавить `callback_query.from_user.id == owner_id` проверку.

### BUG-021 · Миссинг ownership check при экипировке
- **Файл**: `miniapp_views.py` · строки 2165–2196
- **Описание**: Экипировка предмета по `item_id` проверяет `owner_id = uid` при чтении, но UPDATE отдельным запросом без WHERE owner_id. Параллельный трансфер предмета может привести к экипировке чужого.
- **Воздействие**: Пользователь экипирует легендарный предмет другого игрока.
- **Исправление**: WHERE `owner_id=uid AND id=item_id` в UPDATE.

### BUG-022 · Datetime без timezone → ошибки DST
- **Файл**: `db.py` · строки ~1300
- **Описание**: `datetime.isoformat()` без timezone сохраняется в TIMESTAMPTZ. PostgreSQL интерпретирует как local time.
- **Воздействие**: При переходе на летнее/зимнее время все временные метки смещаются. Стрики, экспедиции, квесты ломаются.
- **Исправление**: Всегда передавать `datetime.now(timezone.utc)`.

### BUG-023 · division_by_zero в level_for_xp
- **Файл**: `db.py` · строка ~1700
- **Описание**: `level_for_xp(xp)` вычисляет `math.sqrt(xp / 25)`, но не проверяет отрицательный XP.
- **Воздействие**: `math.sqrt(negative)` → `ValueError` → крэш всего расчёта рангов.
- **Исправление**: `max(0, xp)` перед вычислением.

### BUG-024 · Миграция браков — потеря данных
- **Файл**: `db.py` · строки ~2566
- **Описание**: Миграция из per-chat браков в глобальные использует `(user_id, partner_id)`, но дублирующиеся браки (один пользователь женат в нескольких чатах) схлопываются в одну запись.
- **Воздействие**: Пользователь показывает «женат» не на том партнёре.
- **Исправление**: Приоритетная миграция (по самому старому браку или по активности).

### BUG-025 · repay_loan — двойной возврат
- **Файл**: `db.py` · строка ~2400
- **Описание**: `repay_loan()` не проверяет текущий статус займа перед списанием. Можно вернуть один и тот же заём дважды.
- **Воздействие**: Кредитор получает двойную выплату.
- **Исправление**: `WHERE status = 'accepted'` в UPDATE.

### BUG-026 · Аукцион — UPDATE без RETURNING
- **Файл**: `db.py` · строка ~6770
- **Описание**: Обновление ставки и последующий SELECT — два запроса. Между ними другая ставка может перебить.
- **Воздействие**: Неправильный `highest_bidder_id` записан в лот.
- **Исправление**: `UPDATE ... RETURNING *`.

### BUG-027 · VIP покупка без проверки текущего статуса
- **Файл**: `miniapp_views.py` · строки 2734–2752
- **Описание**: При покупке VIP нет проверки `WHERE vip=0`. Пользователь может покупать VIP бесконечно.
- **Воздействие**: Бесконечное продление VIP за фиксированную цену (если цена ниже выгоды VIP).
- **Исправление**: Проверять текущий статус VIP перед покупкой.

### BUG-028 · AppContext — молчаливый провал аутентификации
- **Файл**: `frontend/src/AppContext.tsx` · строки 33–44
- **Описание**: При провале `fetchUserData()` ошибка поглощается: `catch { }`. Пользователь видит пустой экран без возможности повторить.
- **Воздействие**: При недоступности бэкенда мини-приложение полностью мертво, без объяснения.
- **Исправление**: Добавить error state + retry button в AppContext.
